# MELSEC 対応の計画

三菱 MELSEC Q (Q03UDECPU / GX Works2) に faRuby を載せるための記録です。
**実機で確かめた事実**と、そこから決めた設計を置いています。

確かめ方は [Ruby との違い](differences.md#確認の進め方) と同じで、確かめたい式を
並べた ST を転送し、結果をホストから読みます。**プローブは使い終わったら
消します。** 分かったことはここに書いてあり、ST そのものは git の履歴に
残っています (`plc/mitsubishi/probe/`)。

## 実機で分かったこと

対象は **Q03UDECPU** (プログラム容量 30K ステップ = 122,880 バイト)。

### KV と同じだったもの

**判断をやり直さずに済みます。**

| 項目 | 結果 |
|------|------|
| 整数除算 `-7 / 2` | -3 (0 方向へ切り捨て)。Ruby は切り下げなので補正が要る |
| 入れ子 `FOR` の `EXIT` | 内側だけを抜ける |
| 実数 → 整数 | **四捨五入** (`REAL_TO_INT(-2.7)` = -3、`(2.7)` = 3、`(-2.2)` = -2)。`INT` 命令も同じ |
| ビット指定 + インデックス修飾 | **不可**。`D260Z2.1` は構文エラー |

実数の丸めは KV-X500 と同じなので、`Dialect#rounds_float_to_int?` の補正が
そのまま使えます。ビット指定も KV と同じ制約なので、今回入れた
`$DM[a] |= 1 << 3` (読んで直して書く) がそのまま効きます。

### KV より良かったもの

| 項目 | KV-X500 | MELSEC Q |
|------|---------|----------|
| ST 1 本の大きさ | 分割が要る (KV Studio の上限) | **89,987 文字が 1 本で通る** |
| 固定領域 | ZF をバンクに分けた FM。`FRSET` でバンクを選ぶ | **ZR はバンク無し** |

**分割が要りません。** X500 は 13 本に分けたせいで 1 命令あたり 4.8 µs 損し、
速度を 20% 失っています ([分割の代償](architecture.md#分割の代償-実測))。
faRuby の ST はコードだけで 89,195 文字なので、**1 本に収まります**。

`FRSET` が無いのも大きい点です。X500 ではホストが書くバンクとスクリプトが読む
バンクが食い違い、**全命令が 0 に見える**という形で 1 往復溶かしました。

### 型付きラベル配列 — これが設計を決めた

**デバイスに割り付けた型付きラベルなら、32 ビットの計算が素の ST で 1 文で
書けます。**

```
VMD : ARRAY[0..3] OF DINT  AT D220
VMW : ARRAY[0..3] OF INT   AT D230
VMF : ARRAY[0..3] OF REAL  AT D240
VMX : ARRAY[0..3] OF REAL  AT D220   (VMD に重ねる)

VMD[Z1] := 123456;              添字にインデックスレジスタを使える
VMD[1]  := VMD[0] + VMD[0];     32 ビットの計算が 1 文
VMF[0]  := 1.5;
```

**同じアドレスに型違いのラベルを重ねられます。** `VMX[2] := 2.5` と書いてから
`VMD[2]` を読むと 1075838976 (0x40200000) が入っています。faRuby は
**レジスタの値ワードを整数とも実数とも読む**ので、これが要でした。

| faRuby | KV-5000 / X500 | MELSEC Q |
|--------|---------------|----------|
| レジスタの値 (32 ビット) | `EM1.L:Z1` | `VMD[i]` |
| 実数として | `EM1.F:Z1` | `VMX[i]` (`VMD` に重ねる) |
| 型タグ (16 ビット) | `EM0:Z1` | `VMW[i]` |
| 計算 | `EM1.L:Z1 = EM1.L:Z1 + EM1.L:Z2` | `VMD[i] := VMD[i] + VMD[j]` |

### 構造体がスロットと一対一で合う

**これで faRuby のメモリ配置をそのまま使えます。** ホスト側 (plc_codegen)
もシミュレータも `MemoryLayout` も触らずに済みます。

```
TYPE VMSLOT : STRUCT
  SLTAG : INT;      タグ  1 ワード
  SLNUM : DINT;     値    2 ワード
  SLPAD : INT;      予備  1 ワード
END_STRUCT END_TYPE

VMREG  : ARRAY[0..79] OF VMSLOT   AT D...
VMREGF : ARRAY[0..79] OF VMSLOTF  AT D...   値を REAL にした同じ形
```

**1 要素が 4 ワードちょうどで、詰め物が入りません** (実機で確認済み)。
DINT が偶数位置に揃えられると 6 ワードになって配置が合いませんでしたが、
そうはなりませんでした。faRuby のスロットは タグ 1 + 値 2 + 予備 1 の
4 ワードなので、そのまま重なります。

添字は変数で書けます。**レジスタ番号がそのまま添字**になり、KV のような
アドレス計算が要りません。

```
KV      Z1 := EM7:Z9 * 4 + EM32:Z9 + Z9;
        Z2 := EM8:Z9 * 4 + EM32:Z9 + Z9;
        EM1.L:Z1 := EM1.L:Z2;
        EM0:Z1 := EM0:Z2;

三菱    VMREG[VMOPA].SLNUM := VMREG[VMOPB].SLNUM;
        VMREG[VMOPA].SLTAG := VMREG[VMOPB].SLTAG;
```

値を実数として読むのは、**同じアドレスに REAL 版の構造体を重ねます**。
`VMREGF[3].SLNUM := 2.5` と書いてから `VMREG[3].SLNUM` を読むと
1075838976 (0x40200000) が入っています。

### 使えなかった綴り


命令を直接呼ぶ道は塞がっていました。**ラベル配列で書く理由の裏返しです。**

| 書き方 | 結果 |
|-------|------|
| `D+(TRUE, s1, s2, d)` | 構文エラー |
| `DPLUS(TRUE, s1, s2, d)` | 構文エラー |
| `TRUNC(x)` | 無い |
| `ADD_E(...)` | あるが**変数の型を揃える必要がある** |
| `DMOV` / `EMOV` / `INT` | 使える |
| 中身の無い分岐 | **不可**。注釈だけで閉じると「`;` が見つかりません」 |
| 実数と整数リテラルの比較 | **不可**。`VMSLOTF[i].SLNUM <> 0` は型が合わない |
| `SHR` / `SHL` の桁数 | **定数のみ**。変数は置けない |
| `AND` / `OR` / `XOR` | **ビット列型のみ**。32 ビット整数はそのまま渡せない |
| `DWORD#1` | **不可**。`D#` を時間の定数と読まれる |
| `FOR` の制御変数への代入 | **不可**。「1 番目の引数に不正な値」 |

### 残る警告 C9215 は放っておいてよい

**「ワードデバイスは符号付きとして比較します」** という警告が 20 件出ます。
生のワードデバイスを直に比べているところ (フレームの区分 `D5Z3`、文字列の
バイト列) です。

**faRuby はそこを符号付きとして扱います。** 比べているのはフレームの区分
(0-3) や文字数で、32767 を超えません。`INT_TO_WORD` を挟むと符号なしの比較に
変わってしまい、かえって合わなくなります。

**空の分岐は KV スクリプトでも KV-X500 の ST でも通ります。** 生成器は
`OP_NOP` や「ここへは来ない」の分岐を注釈だけで閉じているので、三菱向けだけ
何もしない代入を 1 つ置きます (`Dialect#finish`)。

置くのは**実行中のオペコードへの自己代入**です。**ループの制御変数は使えません。**
1 本にまとめたときステップのループがループカウンタを使うようになり、そこを
踏みました。`test/test_melsec_types.rb` が、回っているループの変数に代入して
いないことを見ています。

**シフトは掛け算・割り算に開きます。** faRuby がずらす桁数は実行時に決まる
ので `SHR` を使えません。桁数を 16/8/4/2/1 の 5 段に分けて、立っている桁の
ぶんだけ掛け (割り) ます。ループを回すより短く、スクラッチも要りません。
ここへ来る値は正で、桁数は 0-31 です (呼ぶ側が保証しています)。

```
IF n >= 16 THEN v := v / 65536; n := n - 16; END_IF;
IF n >=  8 THEN v := v / 256;   n := n -  8; END_IF;
...
```

**ビット演算はビット列に読み替えます。**

```
KV    EM1.L:Z1 = EM1.L:Z1 AND 1
三菱  VMSLOT[i].SLNUM := DWORD_TO_DINT(DINT_TO_DWORD(VMSLOT[i].SLNUM) AND DWORD#1);
```

### 静かに壊れる形

**生のワードデバイスを素の式で足すと、16 ビットで計算されます。**

```
DMOV(TRUE, K100000, D190);
DMOV(TRUE, K200000, D194);
D206 := D190 + D194;      (* 300000 ではなく 37856 *)
```

エラーになりません。下位ワードだけを足した答え (34464 + 3392) が入ります。
**三菱版で生デバイスの式を使わない理由**がこれです。ラベルなら型があるので
起きません。

### ラベル名がデバイス名に見えてはいけない

**予約語も使えません** (`VAL` が弾かれました)。**`BC` も使えません。** B (リンクリレー) は 16 進アドレスなので、`BC` は
B デバイスの 0x0C と読まれます。`PC` も P (ポインタ) の 0x0C です。

16 進アドレスのデバイス (B / W / X / Y / SB / SW / DX / DY) の後ろに
`A`-`F` が続く名前は、まず衝突すると思ってください。KV の `$B1F` が
B の 0x1F になるのと同じ理屈です。

faRuby が出すラベルは **`VM` を頭に付けます**。

### 型をまたぐ代入は明示的な変換が要る

**KV は黙って広げてくれました。**

```
KV    EM1.L:Z1 := EM8:Z9;              16 ビットを 32 ビットへそのまま
三菱  VMRV[VMOPA] := INT_TO_DINT(VMOPB);
```

バイトコードから読んだオペランドは `INT`、レジスタの値は `DINT` なので、
**オペランドをレジスタに入れる箇所はすべて変換が要ります**。比較も同じで、
整数と実数を直に比べられません。

リテラル (`VMRV[i] := 4;`) はそのまま通ります。

**1 か所ずつ書き足すのは無理でした。** 命令ごとに事情が違い、抜けたところは
変換にかけるまで分かりません。変換にかけて 1 件直して、また変換にかけて、を
繰り返すことになります。

そこで、**出来上がった文の型を見て狭いほうを広げる規則を 1 つだけ**置きました
(`tools/melsec_types.rb`)。型はラベルの控えから引きます。生成器が指したものが
そのまま型になるので、表を別に持つ必要がありません。

```
VMSLOT[VMREGSLOT + a].SLNUM := VMOPERANDB;
                    ↓
VMSLOT[VMREGSLOT + a].SLNUM := INT_TO_DINT(VMOPERANDB);
```

**式ごと包まずに項ごとに変換します。** `VMTEMP32L + VMSTRCOUNT` のように
1 つの式の中で幅が混ざるところがあり、外から包んでも中は直りません。
**添字は 16 ビットのまま**です。レジスタ番号を広げても意味がありません。

同じ判定で生成物を検査します (`tools/melsec_typecheck.rb`)。**片方だけ賢く
なることがない**よう、綴り方と検査は同じ型判定を使います。テストは
`test/test_melsec_types.rb`。

使っている変換は 5 つです。**`INT_TO_DINT` 以外は実機で未確認**。

| 変換 | 箇所数 |
|-----|-------|
| `DINT_TO_INT` | 126 |
| `INT_TO_DINT` | 74 |
| `INT_TO_REAL` | 32 |
| `DINT_TO_REAL` | 30 |
| `REAL_TO_DINT` | 4 |

### ラベルは符号付き。65535 が入らない


**KV の `EM` はサフィックス無しで 16 ビット符号なし**でしたが、MELSEC の
`INT` は符号付き (-32768〜32767) です。KV の生成コードが「もう実行した」の
目印に使っている 65535 は、そのままでは入りません。

**`-1` に置き換えると壊れます。** 群の振り分けは `IF 番号 <= 上限` で見るので、
`-1` はどの群でも真になり、全部の群が実行してしまいます。**32767 を使います**
(オペコードは 0-105 なので、上限より大きい正の数なら何でも構いません)。

同じ理由で、**ビット列を 16 ビットに置く箇所も符号付きで書きます**。
-Infinity の上位ワード 0xFF80 は 65408 ではなく **-128** です。数の大きさに
意味はなく、同じビット列であれば構いません。

### 下ごしらえ (PLC 1 台ごと)



KV の「EM のローカルデバイス予約個数」に当たるものです。

1. **PC パラメータ → PLC ファイル設定 → ファイルレジスタ**で容量を確保する
   (8K ワード確保済み。faRuby の固定領域は 1 インスタンス 5,000 ワード)
2. **デバイス/ラベル自動割付設定から ZR を外す**
3. **内蔵 Ethernet ポート設定で「RUN 中書込を許可する」**
4. **デバイス/ラベル自動割付設定のワードデバイス (VAR 用) を広げる**
5. **プログラム設定に `vm_01_init` → `vm_02_body` の順で登録する**

3 を忘れると**読めるのに書けません**。MC プロトコルがエンドコード 0x55 を
返します。ホストはバイトコードを ZR へ書くので、これが無いと転送できません。

4 は 1 本にまとめたときに要ります (下記)。5 はどちらも毎スキャン実行で、
**ラダーは要りません**。`vm_01_init` は `RESET_REQ` を、`vm_02_body` は
`STATUS` を自分で見るので、呼ぶ側は順番だけ守れば足ります。

2 を忘れると、ZR のどのアドレスを書いても
**「自動割付した範囲を超えている」**で変換が止まります。アドレスを変えても
同じ文言が出るので、容量の問題に見えて紛らわしいところです。

### 一時変数の置き場所 (1 本にまとめるときに効く)

**GX Works2 は ST の途中結果を D に自動割付します。** 式が増えると一時変数も
増え、足りないと F1218「自動割付デバイス設定のワードデバイス (VAR 用範囲) の
内 D の点数が足りません」で止まります。

**分割していると各プログラムで使い回せます。** 1 本にまとめると同時に多く要る
ので、そこで初めて足りなくなります。分割は KV Studio の上限のためだけのもの
ですが、三菱では**一時変数の数が分割をやめる側の制約**になります。

変えるのは 2 か所です。

1. **デバイス/ラベル自動割付設定**でワードデバイス (VAR 用) の `D` の範囲を広げる
2. 足りなければ **PC パラメータ → デバイス設定**で `D` の点数を増やす

**faRuby の D4000-D5999 とは重ねないでください。** Q03UDECPU は既定で D が
12288 点なので、自動割付に使えるのは D6144-D12287 の 6144 点です。

型変換 (`INT_TO_DINT` など) を挟むほど一時変数が増えます。faRuby の三菱版は
232 か所で変換を挟んでいるので、ここが効きます。

`R0` と `ZR0` は**同じ場所**です。バンク付きの見え方と通し番号の見え方の違いで、
実体は同じファイルレジスタです。**faRuby は ZR だけを使い、R は触りません。**

## 大きさの見込み (実測)

**群 1 (オペコード 0x00-0x07) を手で翻訳して測りました。**

```
1,088 文字 / 59 文 → 1,176 バイト
1 文あたり 19.9 バイト (5.0 ステップ)
```

`D310 := D310 + 1;` だけを並べたプローブ 3 では 3.0 ステップでしたが、
**配列の添字が入る本物は 5.0 ステップ**でした。

同じ群を KV は 83 文で書いており、三菱は 59 文 (71%) です。**アドレス計算が
消えたぶん**が効いています。

```
KV    Z1 := EM7:Z9 * 4 + EM32:Z9 + Z9;
      Z2 := EM8:Z9 * 4 + EM32:Z9 + Z9;
      EM1.L:Z1 := EM1.L:Z2;
      EM0:Z1 := EM0:Z2;

三菱  VMRV[VMOPA] := VMRV[VMOPB];
      VMRT[VMOPA] := VMRT[VMOPB];
```

KV 全体 5,503 文から三菱は 3,912 文と見込まれ、**77,970 バイト = 容量の 63%**
になります。

| 重い群がこの | 見込み | 容量の |
|------------|-------|-------|
| 1.0 倍 (測定どおり) | 77,970 | 63% |
| 1.5 倍 | 116,955 | 95% |
| 2.0 倍 | 155,940 | **126% — 入らない** |

**測ったのはいちばん軽い群です。** `OP_SEND` を含む群 5 は型の区分検査・
文字列比較・ハッシュ探索が入るので重くなります。1.5 倍までなら入ります。

超えたときの手は見えています。**`OP_SSEND` が `OP_SEND` の組み込みメソッド
振り分けを丸ごと重複して持っており**、KV 換算で約 36,000 文字 (全体の 40%)
あります。KV では上限がスクリプトごとなので見送りましたが、三菱は 1 本なので
全体に直接効きます。

## メモリ配置

必要な量は KV と同じでした。設定 (`memory.*`) がそのまま使えます。

| 区分 | 内容 | ワード数 |
|------|------|---------|
| 可変 | VM 状態 56、レジスタ 240 (型 80 + 値 160)、フレーム 160、グローバル 300、配列プール 800 | 1,556 → **2,000** |
| 固定 | IREP 128、バイトコード 3,000、定数プール 450、シンボル表 400、メソッド表 64 | 4,042 → **5,000** |

レジスタとグローバル変数が KV より小さいのは、**型タグと値を別の配列に分けた**
ためです。KV は 1 スロット 4 ワード (型 1 + 値 2 + 予備 1) でしたが、
型付きラベルなら予備が要りません。

| | デバイス | 設定 |
|---|---------|------|
| 可変 | **D4000-D5999** | `base: 4000` |
| 固定 | **ZR0-ZR4999** | `fixed_base: 0` |
| インスタンス | **1** | |

**D は 6144 から GX Works2 の自動割付**なので、その手前に寄せています。
2 インスタンスにするなら `base: 2000` (D2000-D5999) ですが、ZR が 10,000 ワード
要るのでファイルレジスタを 16K に増やす必要があります。

## ラベル定義も生成物にする

**メモリ配置を変えたらラベルのデバイス欄も変わります。** 手で直すと必ずずれるので、
同じ配置から両方を出します。

```
plc/mitsubishi/Q03UDECPU/
  faruby_labels.tsv    貼り付け用のグローバルラベル
  faruby_vm.st         VM 本体 (1 本)
```

貼り付け用の行はタブ区切り **11 列**で、GX Works2 のラベル編集にそのまま
貼れます。列は 区分・名前・型・(空)・デバイス・IEC アドレス と、後ろに空欄 5 つ。

```
VAR_GLOBAL	VMRV	ダブルワード[符号付き](0..31)		D850	%MD0.850
```

**IEC アドレスの領域番号はデバイスで決まります。** D は 0、ZR は 12 です
(`ZR0` → `%MW12.0`)。幅は 16 ビットが `%MW`、32 ビットと実数が `%MD`。

### 32 ビットを 16 ビットに切り詰めるのはビット列を経由する

**`DINT_TO_INT` は範囲を検査します。** iQ-R は 60000 を 16 ビットデバイスへ
書こうとすると「データ変換できない不正」で CPU が止まります
(`$D320U = 60000`)。

faRuby が欲しいのは値の変換ではなく**下位 16 ビットのビット列**なので、
ビット列型を経由します。こちらは検査しません。

```
DINT_TO_INT(x)                  範囲を検査する
WORD_TO_INT(DINT_TO_WORD(x))    下位 16 ビットをそのまま
```

**GX Works2 (Q) は検査せず黙って切り詰めていました。** 機種で分けていません。
分けるとどちらかだけ直して忘れることになります。

レジスタには利用者が何を入れるか分からないので、**切り詰めるところは
すべてこの形**です。1 か所だけ直しても、次に止まる場所が分かりません。

### ワード[符号なし] は使える (未採用)

faRuby の 16 ビットを `ワード[符号なし]/ビット列[16ビット]` にすれば、
符号付きにしたせいで足し続けてきた補正がまとめて消えます。**KV の `EM` は
もともと符号なしで、生成器はそれを前提に書かれています。**

| 消える補正 | いま |
|----------|------|
| センチネル | 65535 が入らないので 32767 |
| 16 ビットのビット列 | 0xFF80 を -128 と書く |
| バイト分割 | 商と余りの符号を戻す |
| 切り詰め | ビット列を経由する |

**実機で確かめました** (iQ-R)。ビット列型ですが、四則演算も比較も書けます。

```
VMU1 := 65000;               32767 超が入る
VMU2 := VMU1 / 256;          253。符号なしで割る
IF VMU1 > 32767 THEN         成立する
VMU6 := VMU1 * 2;            64464。下位 16 ビットに回り込む
VMU5 := DINT_TO_WORD(60000); 検査しない
```

**採用していません。** 16 ビットのラベルすべてが型変更になり、`Z` レジスタは
PLC 側で符号付き固定なので混ざる式に変換が要ります。型合わせの層
(`tools/melsec_types.rb`) にも「符号なし 16 ビット」を足すことになります。
いまの形で 3 機種とも動いているので、**容量が足りなくなったときの手**として
残しておきます。

### iQ-R は ZR に割り付けたラベルを保持クラスにする


**ZR はラッチデバイスです。** GX Works3 は `VAR_GLOBAL` のまま割り付けると
変換を通しません。

```
VAR_GLOBAL クラスにラッチ設定したデバイスが割付けられています。
VAR_GLOBAL_RETAIN クラスに変更してください。
```

固定領域に置く 4 つ (`VMCODE` / `VMFSLOT` / `VMFSLOTF` / `VMFSLOTW`) が
該当します。**GX Works2 (Q) にはこの検査がありません。**

### iQ-R は書き込む前にメモリの初期化が要ることがある

ラベルの割り付けを変えて書き込もうとすると、GX Works3 が
**「グローバルラベル割付情報を書き込んだメモリを初期化後、……書き込んで
ください」**と知らせてきます。ファイルレジスタ (ZR) の確保と、ラベルの
割り付け情報が同じメモリを取り合うためと思われます。

**初期化してから書き直すと通ります** (実機で確認済み)。エラーではなく
手順の案内なので、変換そのものは通っています。

同じ画面で書き込むのは 4 つです。後ろ 2 つがラベルの実体で、
`faruby_labels.tsv` を貼り直すたびに要ります。

- シーケンスプログラム
- FB ファイル
- **グローバルラベル設定ファイル**
- **グローバルラベル割付情報**

「グローバルラベル設定の外部機器からのアクセス設定」は faRuby には
要りません。**ラベルはデバイスに割り付けてあり、ホストはデバイスを直に
読みます** (`VMPC` ではなく `D4000` と指定する)。名前では引きません。

### ラベルは CSV で取り込む

**貼り付けより確実です。** 表への貼り付けは列の数え方が版で変わり、構造体は
別の画面になります。CSV はそのまま取り込めます。

UTF-16LE のタブ区切りで、1 行目のファイル名も見出しも中身もすべて引用符で
囲みます。**列は版で違います。**

| | 列数 | デバイスの位置 |
|---|-----|-------------|
| GX Works2 (Q) | 11 | 5 列目「デバイス」 |
| GX Works3 (iQ-R) | 28 | 6 列目「割付け(デバイス/ラベル)」 |

型は IEC の綴りです (`INT` / `DINT` / `REAL` / `ARRAY [0..499] OF VMSLOTT`)。
生成器は見出しの名前で値を置くので、版が増えても列の並びを足すだけです。

構造体は型ごとに別ファイルです (`VMSLOTT.csv` など)。**先に取り込みます。**
ラベルの型の欄が構造体名を指すためです。

### 構造体の配列の先頭デバイスは取り込むたびに設定し直す

**CSV の欄に入りません。** 別画面が持っていて、表には「詳細設定」の押し
ボタンが出るだけです。

**取り込むと消えます** (実機で確認済み)。ラベルを 1 つ足しただけでも、
6 つを設定し直すことになります。

| ラベル | 先頭デバイス |
|-------|------------|
| `VMSLOT` `VMSLOTF` `VMSLOTW` | `D4000` |
| `VMFSLOT` `VMFSLOTF` `VMFSLOTW` | `ZR0` |

構造体をやめれば消せる手間ですが、**値スロットを 4 ワードの構造体で指すのが
三菱版の要**です (KV のアドレス計算が添字 1 つになる)。普通の配列にすると
1 アクセスごとに掛け算が要ります。

### 構造体の配列だけは貼り付けで渡せない




**先頭デバイスを別画面が持っています。** 表に出るのは「詳細設定」の
押しボタンだけで、書き出すと `詳細設定` という文字が入ります。

faRuby が使う構造体の配列は 5 つ (`VMSLOT` / `VMSLOTF` / `VMSLOTW` を D に、
`VMFSLOT` / `VMFSLOTF` を ZR に) なので、そこだけ手で設定します。生成した
`faruby_labels.md` に対応表が出ます。

**型名はラベル名と別にします** (`VMSLOT` に対して `VMSLOTT`)。型の欄に
構造体名が入るので、同じ名前だとどちらの話か読めません。

### インデックスレジスタは KV と同じように使える

**Z は変数としても修飾にも使えます** (実機で確認済み)。

```
Z0 := 12;          変数として
Z0 := 10 + 20;     式も書ける
D110Z0 := 2;       インデックス修飾 (KV の D110:Z0 に当たる)
ZR0Z0 := 26;       ファイルレジスタも
FOR Z0 := 1 TO 5 DO
```

KV との違いは**区切り記号だけ**です (`EM7:Z9` と `D7Z9`)。生成コードは Z1-Z8 を
算法全体の一時変数に使っているので、**そこは機種によらず同じまま**です。

ただし **Z は 16 ビット符号付き (-32768〜32767)** です。KV の Z は 32767 を
超えても折り返さないことを確かめていますが ([Ruby との違い](differences.md))、
三菱はそうとは限りません。**配置を Z に載る範囲に収めます。** いまの配置
(D4000-D5999、ZR0-ZR4999) は遠く届かないので問題ありませんが、領域を広げる
ときは効いてきます。

32 ビットの修飾 (ロングインデックス修飾 `ZZ`) が ST で使えるかは未確認です。
いまは要りません。

## Ruby から触れるデバイス

**種別はメーカーごとに違います。** キーエンスの `EM` / `MR` に当たるものは
三菱にありません。表は `tools/device_set.rb` に 1 つずつ持たせてあります。

| | キーエンス | 三菱 Q |
|---|---|---|
| ワード | EM, DM, ZF | **D, W, R, ZR** |
| ビット | R, MR, B, LR, T, C | **M, L, B, X, Y** |

種別の番号は faRuby の中だけのもので、バイトコードと生成コードの両方が
この表から出ます。**どちらも同じ機種向けに同時に作る**ので、機種ごとに
番号が違っても食い違いません。

`R` と `ZR` は同じファイルレジスタの別の見え方です。faRuby 自身は ZR しか
使わないので、Ruby からはどちらでも指せます。

**`X` は入力です。** 書けてしまいますが、リフレッシュで上書きされるので
書く意味はありません。読み取りに使ってください。

### 幅の指定 (実機で確認済み)

キーエンスはデバイスにサフィックスを付けて幅を選びます (`DM0.L:Z6` で
32 ビット)。**三菱にこの綴りはありません。** 代わりの手が 2 つあります。

**ビットデバイスは桁指定が使えます** (`K4M0Z6`)。インデックス修飾と併用でき、
16 ビットも 32 ビットも 1 文で読み書きできます。プローブ 8 で確認しました。

**ワードデバイスに 32 ビットの綴りはありません。** 16 ビット 2 回に開いて、
`VMTEMP32` / `VMTEMP32HI` の重ね合わせに載せます。同じ場所を `VMTEMP32F` で
読めば実数になります (変換ではなくビット列の読み替え)。

| 幅 | キーエンス | 三菱 (ワード) | 三菱 (ビット) |
|---|---|---|---|
| ビット 1 つ | `MR0:Z6` | — | `M0Z6` |
| 16 ビット符号付き | `DM0:Z6` | `D0Z6` | `K4M0Z6` |
| 16 ビット符号なし | `DM0.U:Z6` | `D0Z6` + 負なら 65536 を足す | `K4M0Z6` + 同じ |
| 32 ビット | `DM0.L:Z6` | `D0Z6` と `D1Z6` を重ね合わせへ | `K8M0Z6` |
| 実数 | `DM0.F:Z6` | 同上。`VMTEMP32F` で読む | `K8M0Z6` → 同じ |

**16 ビットは符号付きです。** 符号なしで読むには、負なら 65536 を足して
32 ビットに広げます。KV の `.U` はデバイスが符号なしなのでそのまま読めました。

## 速度 (実測)

`rake bench` を Q03UDECPU で走らせた値です。**測るループはキーエンスと同じ**で、
置き場のデバイスだけが違います (`$DM660L` と `$D3660L`)。

| ループ | 命令/秒 | 1 命令 | スキャン周期 |
|-------|--------|-------|------------|
| `OP_ADDI` | 35,406 | 28.2 µs | 1.41 ms |
| `OP_ADD` | 36,308 | 27.5 µs | 1.38 ms |

**KV-5000 とは CPU が違うので、速さそのものは比べられません。** 比べられるのは
同じ機種の中での変化だけです。

| | 命令/秒 | 1 命令 |
|---|--------|-------|
| KV-5000 (8 本に分割) | 42,039 | 23.8 µs |
| KV-5000 (1 本だったころ) | 52,611 | 19.0 µs |
| **MELSEC Q (1 本)** | **35,406** | **28.2 µs** |

三菱は最初から 1 本なので、**分割の代償 (KV で 1 命令あたり 4.8 µs) を
払っていません**。それでも KV-5000 より遅いのは CPU の差です。
