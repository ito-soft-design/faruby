# ハッシュの計画

ロードマップ [項目 6](roadmap.md) のうち Hash の設計メモです。まだ実装して
いません。Symbol も一緒に扱います。Hash のキーとして必要になるためです。

## 逆アセンブルで分かったこと

mrbc 3.3.0 の出力です。

```
h = {}                 OP_HASH     [2, 0]        R[2] = 空のハッシュ
h = { a: 1 }           OP_LOADSYM  [2, 0]        R[2] = symbols[0] (:a)
                       OP_LOADI_1  [3]
                       OP_HASH     [2, 1]        R[2] = 1 組ぶんのハッシュ
h = { a: 1, b: 2 }     OP_LOADSYM/LOADI を 4 つ並べてから OP_HASH [2, 2]
h[:a]                  OP_LOADSYM + OP_GETIDX [2]
h[:b] = 2              OP_LOADSYM + OP_SETIDX [3]
h.size                 OP_SEND  [2, sym(size), 0]
h.key?(:a)             OP_SEND  [2, sym(key?), 1]
h.each { |k, v| }      OP_BLOCK + OP_SENDB [2, sym(each), 0]
h = { "x" => 1 }       OP_STRING + OP_HASH       ← String が要る
```

`OP_HASH [a, b]` は **`b` 組の鍵と値**を `R[a]` から順に並べたものです。
1 組が 2 レジスタなので `OP_HASH [2, 3]` は `R[2]`-`R[7]` を読みます。

**配列のときと同じく、既存の仕組みにかなり載ります。**

- `h[:a]` / `h[:a] = 1` は `OP_GETIDX` / `OP_SETIDX`。**実装済み**で、
  型タグの枝を足すだけです (デバイス族・配列に続いて 3 つ目)
- `size` / `key?` は `OP_SEND`、`each` は `OP_SENDB`。どちらも実装済みの経路

新しく要るのは `OP_LOADSYM` と `OP_HASH`、そして実体の置き場所です。

### 見落とせない点が 2 つあります

**1. `h.each` はブロックに引数を 2 つ渡します。** `OP_ENTER [524288]` は
`524288 >> 18 = 2` で必須引数 2 個です。faRuby の反復はこれまで**常に 1 個**
しか渡していませんでした (`times` の添字、`each` の要素)。鍵と値の 2 つを
渡す形が要ります。

**2. シンボルの番号は irep ごとに違います。** `OP_LOADSYM` のオペランドは
シンボル表の索引で、**シンボル表は irep ごとに別**です。索引をそのまま値に
すると、別の irep の `:foo` と等しくなりません。

ホスト側で名前に通し番号を振る仕組みは**メソッドで既に作ってあります**
(`method_ids`)。同じ名前には同じ番号が付くので、これをそのまま使えます。
ただし今は組み込みメソッド名に番号を振っていない (`METHOD_ID_NONE`) ので、
`:each` のようなシンボルが 0 になってしまいます。**全ての名前に番号を振る**
よう変えます。VM が組み込みかどうかを見るのはメソッド番号 (1 ワード目) で、
ID (2 ワード目) ではないため、この変更で壊れる経路はありません。

## 決めること

### ハッシュの表し方 — 配列 2 本

**新しいプールを作らず、配列のスロットを 2 つ使います。** 鍵の配列と値の
配列です。値スロットは 2 ワードあるので、下位に鍵の配列、上位に値の配列の
スロット番号を入れます (デバイス参照・ブロックと同じ手)。

```
h = { a: 1, b: 2 }

  R[x]  タグ=TT_HASH  下位=3 (鍵の配列)  上位=4 (値の配列)

  スロット3  要素数=2  [:a, :b]
  スロット4  要素数=2  [1, 2]
```

**メモリ配置を変えずに済みます。** 確保・容量検査・要素の読み書きはすべて
配列のものをそのまま使えます。`vm_init.kvs` も 1 インスタンスの大きさも
変わりません。

引き換えに、ハッシュ 1 つがプールを 2 スロット消費します。既定 16 スロット
なので、ハッシュ 8 個で使い切ります。

### 検索は線形

鍵の配列を先頭から見て一致するものを探します。ハッシュ表は作りません。
**容量が 12 なので、ハッシュ関数を計算するより順に見るほうが速い**ためです。
順序が保たれるのは Ruby と同じです。

### シンボルの表し方

`TT_SYMBOL` (タグ 6、予約済み) と**ホストが振った通し番号**です。値としては
整数 1 語なので、`OP_EQ` の既存経路 (タグと値の一致) がそのまま使えます。

シンボルをデバイスへ書くと番号が書かれます。名前は VM 側に無いので戻せません。

### each の引数 2 個

反復フレームの種別に `FRAME_KIND_HASH_EACH` を足し、`set_block_argument` が
`R[1]` に鍵、`R[2]` に値を置くようにします。`call_argc` は 2 です。
種別で分ける形は `each` (配列) で作ってあるので、そこに 1 つ増えるだけです。

**`h.each { |k| }` は Ruby と違います。** Ruby は `k` に `[鍵, 値]` の配列を
渡しますが、faRuby は鍵だけを渡します。配列を毎回作るとプールを食い潰す
ためで、意図的な差です。

## 進め方

1. **Symbol** — `OP_LOADSYM` と全シンボルへの通し番号。`==` で比べられる
   ところまで。Hash と独立に確かめられる — **実装済み** (実機未確認)
2. **`OP_HASH` と添字** — 配列 2 本での確保、`OP_GETIDX` / `OP_SETIDX` の
   ハッシュ枝 (線形検索)
3. **メソッド** — `size` / `length` / `key?` / `keys` / `values`
4. **`each`** — ブロック引数 2 個

段階 1 が終われば単体テストで確かめられます。2 以降は Ruby のプログラムから
届きます。

### 段階 1 でしたこと

- `OP_LOADSYM` を実装。値はシンボル表の 2 ワード目 (通し番号)
- **すべての名前に通し番号を振る**ようにした。以前は組み込みメソッド名を
  飛ばしていたので、`:each` のようなシンボルが 0 になってしまう
- **メソッド表は ID で引くため、名前の数だけ枠が要ります。** 番号を振る
  対象が広がったぶん枠も要るので、`max_methods` を 32 → 64 にし、溢れたら
  転送前に止める検査を足しました。以前は上限検査が無く、表の外を読み書き
  する可能性がありました

シミュレータで確認済みです。**irep をまたいだ比較**が要点で、メソッドの
戻り値のシンボルとトップレベルのシンボル、ブロックの中のシンボル、
メソッド名と同じ名前のシンボル、組み込みメソッドと同じ名前のシンボルが
すべて正しく比較できます。

## 先送りする論点

**文字列キー。** `{ "x" => 1 }` は `OP_STRING` になるため String の後です。
Symbol キーだけで始めます。

**削除。** `h.delete(:a)` は要素をずらす必要があります。`<<` と違って
「返さないスロット」の方針と噛み合わないので、後回しにします。

**`Hash.new(0)` の既定値。** `OP_SSEND` でクラスメソッドを呼ぶ形になり、
クラスの仕組みが要ります。範囲外です。

## 確認が要ること

- ハッシュ 1 つが 2 スロットで足りるか。実際のプログラムで 16 スロットが
  どれくらい持つか
- `OP_HASH` のオペランドが「組の数」であることの実機確認 (逆アセンブルでは
  そう読めるが、3 組以上で確かめる)
- `h.each { |k| }` (引数 1 個) が止まらずに動くか
