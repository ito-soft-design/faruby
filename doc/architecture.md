# アーキテクチャ

## VM の仕組み

mruby/c はレジスタベースの VM です。スタックベースではなく、各命令がレジスタ番号を指定して操作します。

### レジスタ構成

- `R[0]` : self (トップレベルでは 0)
- `R[1]` ~ `R[nlocals-1]` : ローカル変数
- `R[nlocals]` ~ `R[nregs-1]` : テンポラリレジスタ (計算用)

### バイトコード形式

mruby 2.0 以降の可変長バイトコードを使用します。各命令は 1 バイトのオペコードと可変長のオペランドで構成されます。

| 形式 | バイト数 | レイアウト |
|------|---------|-----------|
| Z    | 1       | [opcode] |
| B    | 2       | [opcode][a:8] |
| BB   | 3       | [opcode][a:8][b:8] |
| BS   | 4       | [opcode][a:8][b:16] |
| BSS  | 6       | [opcode][a:8][b:16][c:16] |
| BBB  | 4       | [opcode][a:8][b:8][c:8] |
| S    | 3       | [opcode][a:16] |
| W    | 4       | [opcode][a:24] |

16ビット以上のオペランドはビッグエンディアンです。

### RITE バイナリ形式

mrbc が出力する `.mrb` ファイルの構造:

```
+-------------------------------+
| Binary Header (20 bytes)      |  "RITE" + version + size + compiler
+-------------------------------+
| IREP Section Header (12 bytes)|  "IREP" + section_size + rite_version
+-------------------------------+
| IREP Record (top-level)       |  nlocals + nregs + ilen + 命令列 + pool + symbols
+-------------------------------+
| END Section (8 bytes)         |  "END\0" + 0x00000008
+-------------------------------+
```

## PLC メモリマップ (EM レジスタ)

Keyence KV-5000 の EM (拡張データメモリ) を使用します。DM はモジュールで使用されるため避けます。

### VM 状態領域 (EM0-EM19)

| EM | 用途 | 型 | 説明 |
|----|------|-----|------|
| EM0 | PC | .U | プログラムカウンタ (バイトオフセット) |
| EM1 | STATUS | .U | 0=停止, 1=実行中, 2=完了, 3=エラー |
| EM2 | ERROR | .U | エラーコード (0=正常) |
| EM3-4 | STEP_COUNT | .D | 累計実行命令数 |
| EM5 | STEPS_PER_CYCLE | .U | 1スキャンあたり実行命令数 |
| EM6 | CURRENT_OPCODE | .U | 最後にデコードしたオペコード |
| EM7-9 | OPERANDS | .U | オペランド a, b, c |
| EM10 | BYTECODE_LEN | .U | バイトコード長 |
| EM11 | NREGS | .U | レジスタ数 |
| EM12 | NLOCALS | .U | ローカル変数数 |
| EM13 | RESET_REQ | .U | リセット要求 (1=要求, vm_init で処理後 0 に戻る) |
| EM14 | NUM_SYMBOLS | .U | シンボル数 |

### レジスタファイル (EM100-EM259)

VM レジスタ R[n] は 32 ビット符号付き整数として格納されます。

```
R[n] = EM(100 + n * 2).L
```

各レジスタは 2 ワード (EM 2 個) を使用します。`.L` サフィックスで 32 ビット符号付きアクセスします。

| VM レジスタ | EM アドレス |
|------------|------------|
| R[0] (self) | EM100.L |
| R[1] | EM102.L |
| R[2] | EM104.L |
| ... | ... |
| R[79] | EM258.L |

### バイトコード領域 (EM1000-EM3999)

バイトコードは 1 バイト / 1 EM レジスタで格納します (簡易方式)。

```
byte[n] = EM(1000 + n).U
```

フェッチは Z レジスタ間接アドレッシング (`Z1 = PC + 1000` → `EM0:Z1`) で行い、PC をインクリメントします。

### 定数プール (EM4000-EM4499)

```
Pool[n] = EM(4000 + n * 2).L
```

### デバイスマッピングテーブル (EM5000-EM5199)

グローバル変数と PLC デバイスの対応を格納します。各シンボルにつき 2 EM ワード:

```
EM(5000 + idx * 2)     = device_type   (0-9)
EM(5000 + idx * 2 + 1) = device_address
```

| デバイスタイプ | ID | 種別 | アクセス | 用途 |
|-------------|-----|------|---------|------|
| EM | 0 | ワード | .L (32ビット) | 拡張データメモリ |
| DM | 1 | ワード | .L (32ビット) | データメモリ |
| ZF | 2 | ワード | .L (32ビット) | ファイルレジスタ |
| R | 3 | ビット | 個別ビット (0/1) | 内部リレー |
| MR | 4 | ビット | 個別ビット (0/1) | 補助リレー |
| B | 5 | ビット | 個別ビット (0/1) | リンクリレー |
| L | 6 | ビット | 個別ビット (0/1) | ラッチリレー |
| ~~CR~~ | ~~7~~ | ~~ビット~~ | — | コントロールリレー (インデックス扱い不可、非対応) |
| T | 8 | ビット | 個別ビット (0/1) | タイマ |
| C | 9 | ビット | 個別ビット (0/1) | カウンタ |

**ワードデバイス** (EM, DM, ZF) は `.L` サフィックスで 32 ビット符号付き整数としてアクセスします。

**ビットデバイス** (R, MR, B, L, T, C) は個別ビットとしてアクセスします。書き込み時は非0→ON(1)、0→OFF(0) に変換されます。ビットデバイスは `.L` や `.U` での間接アクセスが 16 飛びになるため、個別ビットとして直接アクセスする必要があります。

**注意**: CR (コントロールリレー) はインデックス修飾による間接アクセスができないため非対応です。

Ruby のグローバル変数名から PLC デバイスを特定する命名規則:

| Ruby コード | シンボル | device_type | アドレス |
|------------|---------|-------------|---------|
| `$DM100` | `"$DM100"` | 1 (DM) | 100 |
| `$MR10` | `"$MR10"` | 4 (MR) | 10 |
| `$ZF500` | `"$ZF500"` | 2 (ZF) | 500 |
| `$foo` | `"$foo"` | 0 (EM) | 6000+ (自動割当) |

デバイス名にマッチしないグローバル変数 (`$foo` 等) は EM6000+ 領域に自動割当されます。

### 汎用グローバル変数領域 (EM6000+)

デバイス名にマッチしないグローバル変数の格納先です。32 ビット (2 ワード/変数) で順番に割り当てられます。

## KV スクリプト VM 実行モデル

### fetch-decode-execute ループ

```
FOR EM20 = 1 TO EM5 (STEPS_PER_CYCLE)
    1. オペコードフェッチ: Z1 = PC + 1000; EM0:Z1 を読み、PC++
    2. デコード: IF/ELSE IF チェーンでオペコード判定
    3. オペランドフェッチ: 形式に応じて追加バイトを読む
    4. 実行: レジスタ操作
    5. STOP/RETURN で BREAK
NEXT
```

### Z レジスタの使い方

KV スクリプトでは Z1-Z12 を間接アドレッシングに使用します。

- Z1 : バイトコードアドレス計算 (PC + 1000)
- Z2 : レジスタアドレス計算 (a * 2 + 100)
- Z3-Z6 : テンポラリ

### スキャンサイクルとの関係

- FOR ループは 1 スキャン内で完了します
- STEPS_PER_CYCLE が大きすぎるとスキャンタイムが延びます
- 推奨初期値: 50

## 対応オペコード

### マイルストーン1: 整数四則演算

| Opcode | Code | Format | 動作 |
|--------|------|--------|------|
| OP_NOP | 0x00 | Z | 何もしない |
| OP_MOVE | 0x01 | BB | R[a] = R[b] |
| OP_LOADL | 0x02 | BB | R[a] = Pool[b] |
| OP_LOADI8 | 0x03 | BB | R[a] = signed(b) |
| OP_LOADINEG | 0x04 | BB | R[a] = -b |
| OP_LOADI__1 | 0x05 | B | R[a] = -1 |
| OP_LOADI_0..7 | 0x06-0x0D | B | R[a] = 0..7 |
| OP_LOADI16 | 0x0E | BS | R[a] = signed16(b) |
| OP_LOADI32 | 0x0F | BSS | R[a] = (b<<16)\|c |
| OP_LOADSELF | 0x12 | B | R[a] = self (=0) |
| OP_LOADNIL | 0x11 | B | R[a] = 0 |
| OP_RETURN | 0x38 | B | VM 停止 (トップレベル) |
| OP_ADD | 0x3C | B | R[a] = R[a] + R[a+1] |
| OP_ADDI | 0x3D | BB | R[a] = R[a] + b |
| OP_SUB | 0x3E | B | R[a] = R[a] - R[a+1] |
| OP_SUBI | 0x3F | BB | R[a] = R[a] - b |
| OP_MUL | 0x40 | B | R[a] = R[a] * R[a+1] |
| OP_DIV | 0x41 | B | R[a] = R[a] / R[a+1] |
| OP_STOP | 0x69 | Z | VM 停止 |

### マイルストーン2: 条件分岐・ループ

#### 真偽値の表現

- true = 1 (整数)、false/nil = 0 (整数)
- 条件判定: 0 は偽、非0 は真

#### ブーリアン値ロード

| Opcode | Code | Format | 動作 |
|--------|------|--------|------|
| OP_LOADTRUE | 0x13 | B | R[a] = 1 |
| OP_LOADFALSE | 0x14 | B | R[a] = 0 |

#### 比較演算

| Opcode | Code | Format | 動作 |
|--------|------|--------|------|
| OP_EQ | 0x42 | B | R[a] = (R[a] == R[a+1]) ? 1 : 0 |
| OP_LT | 0x43 | B | R[a] = (R[a] < R[a+1]) ? 1 : 0 |
| OP_LE | 0x44 | B | R[a] = (R[a] <= R[a+1]) ? 1 : 0 |
| OP_GT | 0x45 | B | R[a] = (R[a] > R[a+1]) ? 1 : 0 |
| OP_GE | 0x46 | B | R[a] = (R[a] >= R[a+1]) ? 1 : 0 |

#### ジャンプ

| Opcode | Code | Format | 動作 |
|--------|------|--------|------|
| OP_JMP | 0x25 | S | PC += signed16(a) |
| OP_JMPIF | 0x26 | BS | if R[a] != 0 then PC += signed16(b) |
| OP_JMPNOT | 0x27 | BS | if R[a] == 0 then PC += signed16(b) |
| OP_JMPNIL | 0x28 | BS | if R[a] == 0 then PC += signed16(b) |

ジャンプオフセットは**相対値** (符号付き16ビット)。オフセットの基点は全オペランドを読み終えた後の PC。ループ (while) では負のオフセットで後方ジャンプする。

### マイルストーン3: グローバル変数で PLC I/O

| Opcode | Code | Format | 動作 |
|--------|------|--------|------|
| OP_GETGV | 0x15 | BB | R[a] = global[symbols[b]] |
| OP_SETGV | 0x16 | BB | global[symbols[b]] = R[a] |

オペランド `b` は IREP シンボルテーブルのインデックス。デバイスマッピングテーブル (EM5000+) を参照し、対応する PLC デバイスにアクセスする。全デバイスは 32 ビット (.L) アクセスで統一。

## mruby バージョン対応

### 現在の対応バージョン

**mruby 3.3.0** (RITE バイナリ形式 `"0300"`)

### mruby 4.0 への移行メモ

mruby 4.0.0 (2026年4月リリース) では以下の非互換変更があり、対応が必要になる。

#### RITE バイナリ形式

- バージョンが `"0300"` → `"0400"` に変更。バイナリ互換性なし
- ヘッダー構造自体は同一 (20バイト)
- セクション識別子 (`IREP`, `END\0` 等) は変更なし
- **影響箇所**: `tools/mrb_parser.rb` のヘッダーバージョンチェック

#### オペコード番号の変更

13個の新オペコードが enum の途中に挿入されたため、挿入位置以降の全オペコード番号がずれる。LOAD 系 (0x00-0x0F付近) は変化なしだが、SEND/RETURN/算術系は番号が変わる。

主な新オペコード:

- `OP_SEND0`, `OP_SSEND0`: 引数なしメソッド呼び出し (高速化)
- `OP_RETSELF`, `OP_RETNIL`, `OP_RETTRUE`, `OP_RETFALSE`: 1バイト特殊 return
- `OP_ADDILV`, `OP_SUBILV`: ローカル変数の加減算融合命令
- `OP_BLKCALL`: ブロック直接呼び出し

リネーム: `OP_LOADT` → `OP_LOADTRUE`, `OP_LOADF` → `OP_LOADFALSE`

**影響箇所** (オペコード番号がハードコードされている):

1. `tools/disasm.rb` — OPCODES テーブル
2. `simulator/kv_vm_simulator.rb` — fetch-decode-execute のオペコード判定
3. `plc/keyence/vm_core.kvs` — PLC 側 VM の IF/ELSE IF チェーン

#### OP_ENTER の変更

ビットレイアウトが 23bit → 24bit に拡張 (`n1:m5:o5:r1:m5:k5:d1:b1`)。マイルストーン1では未使用だが、メソッド呼び出し対応時に影響する。

#### 対応方針

1. **オペコード定義の分離**: バージョン別のオペコードテーブルファイルを用意し、RITE ヘッダーのバージョンで自動切替
2. **vm_core.kvs の自動生成**: オペコードテーブルから vm_core.kvs を生成するスクリプトを作成し、バージョン変更時は再生成で対応
3. **ops.h からの自動生成**: mruby ソースの `include/mruby/ops.h` を解析してオペコードテーブルを自動生成する方式も検討
