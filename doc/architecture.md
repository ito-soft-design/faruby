# アーキテクチャ

Ruby と PLC で意味が食い違う箇所と、その埋め方は
[Ruby との違い](differences.md) にまとめてあります。
新しい機種に対応する際に実機で確認すべき項目もそちらです。

## VM の仕組み

mruby/c はレジスタベースの VM です。スタックベースではなく、各命令がレジスタ番号を指定して操作します。

### レジスタ構成

- `R[0]` : self (トップレベルでは 0)
- `R[1]` ~ `R[nlocals-1]` : ローカル変数
- `R[nlocals]` ~ `R[nregs-1]` : テンポラリレジスタ (計算用)

### バイトコード形式

mruby 2.0 以降の可変長バイトコードを使用します。各命令は 1 バイトのオペコードと可変長のオペランドで構成されます。

| 形式 | バイト数 | レイアウト |
|------|---------|-----------|
| Z    | 1       | [opcode] |
| B    | 2       | [opcode][a:8] |
| BB   | 3       | [opcode][a:8][b:8] |
| BS   | 4       | [opcode][a:8][b:16] |
| BSS  | 6       | [opcode][a:8][b:16][c:16] |
| BBB  | 4       | [opcode][a:8][b:8][c:8] |
| S    | 3       | [opcode][a:16] |
| W    | 4       | [opcode][a:24] |

16ビット以上のオペランドはビッグエンディアンです。

### RITE バイナリ形式

mrbc が出力する `.mrb` ファイルの構造:

```
+-------------------------------+
| Binary Header (20 bytes)      |  "RITE" + version + size + compiler
+-------------------------------+
| IREP Section Header (12 bytes)|  "IREP" + section_size + rite_version
+-------------------------------+
| IREP Record (top-level)       |  nlocals + nregs + ilen + 命令列 + pool + symbols
+-------------------------------+
| END Section (8 bytes)         |  "END\0" + 0x00000008
+-------------------------------+
```

## PLC メモリ配置

faRuby が使用する領域は**設定ファイルで指定します**。ラダーが使用していない
領域を割り当ててください。重なると双方が壊れます。

```yaml
# faruby.yml (faruby_default.yml の値を上書きする)
memory:
  device: EM        # 使用するデバイス種別
  base: 20000       # faRuby が使用する領域の先頭
  align: 1000       # ブロックサイズをこの倍数に切り上げる
  instances: 2      # 同時実行するインスタンス数
  max_regs: 80
  max_bytecode: 3000
  max_pool: 150
  max_symbols: 100
  max_globals: 100
  max_ireps: 16
  max_frames: 16     # 呼び出しの深さの上限
  max_methods: 32    # ユーザー定義メソッドの数
```

現在の配置はコンソールの `memmap` コマンドで確認できます。

> **重要**: 領域の先頭アドレスは生成されるスクリプトに**定数として
> 焼き込まれます**。設定を変えたら `rake vm_core` で再生成し、KV Studio に
> 取り込んで PLC へ転送し直してください。実行時に切り替わるわけではありません。
>
> 領域の**中の**位置は実行時に決まります。バイトコード・定数プール・
> シンボル表は irep ごとに場所が違い、レジスタは呼び出しごとに窓がずれます。

### 設定ファイルの構成

| ファイル | 役割 | git |
|---------|------|-----|
| `faruby_default.yml` | 既定値の定義。編集しない | コミット |
| `faruby.yml.example` | 設定が必須の項目の雛形 | コミット |
| `faruby.yml` | 利用者の設定・差分 | 除外 |

`faruby.yml` に無い項目は `faruby_default.yml` の値が使われます。ネストした
キーは個別に解決するため、`memory.base` だけを書いても他のメモリ設定は
既定値のまま残ります。

`rake vm_core` は `faruby.yml` の上書きを反映します。一方テストは
`faruby_default.yml` だけを見るため、生成スクリプトのバイト一致検証
(手編集の検出) は利用者設定に左右されません。

その代わり、`faruby.yml` で配置を上書きして再生成すると、生成物は
その設備専用になりコミット済みのスクリプトと一致しなくなります
(バイト一致テストが失敗します)。**恒久的な配置はこのリポジトリの
`faruby_default.yml` に書いてください。** `faruby.yml` での上書きは
一時的な検証用と考えると運用が破綻しません。

### 領域の並び

1インスタンス分のブロックを `instances` 個並べた配置です。

```
base + 0 * instance_size   インスタンス0
base + 1 * instance_size   インスタンス1
```

ブロック内はサイズ設定から詰めて計算します（既定設定での例）。

領域は**実行中に変わるもの (EM)** と**変わらないもの (FM)** に分かれています。

**実行中に変わる領域 (EM)**

| 領域 | 範囲 | ワード数 |
|------|------|---------|
| VM状態 | EM20000 - EM20055 | 56 |
| レジスタスタック | EM20056 - EM20375 | 320 (80 × 4) |
| 呼び出しスタック | EM20376 - EM20535 | 160 (16 × 10) |
| メソッド表 | EM20536 - EM20599 | 64 (64 × 1) |
| 汎用グローバル変数 | EM20600 - EM20999 | 400 (100 × 4) |
| 配列プール | EM21000 - EM21799 | 800 (16 × 50) |
| 予備 (端数調整) | EM21800 - EM21999 | 200 |

合計 2000 ワード / インスタンス。

**実行中に変わらない領域 (FM)**

| 領域 | 範囲 | ホストから | ワード数 |
|------|------|-----------|---------|
| IREPテーブル | FM0 - FM127 | ZF98304 - | 128 (16 × 8) |
| バイトコード | FM128 - FM3127 | ZF98432 - | 3000 |
| 定数プール | FM3128 - FM3727 | ZF101432 - | 600 (150 × 4) |
| シンボル表 | FM3728 - FM4127 | ZF102032 - | 400 (100 × 4) |
| 予備 (端数調整) | FM4128 - FM4999 | | 872 |

合計 5000 ワード / インスタンス。

**バイトコード・定数プール・シンボル表は全 irep で 1 つの領域を分け合います。**
メソッドを定義すると本体が子 irep になり、同じ領域を先頭から詰めて使います。
どの irep がどこにいるかは IREP テーブルに入れ、実行時に引きます。

### FM と ZF

FM は ZF をバンクに分けたものです。1 バンク 32768 ワードで n = 0-3、faRuby は
**バンク 3** を使います。

- **スクリプトからは FM**。先頭で `FRSET(3)`、末尾で `FRSET(0)` に戻します。
  現在のバンクを読む命令が無いため、Z レジスタのように退避して戻せません。
  **ラダーが 0 以外のバンクを使っていると壊します。**
- **ホストからは ZF の絶対アドレス**。バンクを選ぶ手段が無いためです。
  バンク 3 の FM0 は ZF98304 です。

FM のアドレスは 0-32767 で 16 ビットに収まるため、インデックスレジスタ Z に
載ります。ZF の絶対アドレス (最大 131071) は 16 ビットを超えるため、
スクリプト側で直接使うことはできません。

分けたことで EM 側は小さくなりました。固定側の転送はプログラムを
入れ替えたときだけで、実行中は読むだけです。

各領域の合計は 1760 ワードですが、`align` (既定 1000) の倍数に切り上げるため
2000 ワードを占有します。開始・終了アドレスが区切りの良い値になり、
複数インスタンスの場合も各ブロックが EM20000 / EM22000 / EM24000 と
丸い境界に載ります。

アドレス配置は [tools/memory_layout.rb](../tools/memory_layout.rb) が計算し、
レイアウトに依存しない定数は [tools/vm_constants.rb](../tools/vm_constants.rb)
にあります。

### 複数インスタンス

`instances` の数だけ独立した VM が動き、それぞれ別の Ruby プログラムを
並行して実行します。既定は 2 です。

ブロック先頭は Z9 に載り、ブロック内の位置はオフセットをインデックス修飾で
足して指します (`EM7:Z9`)。命令本体は 1 つだけで、外側の `FOR ... STEP` が
ブロック先頭を載せ替えながら全インスタンスを巡ります。

```
FOR Z9 = 20000 TO 25000 STEP 5000     ' インスタンスごと
    IF EM1:Z9 = 1 THEN                 ' そのインスタンスが実行中なら
        FOR EM20:Z9 = 1 TO EM5:Z9      ' 命令を回す
            Z1 = EM7:Z9 * 4 + 33 + Z9  ' レジスタアドレス
            ...
```

スクリプトを複製する案もありましたが、インスタンスの数だけ分岐が増え、
[KV Studio の変換上限](#kv-studio-の変換上限)に当たります。この方式なら
`instances` を増やしてもコメント数行しか増えません。

停止中のインスタンスは STATUS の判定で空振りするだけなので、数を増やしても
命令実行の負荷は変わりません。`steps_per_cycle` はインスタンスごとの値です。

操作対象はコンソールの `instance` コマンドで切り替えます。`compile` / `load` /
`run` / `status` / `regs` はすべて選択中のインスタンスに対して働きます。

#### KV スクリプトで確認した挙動

この方式が成立するかは実機で確かめてから実装しました。

| 確認事項 | 結果 |
|---------|------|
| Z への算術 (`Z9 = 20000 + EM39100 * 5000`) | 可 |
| 32767 を超える値 | 折り返さない (35000 を確認) |
| 式の項としての Z (`Z1 = 7 * 4 + 33 + Z9`) | 可 |
| インデックス修飾での読み・書き・32ビット | 可 |
| `FOR` のループ変数と上限にインデックス修飾 | 可 |
| 入れ子 `FOR` の `BREAK` | **内側のみ**を抜ける |
| `FOR ... STEP` | 可 |

`BREAK` が内側だけを抜けるため、既存の「停止 = BREAK」がそのまま
「このインスタンスを止めて次へ進む」になります。`STEP` が使えるため、
ブロック先頭と外側ループ変数を Z9 一本で兼ねられます。

#### インデックスレジスタの配分

KV-5000 の Z は 12 本ありますが、**Z11 と Z12 は特別な用途があり使用できません**
(実機で確認済み)。使えるのは Z1-Z10 です。

| レジスタ | 用途 |
|---------|------|
| Z1 | 主オペランド (通常は代入先の R[a]) の値スロット先頭 |
| Z2 | 副オペランド |
| Z3 | `OP_SETIDX` の代入元。空いていればテンポラリ |
| Z4-Z5 | 配列・ハッシュのスロットの見出しと要素 |
| Z6-Z8 | テンポラリ (バイトコードフェッチ、デバイステーブル参照、写しのループ) |
| Z9 | 実行中インスタンスのブロック先頭 |
| Z10 | 未使用 |

**faRuby が使うのは Z1-Z9 です。** 定義は `KvsEmitter::USED_Z` の 1 か所で、
退避コードもテストもここから作ります。役割は命令ごとに違うので、上の表は
どの命令でも変わらないものだけを挙げています。

Z が足りないところでは VM 状態の空きワードを作業に使います。文字列の比較や
走査がそうで、`FOR` のループ変数はデバイスでもよいことを利用しています。

## デバイスと VM 状態

Keyence KV-5000 の EM (拡張データメモリ) を既定で使用します。DM はモジュールで使用されるため避けます。

### VM 状態領域 (ブロック先頭から 56 ワード)

アドレスはブロック先頭 (`memory.base` + インスタンス番号 × ブロックサイズ)
からのオフセットです。既定設定では EM20000-EM20055。

定義は [tools/memory_layout.rb](../tools/memory_layout.rb) の `OFFSET_*` が
唯一の出どころで、この表に漏れがないことはテストで確かめています。

| オフセット | 用途 | 型 | 説明 |
|-----------|------|-----|------|
| +0 | PC | .U | プログラムカウンタ (バイトオフセット) |
| +1 | STATUS | .U | 0=停止, 1=実行中, 2=完了, 3=エラー |
| +2 | ERROR | .U | エラーコード (0=正常) |
| +3-4 | STEP_COUNT | .D | 累計実行命令数。フェッチのたびに `INC` で 1 増える (実測 1.5%) |
| +5 | STEPS_PER_CYCLE | .U | 1スキャンあたり実行命令数 |
| +6 | CURRENT_OPCODE | .U | 最後にデコードしたオペコード |
| +7-9 | OPERANDS | .U | オペランド a, b, c |
| +10 | BYTECODE_LEN | .U | バイトコード長 |
| +11 | NREGS | .U | レジスタ数 |
| +12 | NLOCALS | .U | ローカル変数数 |
| +13 | RESET_REQ | .U | リセット要求 (1=要求, vm_init で処理後 0 に戻る) |
| +14 | NUM_SYMBOLS | .U | シンボル数 |
| +16-17 | TEMP32 | .L | 32ビット合成スクラッチ (下位が先) |
| +18-19 | TEMP32_B | .L | 2つ目の32ビットスクラッチ。除算の切り下げ補正で余りを置く |
| +20 | LOOP_COUNTER | .U | fetch-decode-execute の FOR カウンタ |
| +21-29 | Z_SAVE | .U | インデックスレジスタ Z1-Z9 の退避先 (全インスタンス共通) |
| +30 | CUR_IREP | .U | 実行中の irep 番号 |
| +31 | FRAME_SP | .U | 呼び出しフレームの段数 (0 = トップレベル) |
| +32 | REG_BASE | .U | レジスタ窓の先頭 (ブロック内オフセット) |
| +33 | CUR_BYTECODE | .U | 実行中の irep のバイトコード先頭 (FM の絶対アドレス) |
| +34 | CUR_POOL | .U | 同じく定数プール先頭 |
| +35 | CUR_SYMBOLS | .U | 同じくシンボル表先頭 |
| +36 | NUM_IREPS | .U | irep の数 |
| +37 | CALL_ARGC | .U | 呼び出し中の実引数の数。`OP_ENTER` が定義と突き合わせる |
| +38 | IREP_TABLE | .U | このインスタンスの IREP テーブル先頭 (FM の絶対アドレス) |
| +39 | ARRAY_SP | .U | 次に渡す配列プールのスロット番号。返さないので減らない |
| +40 | STR_ENCODING | .U | ソースの文字コード (0=UTF-8, 1=Shift_JIS, 2=ASCII) |
| +41 | STR_FILL | .U | 固定長でデバイスへ書いたときの余りを埋めるバイト (`FARUBY_STR_FILL`) |
| +42-46 | 文字列の作業 | .U | 中身を比べる・継ぎ足すときの作業場所 |
| +47-51 | 文字の切れ目 | .U | `length` と `s[i]` が使う走査の作業場所 |
| +52 | LADDER_INSTANCES | .U | ラダーの外側 FOR の回数 (全インスタンス共通) |
| +53 | LADDER_STEPS | .U | ラダーの内側 FOR の回数。走らないインスタンスは 0 (全インスタンス共通) |
| +54 | DISPATCH | .U | 振り分け用のオペコード番号。担当の群が実行したら空き番号で潰す |

+30 以降は**実行中の irep のもの**です。irep が複数になったため、命令
フェッチ・定数プール・シンボル表の位置は定数ではありません。命令ごとに
IREP テーブルを引くとスキャンタイムが延びるので、切り替えのときだけ
ここへ写します。

+42 以降を**インデックスレジスタではなくデバイスに置いてある**のは、
呼ぶ側 (`OP_EQ` / `!=` / ハッシュの鍵) で Z の空きが違い、共通の手順に
できないためです。`FOR` のループ変数はデバイスでもよいので、Z はアドレスの
計算 1 本で足ります。

#### インデックスレジスタ (Z) の退避

Z はラダーと共有する資源です。faRuby は Z1-Z9 を作業用に書き換えるため、
そのままではラダー側の値を壊します。スクリプトの先頭で退避し末尾で復元する
ことで、faRuby の実行前後で Z の内容が変わらないようにしています。退避は
1 スキャンにつき 1 回だけで、命令ごとの負荷は増えません。

退避・復元はインスタンスループの**外側**で行うため、退避先だけは絶対アドレス
です。全インスタンスで 1 箇所を共有し、置き場所はインスタンス0のブロック内で
足ります。他のインスタンスの同じ位置は未使用のまま残ります (9 ワード)。

`vm_01_init.kvs` も同じ場所へ退避・復元します
(VM 本体とは実行タイミングが排他なので共有できます)。

使用する Z の範囲は `KvsEmitter::USED_Z` が唯一の定義で、退避コードも
テストもここから導かれます。生成コードが宣言外の Z を使っていないことは
テストで検証しています。

実機での確認方法は、退避領域を実行中に読むことです。ここには毎スキャンの
先頭で Z が書き込まれるので、値は「前スキャン末尾の復元が効いたか」を
そのまま映します。復元が抜けていれば、実行位置によって変わる作業値
(レジスタアドレス等) が現れます。

#### KV スクリプトの型に関する注意

##### 使用できる型サフィックス

KV-5000 実機で動作を確認済みのサフィックスです。

| サフィックス | 意味 | 占有 | 検証内容 |
|------------|------|------|---------|
| (なし) | 16ビット符号なし | 1 ワード | 既定。負値を入れると符号なしとして読まれる |
| `.U` | 16ビット符号なし | 1 ワード | `EM60.U:Z7` で確認 |
| `.S` | 16ビット符号付き | 1 ワード | `EM4802.L = EM4800.S` が −500 に符号拡張されることを確認 |
| `.L` | 32ビット符号付き | 2 ワード | `300 * 300 = 90000` が折り返さないことを確認 |
| `.D` | 32ビット符号なし | 2 ワード | `EM4804.D = 4000000000` を確認 |
| `.F` | 単精度実数 (IEEE754) | 2 ワード | `EM4806.F = 1.5` → 0x3FC00000 を確認 |

32ビット / 実数はいずれも**下位ワードが先**です。インデックス修飾付き
(`EM0.S:Z7`, `EM0.F:Z7`) でも同様に動作します。

##### インデックス修飾と型サフィックスの順序

**型サフィックスはデバイス側に付けます。インデックスレジスタの後ろに付けてはいけません。**

```
正: EM0.L:Z1      デバイス EM0 に .L → 32ビットアクセス
誤: EM0:Z1.L      .L がインデックスレジスタ Z1 に結合し、16ビットアクセスになる
```

誤った書き方はコンバートエラーにならず、**静かに 16 ビットアクセスに退化します**。
小さい値では症状が出ないため、`300 * 300` が 24464 (= 90000 − 65536) になるような
桁あふれで初めて発覚します。

インデックスの刻み幅は `.L` でも **1 ワード**で、**下位ワードが先**です
(実機検証: `EM50.L:Z7` に Z7=1 で 0x12345678 を書くと EM51=0x5678, EM52=0x1234)。
したがってレジスタ R[n] の値は `Z1 = n * 4 + レジスタ領域の先頭 + 1` として
`EM0.L:Z1` でアクセスします。

##### 演算の既定の型

**EM はサフィックスを付けないと 16 ビット符号なし**です。そのため
`EM8 = EM8 - 256` のような符号付き演算や `EM8 * 65536` のような桁上がりを伴う
演算は、16 ビットに丸められて壊れます。

負値や 65535 を超える値を組み立てる場合は、下位ワードを EM16・上位ワードを EM17 に
置いてから `EM16.L` として読み出します。これにより符号拡張と桁上がりを KV 側の
32 ビット演算に任せられます。OP_LOADINEG / OP_LOADI16 / OP_LOADI32 が
この方式を使っています。

なお OP_JMP 系の相対ジャンプは PC (EM0) も 16 ビット符号なしのため、
`EM0 = EM0 + EM8` が 16 ビットの剰余演算となり後方ジャンプが正しく成立します
(こちらはスクラッチ不要)。

### 値スロット (共通レイアウト)

レジスタ・定数プール・汎用グローバル変数は共通の **値スロット** 形式で格納します。
1 スロット = 4 ワード です。

| オフセット | 内容 | アクセス |
|-----------|------|---------|
| +0 | 型タグ (TT_*) | `.U` (16ビット) |
| +1 | 値 下位ワード | ┐ `.L` (32ビット符号付き)、+1 が起点 |
| +2 | 値 上位ワード | ┘ |
| +3 | 予備 (将来の拡張用) | — |

**値を書く命令は必ず型タグも書きます。** 値ワードの読み方が型で変わるためです。

| 型 | 値ワードの使い方 |
|----|----------------|
| 整数 | +1 と +2 を 32 ビット符号付きとして (`.L`) |
| 実数 | 同じ 2 ワードを単精度として (`.F`) |
| 文字列・配列 | 配列プールのスロット番号 |
| ハッシュ | +1 が鍵の配列、+2 が値の配列のスロット番号 |
| デバイス参照 | +1 がベースアドレス、+2 が種別と幅 |
| ブロック | +1 が本体の irep、+2 が定義元のフレーム |
| `nil` / `true` / `false` | 値は決め打ち (`TT_CANONICAL_VALUE`) |

**ハッシュ・デバイス参照・ブロックだけは +1 と +2 を別々の 16 ビットとして
使います。** 32 ビットで書くと上のワードが消えるので、`OP_HASH` の結果を
`.L` で書き換えると値の配列を見失います。

`TT_EMPTY` (0) が残るのは、`OP_ENTER` が引数の後ろのレジスタを空にしたところ
だけです。**未代入のローカル変数が偽になる**のはこのためで、Ruby の `nil` に
当たります。

+3 は使っていません。1 スロット 4 ワードにしてあるのは、スロット番号 × 4 の
アドレス計算が掛け算 1 回で済むためです。

#### 型タグ (TT_*)

`.mrb` バイナリには実行時の型情報が含まれないため、本プロジェクトで定義した番号です
(mruby/c の `mrbc_vtype` に倣った命名)。`TT_EMPTY = 0` はレジスタクリア直後の状態と一致します。

| 定数 | 値 | 真偽 | 状態 |
|------|-----|------|------|
| TT_EMPTY | 0 | 偽 | 未初期化 |
| TT_NIL | 1 | 偽 | 実装済み |
| TT_FALSE | 2 | 偽 | 実装済み |
| TT_TRUE | 3 | 真 | 実装済み |
| TT_INTEGER | 4 | 真 | 実装済み |
| TT_FLOAT | 5 | 真 | 実装済み (IEEE754 単精度) |
| TT_SYMBOL | 6 | 真 | 実装済み。値はホストが名前ごとに振った通し番号 |
| TT_STRING | 7 | 真 | 実装済み。値は配列プールのスロット番号 |
| TT_ARRAY | 8 | 真 | 実装済み。値は配列プールのスロット番号 |
| TT_HASH | 9 | 真 | 実装済み。鍵と値で 2 スロット使う |
| TT_OBJECT | 10 | 真 | トップレベルの self にのみ使用 |
| TT_DEVICE | 11 | 真 | デバイス族への参照 (`$DM` など) |
| TT_PROC | 12 | 真 | ブロック。`OP_BLOCK` / `OP_METHOD` が作る |

**この並び順には意味があります。** Ruby で偽になるのは `nil` と `false` だけなので、
偽の 2 つを真より小さい番号に置いてあります。真偽判定が `タグ > TT_FALSY_MAX` の
1 比較で済みます。並べ替えると生成コードが壊れます (テストが検出します)。

値を持たない型の値ワードは `TT_CANONICAL_VALUE` で決めています。`true` = 1、
`false` と `nil` = 0 です。こうしておくとビットデバイスへの書き込みを値だけで
判定でき、`$MR10 = true` も `$MR10 = 1` も ON になります。

#### 型タグを見る命令

| 命令 | 判定 |
|------|------|
| `OP_JMPIF` / `OP_JMPNOT` | タグで真偽を判定 (`nil` と `false` だけが偽) |
| `OP_JMPNIL` | `TT_NIL` だけに反応 (`false` では飛ばない) |
| `OP_EQ` | 数値は型が違っても値で比べ、数値以外は型と値の両方が一致したときだけ真 |
| 大小比較 | 数値の型で振り分けて値を比べる |
| 算術 | 数値の型で振り分ける。数値以外は値をそのまま計算する |

比較の結果は整数の 1/0 ではなく `TT_TRUE` / `TT_FALSE` です。

Ruby と PLC で意味が食い違う箇所と、その判断の経緯は
[Ruby との違い](differences.md) にまとめてあります。

#### 実数

値ワードの 2 ワードに IEEE754 単精度のビット列を置きます。整数と同じ場所を
別の型として読むだけなので、スロットの大きさは変わりません。

KV スクリプトは整数と実数の混在を自動で昇格するため (実機で確認済み)、
faRuby がすることは「タグを見て `.F` と `.L` のどちらの書き方を出すか」だけです。
算術と比較の命令は両オペランドの型で 4 通りに分岐します。

```
IF タグa = TT_FLOAT THEN
    IF タグb = TT_FLOAT THEN   dest.F = a.F + b.F
    ELSE                       dest.F = a.F + b.L
    END IF
    dest タグ = TT_FLOAT
ELSE IF タグb = TT_FLOAT THEN  dest.F = a.L + b.F
    dest タグ = TT_FLOAT
ELSE                           dest.L = a.L + b.L
    dest タグ = TT_INTEGER
END IF
```

整数どうしの経路を残すのは、32 ビット整数が単精度の仮数 (24 ビット) に収まらない
ためです。すべて実数にすると大きな整数の精度が落ちます。

シミュレータは演算のたびに単精度へ丸めます。Ruby の `Float` は倍精度なので、
丸めないと実機と結果がずれます。

> **制約**: 0 除算は Ruby に合わせて `Infinity` を返しますが、KV-5000 は
> `Infinity` を保持・転送できても**演算に使うと軽度エラーになります**。
> 詳細は [Infinity は演算に使えない](differences.md#制約infinity-は演算に使えない)。

デバイスへ書き込むときは、書き込み先の幅を見てから必要な形だけを変換します。
両方の形を先に作ると、`.F` へ書くだけの場合でも `Infinity` を整数へ変換して
しまい、それ自体がエラーになります。

#### ビットデバイスの読み取り

ビットデバイス (`$MR10` など) は ON で `true`、OFF で `false` を返します。
ワードデバイス (`$DM100`) は整数のままで、非ゼロ判定は `$DM100 != 0` と書きます。

書き込み側は値で判定します (非0 → ON)。`true` = 1 / `false` = 0 と決めてあるので、
真偽値でも整数でもそのまま通ります。

#### デバイス参照 (TT_DEVICE)

`$DM100` はコンパイル時にアドレスが確定するため、実行時に計算したアドレスへは
アクセスできません。アドレスを外した `$DM` を「デバイス族」とし、添字を付けて
実行時に決めます。

```ruby
$DM[600 + i] = 0
```

`$DM[i]` は `OP_GETGV` + `OP_GETIDX` にコンパイルされます。どちらも専用命令なので
メソッド呼び出しもヒープも要りません。

`$DM` を読むと `TT_DEVICE` の参照値がレジスタに入ります。値ワードの使い方は
次のとおりです。

| ワード | 内容 |
|--------|------|
| 値 下位 | ベースアドレス (裸の `$DM` なら 0) |
| 値 上位 | デバイス種別 + アクセス幅 × 16 |

種別と幅を1ワードに詰めるのは、スロットの予備ワードを使うと `OP_MOVE` が
4 ワード目まで複製する必要が出て、複製のたびに費用がかかるためです。
種別は 0-9、幅は 0-4 なので 16 倍で分離できます。

シンボル表の +3 が種別で、1 なら「デバイス族」です。`OP_GETGV` はこれを見て、
デバイスを読むか参照値を作るかを選びます。

`OP_GETIDX` / `OP_SETIDX` は参照値から種別・幅・アドレスを取り出し、
`OP_GETGV` と同じデバイス分岐に渡します。

##### 添字はデバイス番号

**ワードデバイスは表示上のアドレスと一致しますが、MR / R / B は一致しません。**
MR400 は番号 64、B10 は 16 です。番号空間では線形で、MR415 の次は MR500 です。
`plc_access` の `PlcDevice` が同じ規則で加減算するため、ホスト側と一致します。

##### 範囲チェック

ベース + 添字が 0-65535 に収まらなければ VM をエラー停止させます。
EM は範囲外を読むと 512 ワード周期で値が返るため、黙って別の場所を
読み書きしてしまうのを防ぎます。

##### アドレス付きに添字は付けられない

`$DM100[i]` は成立しません。`$DM100` はスカラとしても使われ、どちらも同じ
`OP_GETGV` にコンパイルされるため、VM 側で区別できないからです。
`$DM[100 + i]` と書きます。

### ラダーとの領域の住み分け

対象機 (KV-5000) の EM は EM0-EM65535 の 65536 点です。このうち
**EM20000 - EM39999 の 20000 ワードがラダー側で faRuby 用に確保**されています。
1インスタンス 2000 ワードなので 10 インスタンスまで置けます。

```
faRuby 用に確保   EM20000 - EM39999
  インスタンス0   EM20000 - EM21999
  インスタンス1   EM22000 - EM23999
  (以降 EM24000 から 2000 ワードずつ)
```

1インスタンスの大きさは `max_*` の設定から決まります。配列プールを
広げれば置けるインスタンス数は減ります。

**`memory.base` はラダーのデバイス割り付けで判断してください。**
コンソールの `memmap` で faRuby が占有する範囲を確認できます。

> **EM の内容を読んで判断することはできません。** このデバイスは初期化
> されないため、0 でも未使用とは限らず、非ゼロでも使用中とは限りません。
> 実際、EM65536 以降 (範囲外) を読むと 512 ワード周期で同じ値が返り、
> 範囲内と区別がつかない見え方をします。

### レジスタファイル

VM レジスタ R[n] は値スロット 1 個 (4 ワード) を占めます。

```
R[n] の型タグ = layout.reg_type_addr(n)   # スロット先頭
R[n] の値     = layout.reg_addr(n)        # スロット先頭 + 1 を .L で
```

既定設定では EM20032-EM20351 です。

| VM レジスタ | スロット先頭 | 値アドレス |
|------------|------------|-----------|
| R[0] (self) | EM20032 | EM20033.L |
| R[1] | EM20036 | EM20037.L |
| R[2] | EM20040 | EM20041.L |
| ... | ... | ... |
| R[79] | EM20348 | EM20349.L |

## irep の構造

**irep は mruby がプログラムを分けた単位です。** トップレベルが 1 つあり、
`def` の本体とブロックの本体がその子になります。faRuby は全 irep を PLC に
転送し、実行中にどれを見るかを切り替えます。

### 木から通し番号へ

```ruby
def twice(v)          # ← 子 irep になる
  v * 2
end

def quad(v)           # ← 子 irep になる
  twice(twice(v))
end

$DM100 = quad(3)
```

mrbc の出力は木です。faRuby はこれを**階層ごと**に並べて通し番号を振ります。
上の階層から順に、同じ階層の兄弟をまとめて並べる形です。

```
  irep の木                    並べた結果 (階層ごと)

  top ────┬── twice            0: top      ← 階層 0
          └── quad             1: twice   ┐ 階層 1。top の
                               2: quad    ┘ 子が連続する
```

**階層ごとに並べると同じ親の子が連続します。** `OP_METHOD` / `OP_BLOCK` の
オペランドは「親から見た何番目の子か」なので、親の `first_child` を足すだけで
通し番号になります。

```
  top の OP_METHOD [2, 0]  →  first_child(0) + 0 = 1  (twice)
  top の OP_METHOD [2, 1]  →  first_child(0) + 1 = 2  (quad)
```

上の木は 2 階層なので、**どちらの順に並べても結果は同じ**です。差が出るのは
3 階層からなので、`twice` の中にブロックを置いてみます。

```
  irep の木

  top ─┬─ twice ── block
       └─ quad
```

この木を 2 通りに並べると次のようになります。

```
  階層ごと (採用)                 1 本の枝を先に辿る (深さ優先)

  0: top     階層 0               0: top
  1: twice ┐ 階層 1               1: twice
  2: quad  ┘ top の子が連続       2: block   ← twice の子へ降りる
  3: block   階層 2               3: quad    ← top の子がここまで離れる
```

**階層ごとなら top の子は 1 と 2 で連続します。** 1 本の枝を先に辿ると
1 と 3 に分かれるので、足し算では引けなくなり、親ごとに子の番号を並べた表が
要ります。階層ごとならその表は 1 ワード (`first_child`) で済みます。

### IREP テーブルと領域の分け合い

バイトコード・定数プール・シンボル表は **1 つの領域を全 irep で分け合います**。
どの irep がどこにいるかは IREP テーブル (1 エントリ 8 ワード) に入れます。
上の例を既定配置で転送すると次のようになります。

```
  IREP テーブル (FM0-)              バイトコード領域 (FM128-)
  ┌──────────────────────┐          ┌────────────────────────┐
  │ irep 0        FM0    │          │ FM128            ┐     │
  │  bytecode  = FM128 ──┼────────► │  ...  top        │ 28  │
  │  len       = 28      │          │ FM155            ┘     │
  │  pool      = FM3128 ─┼───┐      │ FM156            ┐     │
  │  syms      = FM3728 ─┼─┐ │      │  ...  twice      │ 13  │
  │  nregs     = 4       │ │ │      │ FM168            ┘     │
  │  first_child = 1     │ │ │      │ FM169            ┐     │
  ├──────────────────────┤ │ │      │  ...  quad       │ 17  │
  │ irep 1        FM8    │ │ │      │ FM185            ┘     │
  │  bytecode  = FM156 ──┼─┼─┼────► └────────────────────────┘
  │  len       = 13      │ │ │
  │  syms      = FM3740 ─┼─┤ │      シンボル表 (FM3728-)
  │  ...                 │ │ │      ┌────────────────────────┐
  ├──────────────────────┤ │ └────► │ FM3728 top の 3 個     │
  │ irep 2        FM16   │ │        │   twice / quad /$DM100 │
  │  bytecode  = FM169 ──┼─┼──────► ├────────────────────────┤
  │  syms      = FM3740 ─┼─┘        │ FM3740 quad の 1 個    │
  │  ...                 │          │   twice                │
  └──────────────────────┘          └────────────────────────┘
```

**シンボル表は irep ごとに別です。** 上の例では `twice` という名前が
トップレベル (番号 0) と `quad` の中 (番号 0) の両方に現れますが、別の
エントリです。番号も irep ごとに振り直されるため、名前で照合することは
できません。だからメソッド名にはホスト側で**通し番号**を振ります
([メソッド定義・呼び出しの計画](method_calls.md))。

引数を持たない `twice` (irep 1) はシンボルを 1 つも使わないため、
シンボル表を占有しません。次の irep 2 が FM3740 から始まります。

### 実行時の切り替え

命令ごとに IREP テーブルを引くとスキャンタイムが延びます。そこで
**切り替えのときだけ VM 状態へ写し**、実行中はそれを見ます。

```
                 呼び出し (OP_SSEND)
  ┌───────────┐  ─────────────────►  ┌───────────┐
  │ irep 0    │                      │ irep 2    │
  │ を実行中  │  ◄─────────────────  │ を実行中  │
  └───────────┘   戻り (OP_RETURN)   └───────────┘

  VM 状態 (インスタンスごと)
    EM30 = 実行中の irep 番号     ← 切り替えで書き換わる
    EM33 = バイトコード先頭 ┐
    EM10 = バイトコード長   │ IREP テーブルから写す
    EM34 = 定数プール先頭   │ (命令ごとには引かない)
    EM35 = シンボル表先頭   │
    EM11 = nregs            ┘
    EM38 = IREP テーブル先頭  ← インスタンスごとに違う。転送時に書く

  命令フェッチ:  Z1 = PC + EM33:Z9  →  FM0:Z1
```

戻り先は呼び出しスタックに積みます。詳しくは
[呼び出しフレームとレジスタ窓](#呼び出しフレームとレジスタ窓) を参照してください。

**インスタンスごとに固定領域の位置が違います。** 命令本体は 1 つしか
生成されないため、`EM38:Z9` (IREP テーブルの先頭) を各インスタンスの
VM 状態に置いて、そこから引いています。

## 呼び出しフレームとレジスタ窓

メソッドを呼ぶと、レジスタは**窓をずらして共有します**。呼ばれた側の `R[0]` は
呼んだ側の `R[a]` と同じ場所です。戻り値をコピーする必要がありません。

```ruby
def twice(v)
  v * 2
end
$DM100 = twice(3)      # → OP_SSEND [1, 0, 1]   a=1, 引数1個
```

### 窓のずれ

`OP_SSEND [a, ...]` は窓を `a` スロットぶん進めます。上の例は a=1 です。

```
  レジスタスタック (ブロック先頭 +56 から。1 スロット 4 ワード)

              +56      +60      +64      +68      +72      +76
              ┌────────┬────────┬────────┬────────┬────────┬────────┐
  呼ぶ前      │ R[0]   │ R[1]   │ R[2]   │ R[3]   │        │        │
  (top)       │ self   │ ←ここに│ 3      │        │        │        │
              │        │ 戻り値 │ (引数) │        │        │        │
              └────────┴────────┴────────┴────────┴────────┴────────┘
                        ↑ 窓を +60 へ
              ┌────────┬────────┬────────┬────────┬────────┬────────┐
  呼んだ後    │        │ R[0]   │ R[1]   │ R[2]   │ R[3]   │ R[4]   │
  (twice)     │        │ self   │ v = 3  │        │        │        │
              └────────┴────────┴────────┴────────┴────────┴────────┘

  呼んだ側の R[1] と 呼ばれた側の R[0] は **同じ場所**。
  OP_RETURN が R[b] を R[0] へ写せば、戻った側からは R[1] に見える。
```

### フレームの積み方

窓をずらす前の状態はフレームに積みます。1 フレーム 10 ワード、
呼び出しスタックはブロック先頭 +376 からです。

```
  OP_SSEND                                  OP_RETURN
  ──────────►                               ◄──────────

  ┌─ 呼び出しスタック (+376-) ────────────────────────────┐
  │ フレーム0  @EM20376                                   │
  │   +0 戻り先 PC     = 14   ← 呼び出しの次の命令        │
  │   +1 戻り先 irep   = 0    ← top へ戻る                │
  │   +2 戻り先 窓     = +56  ← 呼んだ側の窓を復元        │
  │   +3 自分の窓      = +60  ← OP_GETUPVAR が見る        │
  │   +4 定義元フレーム = なし ← メソッドは外側を見ない    │
  │   +5 種別          = 0    ← 通常の呼び出し            │
  │   +6,+7 反復の現在値 ┐ times / upto が使う (32ビット) │
  │   +8,+9 反復の上限   ┘                                │
  │ フレーム1  @EM20386   ← 次の呼び出しはここへ          │
  │ ...                                                   │
  │ フレーム15 @EM20526   ← max_frames = 16               │
  └───────────────────────────────────────────────────────┘

  積んだら                            戻るときは
    reg_base += a * 4                   R[b] を R[0] へ写す
    cur_irep  = 本体の irep             frame_sp -= 1
    PC        = 0                       PC / irep / 窓 をフレームから復元
    frame_sp += 1
```

深さは `max_frames` (既定 16) とレジスタ領域の広さの両方で決まります。
窓は呼び出しのたびに前へ進むため、レジスタ領域を使い切る方が先に来ることも
あります。どちらも超えるとエラー (code 5) で停止します。**PLC はメモリが
固定なので、上限を決めて止めるしかありません。**

### ブロックが外側の変数を見る仕組み

メソッドは外側のローカル変数を見ませんが、ブロックは見ます。

```ruby
sum = 0
3.times do |i|
  sum = sum + i        # ← sum は外側 (top) の R[1]
end
```

そこでブロックの値には**本体の irep と定義元のフレーム**を持たせ、フレームには
「定義元フレーム」の欄を置いて鎖にします。`OP_GETUPVAR [a, b, c]` の `c` は
遡る段数で、鎖を `c` 回辿った先の「自分の窓」から `R[b]` を読みます。

```
  2.times do |i|          フレーム0 (外側のブロック)
    2.times do |j|          定義元 = なし  → トップレベル
      s = s + 1           フレーム1 (内側のブロック)
    end                     定義元 = 0
  end

  内側から OP_GETUPVAR [3, 1, 1]  (段数 1)
    フレーム1 の定義元 → フレーム0
    フレーム0 の定義元 → なし = トップレベル
    トップレベルの窓 (+56) の R[1] を読む
```

段数が 0 なら 1 つ外側です。`FRAME_NONE` は「フレームが無い」印で、
レジスタ領域の先頭 (トップレベルの窓) に解決します。

### バイトコード領域

バイトコードは 1 バイト / 1 ワードで格納します (簡易方式)。
既定設定では FM128-FM3127 (全 irep の合計)。

フェッチは Z レジスタ間接アドレッシング (`Z1 = PC + 実行中の irep の
バイトコード先頭` → `FM0:Z1`) で行い、PC をインクリメントします。

### 定数プール

値スロット形式です。型タグはコンパイル時に確定するため codegen が書き込みます。
既定設定では FM3128-FM3727 (150 エントリ、全 irep の合計)。

### シンボル表 (デバイスマッピングテーブル)

**シンボル表には 3 種類が混ざります。** グローバル変数名・デバイス族・
メソッド名です。4 ワード目の種別で振り分け、残りの意味が変わります。

```
種別 0 (値)          +0 device_type  +1 device_address  +2 access_type
種別 1 (デバイス族)  同上。アドレスを持たず、添字で実行時に決める
種別 2 (メソッド)    +0 組み込み番号 +1 ユーザー定義ID  +2 引数の数
```

`$` で始まるシンボルがグローバル変数、それ以外はメソッド名です。

**シンボル表は irep ごとに別です** ([irep の構造](#irep-の構造))。全 irep 分を
1 つの領域に詰め、各 irep の先頭を IREP テーブルに入れます。既定設定では
FM3728-FM4127 (100 シンボル、全 irep の合計)。

| デバイスタイプ | ID | 種別 | アクセス | 用途 |
|-------------|-----|------|---------|------|
| EM | 0 | ワード | .L (32ビット) | 拡張データメモリ (略記 `E`) |
| DM | 1 | ワード | .L (32ビット) | データメモリ (略記 `D`) |
| ZF | 2 | ワード | .L (32ビット) | ファイルレジスタ |
| R | 3 | ビット | 個別ビット (0/1) | 内部リレー |
| MR | 4 | ビット | 個別ビット (0/1) | 補助リレー (略記 `M`) |
| B | 5 | ビット | 個別ビット (0/1) | リンクリレー |
| LR | 6 | ビット | 個別ビット (0/1) | ラッチリレー (略記 `L`) |
| ~~CR~~ | ~~7~~ | ~~ビット~~ | — | コントロールリレー (インデックス扱い不可、非対応) |
| T | 8 | ビット | 個別ビット (0/1) | タイマ |
| C | 9 | ビット | 個別ビット (0/1) | カウンタ |

### ワードデバイスのアクセス幅

**ワードデバイス** (EM, DM, ZF) はアクセス幅をグローバル変数名のサフィックスで指定します。
**既定 (サフィックス無し) は 16 ビット符号付き = 1 ワード**で、PLC の慣習
(DM100 は 1 ワード) と一致します。

| Ruby 記法 | KV サフィックス | access_type | 意味 | 占有 |
|----------|--------------|-------------|------|------|
| `$DM100` | `.S` | 0 | 16ビット符号付き (既定) | 1 ワード |
| `$DM100S` | `.S` | 0 | 同上 (明示) | 1 ワード |
| `$DM100U` | `.U` | 1 | 16ビット符号なし | 1 ワード |
| `$DM100L` | `.L` | 2 | 32ビット符号付き | 2 ワード |
| `$DM100D` | `.D` | 3 | 32ビット符号なし | 2 ワード |
| `$DM100F` | `.F` | 4 | 単精度実数 | 2 ワード |

解析はデバイス名を先に取り、残りをサフィックスとして読みます。名前は正式名を
略記より先に試すため、長い方が優先されます。

- `$L100` はラッチリレー LR の 100 番であり、`$DM100L` の `L` サフィックスとは競合しません
  (デバイス名が先にマッチするため)
- `$EM100` は EM の 100 番です。略記の `E` を先に試すと `E` + `M100` になり解析に失敗します
- `$DML` は DM の族に `.L`、`$DL` は D (= DM) の族に `.L` です
- `$B1F` はリンクリレー B の 16 進アドレス 1F です。**B は 16 進アドレスなので
  `A`-`F` はアドレスの一部**になります。幅を付けたいときは `_` で区切って
  `$B1_F` と書きます。`$B1L` は `L` が 16 進数字でないため、区切らなくても
  幅として読まれます
- 10 進アドレスのデバイス (R, MR) にこの曖昧さはありません。`$R1F` は
  R1 の `.F` です

**アドレス衝突は利用者の責任です。** `$DM100L` は DM100 と DM101 の 2 ワードを占有する
ため、同じプログラム内で `$DM101` を使うと値が壊れます。

**実数 (`F`) は型が変換されます。** `$DM100F` を読むとレジスタは `TT_FLOAT` になり、
書き込むときは整数レジスタなら実数へ、実数レジスタを `.S` 等へ書くなら 0 方向へ
切り捨てて変換します。変換はアクセス幅ごとの分岐に入る前に 1 度だけ行い、
分岐の中でレジスタの型を見なくて済むようにしています。

**汎用グローバル変数** (`$foo` 等) は**値スロットをそのまま持ちます**。デバイスと
違って幅がないので、型タグごと写します。実数も配列もハッシュも文字列も
`true` / `false` / `nil` も入ります。

デバイステーブルにはスロットの先頭アドレスが入り、`OP_GETGV` / `OP_SETGV` は
シンボル種別 `SYMBOL_KIND_GLOBAL` を見てこの経路へ入ります。配列や文字列を
入れてもスロット番号が写るだけなので、**プールは増えません**。

型を入れ替えても前の値は残りません。値ワードは 32 ビットで写すため、
**ハッシュやデバイス参照が使っていた上のワードも一緒に消えます**。

`OP_SETGV` は文字列を見る前に汎用グローバルを分ける必要があり、デバイスへの
書き込みは比較が 1 つ増えます。実機では **31,342 命令/秒**で、増える前の
31,225 から落ちていません (3 回測ってばらつきは 0.1%)。0.4% ほど上に出て
いますが、この幅は測る日によって動くので、**費用は見えなかった**と読みます。

**ビットデバイス** (R, MR, B, LR, T, C) はサフィックス無しなら個別ビットとして
アクセスします。書き込み時は非0→ON(1)、0→OFF(0) に変換されます。

幅サフィックスを付けたときの意味はデバイスの種類によって違います (実機で確認済み)。
MR / R / B / LR はそのビットから連続したビット列を整数として扱い、インデックス修飾の
刻み幅は 1 ビットです。チャンネル境界に揃っていなくてもかまいません。
T / C は幅によらずタイマ・カウンタの現在値を返します。**幅を付けない
`$T0` / `$C0` は接点**で、タイムアップ・カウントアップで真になります。

以前この文書には「16 飛びになる」と書かれていましたが誤りでした。

faRuby 側は種別で場合分けせず、幅サフィックス付きなら `<デバイス>0.<幅>:Z6` を
出すだけです。意味は PLC が決めます。

デバイステーブルの幅には `ACCESS_BIT` という値を用意しました。`ACCESS_S` が 0 の
ため、「幅の指定が無い」ことを 0 では表せないからです。生成コードは
`IF Z8 = ACCESS_BIT` で個別ビットと整数を選び分けます。

> **シミュレータとの差**: シミュレータはビットを 1 ワードに 1 個ずつ持つため、
> 幅アクセスのたびにビット列を組み立て直します。T / C の現在値は
> シミュレータにタイマが無いため再現できず、ビット列として扱います。

**注意**: CR (コントロールリレー) はインデックス修飾による間接アクセスができないため非対応です。

Ruby のグローバル変数名から PLC デバイスを特定する命名規則:

| Ruby コード | シンボル | device_type | アドレス |
|------------|---------|-------------|---------|
| `$DM100` | `"$DM100"` | 1 (DM) | 100 |
| `$MR10` | `"$MR10"` | 4 (MR) | 10 |
| `$ZF500` | `"$ZF500"` | 2 (ZF) | 500 |
| `$foo` | `"$foo"` | 0 (EM) | 6000+ (自動割当) |

デバイス名にマッチしないグローバル変数 (`$foo` 等) は汎用グローバル変数領域に自動割当されます。

### 汎用グローバル変数領域

デバイス名にマッチしないグローバル変数の格納先です。値スロット (4 ワード/変数) が
出現順に割り当てられます。デバイス名付きシンボル (`$DM100` 等) はこの領域を消費しません。

```
n 番目のスロット先頭 = EM(6000 + n * 4)
n 番目の値           = EM(6000 + n * 4 + 1).L
```

**デバイスマッピングテーブルには「値ワード」のアドレス (スロット先頭 + 1) を格納します。**
これにより GETGV/SETGV の EM デバイス経路をスロット非対応のまま流用できます。
型タグは値ワードの 1 つ前 (スロット先頭) にあります。

## KV スクリプト VM 実行モデル

### fetch-decode-execute ループ

```
FOR EM20 = 1 TO EM5 (STEPS_PER_CYCLE)
    1. オペコードフェッチ: Z1 = PC + 1000; EM0:Z1 を読み、PC++
    2. デコード: IF/ELSE IF チェーンでオペコード判定
    3. オペランドフェッチ: 形式に応じて追加バイトを読む
    4. 実行: レジスタ操作
    5. STOP/RETURN で BREAK
NEXT
```

### Z レジスタの使い方

配分は[インデックスレジスタの配分](#インデックスレジスタの配分)にあります。

**Z は値スロットの先頭を指します。** 値ワードはデバイス側のオフセットで
指すので、`EM1.L:Z1` が値、`EM0:Z1` が型タグです。スロット先頭を指すのは
型タグと値の両方を 1 本の Z で読めるようにするためです。

### 命令の振り分けは番号の範囲で組に分ける

`IF` / `ELSE IF` はラダーの条件ジャンプになります。連なりの各枝は連なりの
終わりへ飛ぶので、`END IF` が出るまで対になりません。**KV Studio は対の
ない LABEL / CJ / GOTO を 200 までしか許さず**、59 本を 1 本の連なりに
並べたところで取り込めなくなりました。

そこで番号の範囲で 8 組に分け、まず組を選んでから中を見ます。

```
IF 命令 <= 7 THEN
    IF 命令 = 0 THEN ... ELSE IF 命令 = 1 THEN ... END IF
ELSE IF 命令 <= 20 THEN
    ...
END IF
```

**これが大きな速度の差になりました。**

| | 命令/秒 | スキャン周期 |
|---|--------|------------|
| 1 本の連なり | 31,342 | 1.60 ms |
| 8 組に分割 | **52,611** | **0.95 ms** |

**68% 速くなっています。** 後ろの命令ほど手前の枝を全部通っていたのが、
組を選ぶ比較 1-7 回で飛び越えられるようになったためです。これまで
「手前にある比較の数だけが効く」と測ってきたことの裏返しで、いちばん
効いたのがこの変更でした。

組の数は `KvsEmitter::DISPATCH_GROUPS` です。増やすと溜まりが減り、
後ろの命令が速くなります。

### スキャンサイクルとの関係

- FOR ループは 1 スキャン内で完了します
- STEPS_PER_CYCLE が大きすぎるとスキャンタイムが延びます
- 推奨初期値: 50

| Opcode | Code | Format | 動作 |

オペランド `b` は IREP シンボルテーブルのインデックス。デバイスマッピングテーブルを参照し、対応する PLC デバイスにアクセスする。ワードデバイスは `access_type` に応じて `.S` / `.U` / `.L` / `.D` を選択する (既定は `.S`)。

## オペコード定義表と 2 つのバックエンド

命令の定義は [tools/opcode_table.rb](../tools/opcode_table.rb) に一本化されています。
ここから PLC 側 VM・シミュレータ・逆アセンブラのすべてが導かれます。

```
              tools/opcode_table.rb   ← 命令の定義 (唯一の情報源)
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   KvsEmitter       SimVm       MRUBY_OPCODES
  (文字列を組立)   (実際に実行)    (名前と形式)
        │              │              │
        ▼              ▼              ▼
  vm_*.kvs      kv_vm_simulator    disasm.rb
```

| ファイル | 役割 |
|---------|------|
| [tools/opcode_table.rb](../tools/opcode_table.rb) | 命令定義 (唯一の情報源) |
| [tools/kvs_generator.rb](../tools/kvs_generator.rb) | KV スクリプトを組み立てるバックエンド |
| [simulator/sim_vm.rb](../simulator/sim_vm.rb) | EM メモリ上で実行するバックエンド |
| [tools/transfer_check.rb](../tools/transfer_check.rb) | 取り込み済みスクリプトとの照合 |
| `plc/keyence/vm_*.kvs` | 生成物 (コミット対象)。番号がラダーに置く順 |

**`plc/keyence/*.kvs` は生成物です。直接編集しないでください。**
命令を追加・変更する場合は `opcode_table.rb` を直してから `rake vm_core` で再生成します。

生成物をコミットするのは、KV Studio に取り込む実体が必要なことと、
差分レビューができることの 2 点が理由です。手で編集していないことは
[test/test_kvs_generator.rb](../test/test_kvs_generator.rb) が検証します
(生成結果とコミット済みファイルのバイト一致)。

### 同じ定義を 2 通りに解釈する

命令定義の本体は「バックエンド」を 1 つ受け取ります。

```ruby
OpcodeDef.new(0x3C, "R[a] = R[a] + R[a+1]") do |vm|
  vm.set_reg(:a, vm.binop(:add, vm.reg(:a), vm.reg_next(:a)))
end
```

- `KvsEmitter` に渡すと、`vm.reg(:a)` は文字列 `"EM0.L:Z1"` を返し、
  副作用としてアドレス計算の行を出力します
- `SimVm` に渡すと、`vm.reg(:a)` は EM メモリから読んだ整数を返します

`vm.if_(cond) { ... }` も同様で、KV 側は常にブロックを実行して `IF...END IF` を
出力し、シミュレータ側は条件が真のときだけブロックを実行します。

この仕組みにより、**片方にだけ命令があるという食い違いが構造的に起きません**。
以前は `OP_LOADNIL` が KV スクリプト側にだけ無く、実機で `while` を動かすまで
気づけませんでした。両者を突き合わせる `test_vm_core_parity.rb` も不要になり、
[test/test_opcode_table.rb](../test/test_opcode_table.rb) が
「全命令が両バックエンドで実行できること」を直接検証します。

命令本体には **PLC 機種固有の名前を書きません**。デバイス名・インデックス
レジスタ・型サフィックスはバックエンドの管轄です。この境界は
`test_opcode_table_has_no_device_names` が守ります。

### なぜ生成にしたか

手書き時代は同じイディオムが大量に散らばっており、修正が全箇所に及んでいました。

| 変更 | 影響箇所 |
|------|---------|
| 型サフィックスの位置 (`EM0:Z1.L` → `EM0.L:Z1`) | 91 箇所 |
| 値スロットのストライド (2 → 4 ワード) | 45 箇所 |
| オペランドフェッチの定型 | 58 箇所 (約 174 行) |

生成器ではこれらが `KvsEmitter` の 1 メソッドに集約されているため、
同種の変更は 1 箇所で済みます。`OP_LOADNIL` がシミュレータにだけあって
KV スクリプトに無い、といった実装漏れも定義表に無ければ起きません。

### 命令形式とオペランドの対応

オペランドのフェッチコードは命令形式から自動生成されます。
オペランドは順に **EM7 (a) / EM8 (b) / EM9 (c)** へ格納されます。

| 形式 | オペランド |
|------|-----------|
| Z | なし |
| B | a (1バイト) |
| BB | a, b (各1バイト) |
| BBB | a, b, c (各1バイト) |
| S | a (2バイト) |
| BS | a (1バイト), b (2バイト) |
| BSS | a (1バイト), b, c (各2バイト) |

> **注**: 生成方式への移行時に `OP_JMP` (形式 S) のオペランド格納先が
> EM8 → EM7 に変わりました。オペランド `a` は EM7、という規則に揃えたためです。
> 動作は同一で、`status` コマンドのデバッグ表示のみが変わります。

### KV Studio の変換上限

#### 対のない LABEL / CJ / GOTO は 200 まで (実機で確認済み)

**これに当たりました。** ビット演算を足して分岐が 1,148 になったところで
取り込めなくなりました。

```
[エラー600]:対のないLABEL命令またはCJ/GOTO命令の数が200を超えました。[CJ 3624]
```

`IF` / `ELSE IF` はラダーの条件ジャンプになります。連なりの各枝は連なりの
終わりへ飛ぶので、`END IF` が出るまで対になりません。**1 本の連なりに枝を
並べるほど溜まります。** 効くのは枝の総数ではなく、**同時に開いている数**
です。

命令の振り分けを[番号の範囲で組に分けて](#命令の振り分けは番号の範囲で組に分ける)
避けました。溜まりが減るうえ、**68% 速くなりました**。

数え方は `IF` を開くたびに増やし `END IF` で減らす、開いている連なりごとに
「ここまでに出た枝の数」を足す、という形で見積もれます。当たったときの
見積もりが 61、余裕のある今が 33 です。実際の数はその 3 倍強でした。

#### 1 スクリプト 264,144 文字 (実機で確認済み)

**これにも当たりました。** 配列とデバイスの写しを入れて 332,510 文字に
なったところです。行数ではなく**文字数**で、コメントも空白も数えます。

いちばん太っていたのは**字下げ**でした。入れ子が 12 段まであるので、
4 文字刻みだと空白だけで 199,664 文字 — 全体の 60% です。刻みを 2 文字に
しただけで 232,678 文字 (上限の 88%) に収まりました。`KvsEmitter::INDENT`
の 1 か所です。

| 刻み | 字下げ | 合計 | 上限比 |
|-----|-------|------|-------|
| 4 | 199,664 | 332,510 | 126% |
| 2 | 99,832 | 232,678 | 88% |
| 1 | 49,916 | 182,762 | 69% |

次に大きいのは `OP_SSEND` で、`OP_SEND` の組み込みメソッドの振り分けを
丸ごと持っています (66,014 文字)。共有すれば約 59,000 文字減ります。
コメントは 53,543 文字ですが、生成コードを読んで確かめる作業が何度も
効いているので、削るのは最後にします。

`test_kvs_generator.rb` が**転送する前に**上限と、95% を超えていないかを
見ます。取り込むまで分からないのを避けるためです。

#### 行数そのものは効かない

6,000 行を超えても変換は通ります。効くのは文字数と、上の「対のない
ジャンプ」の数です。タイマ・カウンタの警告
(`対応するタイマ命令が記述されていません`) はデバイス種別ごとの分岐で
`T0:Z6` / `C0:Z6` に触れるためで、44 件出ますが害はありません。

#### どちらもスクリプトごとに数える

**この 2 つの上限はスクリプト 1 本ごとに数えます。** 超えると
KV Studio が「複数に分割してください」と言います。**分ければ分けた
分だけ余裕が増える**ということなので、群ごとに別のスクリプトへ
出しました。次の節に構成があります。

### スクリプトの分割とラダー

命令の群ごとに別のスクリプトを生成し、**2 つのループをラダーに置きます。**

**ファイル名の番号がラダーに置く順です。**

```
[vm_01_init.kvs]                  リセットハンドラ
[vm_02_prologue.kvs]              Z 退避 / バンク選択 / 外側の回数
FOR EM20052 回                    外側 (インスタンス)
  [vm_03_instance.kvs]            Z9 を進める / 内側の回数
  FOR EM20053 回                  内側 (ステップ)
    [vm_04_fetch.kvs]             範囲検査 / fetch / PC 進め
    [vm_05_group1.kvs] … [vm_12_group8.kvs]
  NEXT
NEXT
[vm_13_epilogue.kvs]              バンク復帰 / Z 復元
```

リセットハンドラは Z の退避もバンクの選択も自分で行う独立した
スクリプトですが、**本体より先に置きます。**後ろだと、リセットを
要求したスキャンで古い状態のまま `STEPS_PER_CYCLE` 命令だけ
進んでしまいます。

ラダーが持つのは `FOR` / `NEXT` が 2 組とスクリプトの箱だけです。接点も
`CJ` も要りません。

#### 振り分けをラダーに置かない

**ラダーは群の切り方を知りません。** 群のスクリプトが自分で番号の範囲を
見て、担当外なら素通りします。ラダーに振り分けを書くと、境界を変える
たびに描き直すことになるためです。この形なら `DISPATCH_GROUPS` を増やす
ときも、ラダーに箱を足すだけで済みます。

担当外の群は比較 1-2 回で終わるので、**1 命令あたりの比較の数は 1 本に
まとめていたときと変わりません。**

#### ラダーの FOR は回数しか指定できない

途中で抜けることもできません。回数はスクリプトが決めて渡します。

| デバイス | 中身 |
|---------|------|
| `EM20052` | インスタンス数 |
| `EM20053` | ステップ数。**走らないインスタンスは 0** |

止まったときは内側のループを抜けられないので、取り込みが
どの群の範囲にも入らない番号 (65535) を `CURRENT_OPCODE` に置きます。
残りのステップは群 8 つの範囲判定だけを通って空回りします。

#### BREAK はスクリプトの中で対になっていること

ステップのループがラダーへ出たので、命令を途中で打ち切る `BREAK` は
相手を失います。**1 回だけ回る `FOR` で群の本体を包んで**受けています。
176 か所ある打ち切りはどれも直前に `STATUS` を実行中以外にしているので、
抜けた後の動きは今までと同じです。

#### 群と群の間に番号を落とさない

1 本の連なりだったころは、実装していない番号は次の組の `ELSE` が拾って
エラーにしていました。分けると**どのスクリプトも拾わずに素通りします。**
各群の下限を前の群の続きにして塞いであります (`group_range`)。実際に
31-32・41-44・89-94 が落ちる形になっていました。最大の番号より上は
取り込みが見ます。

#### 取り込み直すファイルを PLC 側から決める

スクリプトが 13 本あるので、**どれを入れ替えたか覚えておくのは当てに
なりません。**コミットの差分も、取り込み忘れがあると合いません。

KV Studio でニーモニックを書き出して `rake transfer` で照合します。
書き出しにはスクリプトの元のソースがコメントとして入っているので、
生成物と 1 行ずつ比べられます。実際にこれで、名前だけ変えて中身を
入れ直していないスクリプトが 1 本見つかりました。

#### 分けた結果

| スクリプト | 文字数 | 上限比 |
|-----------|-------|-------|
| `vm_09_group5.kvs` | 100,529 | 38% |
| `vm_08_group4.kvs` | 53,813 | 20% |
| `vm_07_group3.kvs` | 32,396 | 12% |
| 他の 10 本 | 686-13,898 | 5% 以下 |

1 本だったころの 232,678 文字 (88%) から、いちばん大きいもので 38% に
なりました。`test_kvs_generator.rb` が**転送する前に**各スクリプトの
上限と、95% を超えていないかを見ます。

#### まだ余地があること

群は命令の**本数**で等分しているため、大きさは偏っています
(100,526 文字と 2,780 文字)。大きさで分け直せばいちばん大きいものは
さらに下がります。**ラダーは境界を知らないので、この変更に追従は
要りません。**

`OP_SSEND` が `OP_SEND` の組み込みメソッドの振り分けを丸ごと持っている
重複 (約 36,000 文字) も残っていますが、上限がスクリプトごとになった今は
急ぎません。共有するには受け手の作り分けに判定が 1 つ増え、よく通る道の
速度を払うことになります。

## mruby バージョン対応

### 現在の対応バージョン

**mruby 3.3.0** (RITE バイナリ形式 `"0300"`)

### mruby 4.0 への移行メモ

mruby 4.0.0 (2026年4月リリース) では以下の非互換変更があり、対応が必要になる。

#### RITE バイナリ形式

- バージョンが `"0300"` → `"0400"` に変更。バイナリ互換性なし
- ヘッダー構造自体は同一 (20バイト)
- セクション識別子 (`IREP`, `END\0` 等) は変更なし
- **影響箇所**: `tools/mrb_parser.rb` のヘッダーバージョンチェック

#### オペコード番号の変更

13個の新オペコードが enum の途中に挿入されたため、挿入位置以降の全オペコード番号がずれる。LOAD 系 (0x00-0x0F付近) は変化なしだが、SEND/RETURN/算術系は番号が変わる。

主な新オペコード:

- `OP_SEND0`, `OP_SSEND0`: 引数なしメソッド呼び出し (高速化)
- `OP_RETSELF`, `OP_RETNIL`, `OP_RETTRUE`, `OP_RETFALSE`: 1バイト特殊 return
- `OP_ADDILV`, `OP_SUBILV`: ローカル変数の加減算融合命令
- `OP_BLKCALL`: ブロック直接呼び出し

リネーム: `OP_LOADT` → `OP_LOADTRUE`, `OP_LOADF` → `OP_LOADFALSE`

**影響箇所**: [tools/opcode_table.rb](../tools/opcode_table.rb) の `MRUBY_OPCODES` のみ。

オペコード番号はここにしか書かれていません。PLC 側 VM・シミュレータ・
逆アセンブラはすべてこの表から導かれるため、番号を直して `rake vm_core` を
実行すれば全体が追従します。

#### OP_ENTER の変更

ビットレイアウトが 23bit → 24bit に拡張 (`n1:m5:o5:r1:m5:k5:d1:b1`)。マイルストーン1では未使用だが、メソッド呼び出し対応時に影響する。

#### 対応方針

1. ~~**KV スクリプトの自動生成**~~ — **実装済み** (第 1 段階)
2. ~~**シミュレータ・disasm も定義表から**~~ — **実装済み** (第 2 段階)。情報源が 1 つになり `test_vm_core_parity.rb` は削除
3. **オペコード定義の分離**: バージョン別の `MRUBY_OPCODES` を用意し、RITE ヘッダーのバージョンで自動切替
4. **ops.h からの自動生成**: mruby ソースの `include/mruby/ops.h` を解析して `MRUBY_OPCODES` を生成する方式も検討
