# アーキテクチャ

Ruby と PLC で意味が食い違う箇所と、その埋め方は
[Ruby と PLC の違い](ruby_and_plc.md) にまとめてあります。
新しい機種に対応する際に実機で確認すべき項目もそちらです。

## VM の仕組み

mruby/c はレジスタベースの VM です。スタックベースではなく、各命令がレジスタ番号を指定して操作します。

### レジスタ構成

- `R[0]` : self (トップレベルでは 0)
- `R[1]` ~ `R[nlocals-1]` : ローカル変数
- `R[nlocals]` ~ `R[nregs-1]` : テンポラリレジスタ (計算用)

### バイトコード形式

mruby 2.0 以降の可変長バイトコードを使用します。各命令は 1 バイトのオペコードと可変長のオペランドで構成されます。

| 形式 | バイト数 | レイアウト |
|------|---------|-----------|
| Z    | 1       | [opcode] |
| B    | 2       | [opcode][a:8] |
| BB   | 3       | [opcode][a:8][b:8] |
| BS   | 4       | [opcode][a:8][b:16] |
| BSS  | 6       | [opcode][a:8][b:16][c:16] |
| BBB  | 4       | [opcode][a:8][b:8][c:8] |
| S    | 3       | [opcode][a:16] |
| W    | 4       | [opcode][a:24] |

16ビット以上のオペランドはビッグエンディアンです。

### RITE バイナリ形式

mrbc が出力する `.mrb` ファイルの構造:

```
+-------------------------------+
| Binary Header (20 bytes)      |  "RITE" + version + size + compiler
+-------------------------------+
| IREP Section Header (12 bytes)|  "IREP" + section_size + rite_version
+-------------------------------+
| IREP Record (top-level)       |  nlocals + nregs + ilen + 命令列 + pool + symbols
+-------------------------------+
| END Section (8 bytes)         |  "END\0" + 0x00000008
+-------------------------------+
```

## PLC メモリ配置

faRuby が使用する領域は**設定ファイルで指定します**。ラダーが使用していない
領域を割り当ててください。重なると双方が壊れます。

```yaml
# faruby.yml (faruby_default.yml の値を上書きする)
memory:
  device: EM        # 使用するデバイス種別
  base: 20000       # faRuby が使用する領域の先頭
  align: 1000       # ブロックサイズをこの倍数に切り上げる
  instances: 2      # 同時実行するインスタンス数
  max_regs: 80
  max_bytecode: 3000
  max_pool: 200
  max_symbols: 100
  max_globals: 100
```

現在の配置はコンソールの `memmap` コマンドで確認できます。

> **重要**: アドレスは生成される `vm_core.kvs` に**定数として焼き込まれます**。
> 設定を変えたら `rake vm_core` で再生成し、KV Studio に取り込んで PLC へ
> 転送し直してください。実行時に切り替わるわけではありません。

### 設定ファイルの構成

| ファイル | 役割 | git |
|---------|------|-----|
| `faruby_default.yml` | 既定値の定義。編集しない | コミット |
| `faruby.yml.example` | 設定が必須の項目の雛形 | コミット |
| `faruby.yml` | 利用者の設定・差分 | 除外 |

`faruby.yml` に無い項目は `faruby_default.yml` の値が使われます。ネストした
キーは個別に解決するため、`memory.base` だけを書いても他のメモリ設定は
既定値のまま残ります。

`rake vm_core` は `faruby.yml` の上書きを反映します。一方テストは
`faruby_default.yml` だけを見るため、`vm_core.kvs` のバイト一致検証
(手編集の検出) は利用者設定に左右されません。

その代わり、`faruby.yml` で配置を上書きして再生成すると、生成物は
その設備専用になりコミット済みの `vm_core.kvs` と一致しなくなります
(バイト一致テストが失敗します)。**恒久的な配置はこのリポジトリの
`faruby_default.yml` に書いてください。** `faruby.yml` での上書きは
一時的な検証用と考えると運用が破綻しません。

### 領域の並び

1インスタンス分のブロックを `instances` 個並べた配置です。

```
base + 0 * instance_size   インスタンス0
base + 1 * instance_size   インスタンス1
```

ブロック内はサイズ設定から詰めて計算します（既定設定での例）。

| 領域 | 範囲 | ワード数 |
|------|------|---------|
| VM状態 | EM20000 - EM20031 | 32 |
| レジスタファイル | EM20032 - EM20351 | 320 (80 × 4) |
| バイトコード | EM20352 - EM23351 | 3000 |
| 定数プール | EM23352 - EM24151 | 800 (200 × 4) |
| デバイステーブル | EM24152 - EM24551 | 400 (100 × 4) |
| 汎用グローバル変数 | EM24552 - EM24951 | 400 (100 × 4) |
| 予備 (端数調整) | EM24952 - EM24999 | 48 |

合計 5000 ワード / インスタンス。

各領域の合計は 4952 ワードですが、`align` (既定 1000) の倍数に切り上げるため
5000 ワードを占有します。開始・終了アドレスが区切りの良い値になり、
複数インスタンスの場合も各ブロックが EM20000 / EM25000 / EM30000 と
丸い境界に載ります。

アドレス配置は [tools/memory_layout.rb](../tools/memory_layout.rb) が計算し、
レイアウトに依存しない定数は [tools/vm_constants.rb](../tools/vm_constants.rb)
にあります。

### 複数インスタンス

`instances` の数だけ独立した VM が動き、それぞれ別の Ruby プログラムを
並行して実行します。既定は 2 です。

ブロック先頭は Z9 に載り、ブロック内の位置はオフセットをインデックス修飾で
足して指します (`EM7:Z9`)。命令本体は 1 つだけで、外側の `FOR ... STEP` が
ブロック先頭を載せ替えながら全インスタンスを巡ります。

```
FOR Z9 = 20000 TO 25000 STEP 5000     ' インスタンスごと
    IF EM1:Z9 = 1 THEN                 ' そのインスタンスが実行中なら
        FOR EM20:Z9 = 1 TO EM5:Z9      ' 命令を回す
            Z1 = EM7:Z9 * 4 + 33 + Z9  ' レジスタアドレス
            ...
```

スクリプトを複製する案もありましたが、660 行が 4 インスタンスで約 2600 行に
なり KV Studio の変換上限に触れる恐れがあります。この方式なら `instances` を
増やしてもコメント数行しか増えません。

停止中のインスタンスは STATUS の判定で空振りするだけなので、数を増やしても
命令実行の負荷は変わりません。`steps_per_cycle` はインスタンスごとの値です。

操作対象はコンソールの `instance` コマンドで切り替えます。`compile` / `load` /
`run` / `status` / `regs` はすべて選択中のインスタンスに対して働きます。

#### KV スクリプトで確認した挙動

この方式が成立するかは実機で確かめてから実装しました。

| 確認事項 | 結果 |
|---------|------|
| Z への算術 (`Z9 = 20000 + EM39100 * 5000`) | 可 |
| 32767 を超える値 | 折り返さない (35000 を確認) |
| 式の項としての Z (`Z1 = 7 * 4 + 33 + Z9`) | 可 |
| インデックス修飾での読み・書き・32ビット | 可 |
| `FOR` のループ変数と上限にインデックス修飾 | 可 |
| 入れ子 `FOR` の `BREAK` | **内側のみ**を抜ける |
| `FOR ... STEP` | 可 |

`BREAK` が内側だけを抜けるため、既存の「停止 = BREAK」がそのまま
「このインスタンスを止めて次へ進む」になります。`STEP` が使えるため、
ブロック先頭と外側ループ変数を Z9 一本で兼ねられます。

#### インデックスレジスタの配分

KV-5000 の Z は 12 本ありますが、**Z11 と Z12 は特別な用途があり使用できません**
(実機で確認済み)。使えるのは Z1-Z10 です。

| レジスタ | 用途 |
|---------|------|
| Z1 | 主オペランド (通常は代入先の R[a]) |
| Z2 | 副オペランド |
| Z3-Z8 | バイトコードフェッチ、デバイステーブル参照 |
| Z9 | 実行中インスタンスのブロック先頭 |
| Z10 | 未使用 (ラダー用に残してある) |

## デバイスと VM 状態

Keyence KV-5000 の EM (拡張データメモリ) を既定で使用します。DM はモジュールで使用されるため避けます。

### VM 状態領域 (ブロック先頭から 32 ワード)

アドレスはブロック先頭 (`memory.base` + インスタンス番号 × ブロックサイズ)
からのオフセットです。既定設定では EM20000-EM20031。

| オフセット | 用途 | 型 | 説明 |
|-----------|------|-----|------|
| +0 | PC | .U | プログラムカウンタ (バイトオフセット) |
| +1 | STATUS | .U | 0=停止, 1=実行中, 2=完了, 3=エラー |
| +2 | ERROR | .U | エラーコード (0=正常) |
| +3-4 | STEP_COUNT | .D | 累計実行命令数 |
| +5 | STEPS_PER_CYCLE | .U | 1スキャンあたり実行命令数 |
| +6 | CURRENT_OPCODE | .U | 最後にデコードしたオペコード |
| +7-9 | OPERANDS | .U | オペランド a, b, c |
| +10 | BYTECODE_LEN | .U | バイトコード長 |
| +11 | NREGS | .U | レジスタ数 |
| +12 | NLOCALS | .U | ローカル変数数 |
| +13 | RESET_REQ | .U | リセット要求 (1=要求, vm_init で処理後 0 に戻る) |
| +14 | NUM_SYMBOLS | .U | シンボル数 |
| +16-17 | TEMP32 | .L | 32ビット合成スクラッチ (下位が先) |
| +18-19 | TEMP32_B | .L | 2つ目の32ビットスクラッチ。除算の切り下げ補正で余りを置く |
| +20 | ループカウンタ | .U | fetch-decode-execute の FOR カウンタ |
| +21-29 | Z 退避 | .U | インデックスレジスタ Z1-Z9 の退避先 (全インスタンス共通) |

#### インデックスレジスタ (Z) の退避

Z はラダーと共有する資源です。faRuby は Z1-Z9 を作業用に書き換えるため、
そのままではラダー側の値を壊します。スクリプトの先頭で退避し末尾で復元する
ことで、faRuby の実行前後で Z の内容が変わらないようにしています。退避は
1 スキャンにつき 1 回だけで、命令ごとの負荷は増えません。

退避・復元はインスタンスループの**外側**で行うため、退避先だけは絶対アドレス
です。全インスタンスで 1 箇所を共有し、置き場所はインスタンス0のブロック内で
足ります。他のインスタンスの同じ位置は未使用のまま残ります (9 ワード)。

`vm_init.kvs` も同じ場所へ退避・復元します
(`vm_core.kvs` とは実行タイミングが排他なので共有できます)。

使用する Z の範囲は `KvsEmitter::USED_Z` が唯一の定義で、退避コードも
テストもここから導かれます。生成コードが宣言外の Z を使っていないことは
テストで検証しています。

実機での確認方法は、退避領域を実行中に読むことです。ここには毎スキャンの
先頭で Z が書き込まれるので、値は「前スキャン末尾の復元が効いたか」を
そのまま映します。復元が抜けていれば、実行位置によって変わる作業値
(レジスタアドレス等) が現れます。

#### KV スクリプトの型に関する注意

##### 使用できる型サフィックス

KV-5000 実機で動作を確認済みのサフィックスです。

| サフィックス | 意味 | 占有 | 検証内容 |
|------------|------|------|---------|
| (なし) | 16ビット符号なし | 1 ワード | 既定。負値を入れると符号なしとして読まれる |
| `.U` | 16ビット符号なし | 1 ワード | `EM60.U:Z7` で確認 |
| `.S` | 16ビット符号付き | 1 ワード | `EM4802.L = EM4800.S` が −500 に符号拡張されることを確認 |
| `.L` | 32ビット符号付き | 2 ワード | `300 * 300 = 90000` が折り返さないことを確認 |
| `.D` | 32ビット符号なし | 2 ワード | `EM4804.D = 4000000000` を確認 |
| `.F` | 単精度実数 (IEEE754) | 2 ワード | `EM4806.F = 1.5` → 0x3FC00000 を確認 |

32ビット / 実数はいずれも**下位ワードが先**です。インデックス修飾付き
(`EM0.S:Z7`, `EM0.F:Z7`) でも同様に動作します。

##### インデックス修飾と型サフィックスの順序

**型サフィックスはデバイス側に付けます。インデックスレジスタの後ろに付けてはいけません。**

```
正: EM0.L:Z1      デバイス EM0 に .L → 32ビットアクセス
誤: EM0:Z1.L      .L がインデックスレジスタ Z1 に結合し、16ビットアクセスになる
```

誤った書き方はコンバートエラーにならず、**静かに 16 ビットアクセスに退化します**。
小さい値では症状が出ないため、`300 * 300` が 24464 (= 90000 − 65536) になるような
桁あふれで初めて発覚します。

インデックスの刻み幅は `.L` でも **1 ワード**で、**下位ワードが先**です
(実機検証: `EM50.L:Z7` に Z7=1 で 0x12345678 を書くと EM51=0x5678, EM52=0x1234)。
したがってレジスタ R[n] の値は `Z1 = n * 4 + レジスタ領域の先頭 + 1` として
`EM0.L:Z1` でアクセスします。

##### 演算の既定の型

**EM はサフィックスを付けないと 16 ビット符号なし**です。そのため
`EM8 = EM8 - 256` のような符号付き演算や `EM8 * 65536` のような桁上がりを伴う
演算は、16 ビットに丸められて壊れます。

負値や 65535 を超える値を組み立てる場合は、下位ワードを EM16・上位ワードを EM17 に
置いてから `EM16.L` として読み出します。これにより符号拡張と桁上がりを KV 側の
32 ビット演算に任せられます。OP_LOADINEG / OP_LOADI16 / OP_LOADI32 が
この方式を使っています。

なお OP_JMP 系の相対ジャンプは PC (EM0) も 16 ビット符号なしのため、
`EM0 = EM0 + EM8` が 16 ビットの剰余演算となり後方ジャンプが正しく成立します
(こちらはスクラッチ不要)。

### 値スロット (共通レイアウト)

レジスタ・定数プール・汎用グローバル変数は共通の **値スロット** 形式で格納します。
1 スロット = 4 ワード です。

| オフセット | 内容 | アクセス |
|-----------|------|---------|
| +0 | 型タグ (TT_*) | `.U` (16ビット) |
| +1 | 値 下位ワード | ┐ `.L` (32ビット符号付き)、+1 が起点 |
| +2 | 値 上位ワード | ┘ |
| +3 | 予備 (将来の拡張用) | — |

現時点で VM が扱うのは整数のみなので、**型タグは書き込まれず TT_EMPTY (0) のまま**です。
Float・String・Array 等を導入する際にレジスタ幅やアドレス計算を変えずに済むよう、
領域だけを先に予約しています。定数プールのみコンパイル時に型が確定するため、
codegen が実際の型タグを書き込みます。

#### 型タグ (TT_*)

`.mrb` バイナリには実行時の型情報が含まれないため、本プロジェクトで定義した番号です
(mruby/c の `mrbc_vtype` に倣った命名)。`TT_EMPTY = 0` はレジスタクリア直後の状態と一致します。

| 定数 | 値 | 真偽 | 状態 |
|------|-----|------|------|
| TT_EMPTY | 0 | 偽 | 未初期化 |
| TT_NIL | 1 | 偽 | 実装済み |
| TT_FALSE | 2 | 偽 | 実装済み |
| TT_TRUE | 3 | 真 | 実装済み |
| TT_INTEGER | 4 | 真 | 実装済み |
| TT_FLOAT | 5 | 真 | 実装済み (IEEE754 単精度) |
| TT_SYMBOL | 6 | 真 | 未実装 (予約) |
| TT_STRING | 7 | 真 | 未実装 (予約) |
| TT_ARRAY | 8 | 真 | 未実装 (予約) |
| TT_HASH | 9 | 真 | 未実装 (予約) |
| TT_OBJECT | 10 | 真 | トップレベルの self にのみ使用 |

**この並び順には意味があります。** Ruby で偽になるのは `nil` と `false` だけなので、
偽の 2 つを真より小さい番号に置いてあります。真偽判定が `タグ > TT_FALSY_MAX` の
1 比較で済みます。並べ替えると生成コードが壊れます (テストが検出します)。

値を持たない型の値ワードは `TT_CANONICAL_VALUE` で決めています。`true` = 1、
`false` と `nil` = 0 です。こうしておくとビットデバイスへの書き込みを値だけで
判定でき、`$MR10 = true` も `$MR10 = 1` も ON になります。

#### 型タグを見る命令

| 命令 | 判定 |
|------|------|
| `OP_JMPIF` / `OP_JMPNOT` | タグで真偽を判定 (`nil` と `false` だけが偽) |
| `OP_JMPNIL` | `TT_NIL` だけに反応 (`false` では飛ばない) |
| `OP_EQ` | 数値は型が違っても値で比べ、数値以外は型と値の両方が一致したときだけ真 |
| 大小比較 | 数値の型で振り分けて値を比べる |
| 算術 | 数値の型で振り分ける。数値以外は値をそのまま計算する |

比較の結果は整数の 1/0 ではなく `TT_TRUE` / `TT_FALSE` です。

Ruby と PLC で意味が食い違う箇所と、その判断の経緯は
[Ruby と PLC の違い](ruby_and_plc.md) にまとめてあります。

#### 実数

値ワードの 2 ワードに IEEE754 単精度のビット列を置きます。整数と同じ場所を
別の型として読むだけなので、スロットの大きさは変わりません。

KV スクリプトは整数と実数の混在を自動で昇格するため (実機で確認済み)、
faRuby がすることは「タグを見て `.F` と `.L` のどちらの書き方を出すか」だけです。
算術と比較の命令は両オペランドの型で 4 通りに分岐します。

```
IF タグa = TT_FLOAT THEN
    IF タグb = TT_FLOAT THEN   dest.F = a.F + b.F
    ELSE                       dest.F = a.F + b.L
    END IF
    dest タグ = TT_FLOAT
ELSE IF タグb = TT_FLOAT THEN  dest.F = a.L + b.F
    dest タグ = TT_FLOAT
ELSE                           dest.L = a.L + b.L
    dest タグ = TT_INTEGER
END IF
```

整数どうしの経路を残すのは、32 ビット整数が単精度の仮数 (24 ビット) に収まらない
ためです。すべて実数にすると大きな整数の精度が落ちます。

シミュレータは演算のたびに単精度へ丸めます。Ruby の `Float` は倍精度なので、
丸めないと実機と結果がずれます。

> **制約**: 0 除算は Ruby に合わせて `Infinity` を返しますが、KV-5000 は
> `Infinity` を保持・転送できても**演算に使うと軽度エラーになります**。
> 詳細は [Infinity は演算に使えない](ruby_and_plc.md#制約infinity-は演算に使えない)。

デバイスへ書き込むときは、書き込み先の幅を見てから必要な形だけを変換します。
両方の形を先に作ると、`.F` へ書くだけの場合でも `Infinity` を整数へ変換して
しまい、それ自体がエラーになります。

#### ビットデバイスの読み取り

ビットデバイス (`$MR10` など) は ON で `true`、OFF で `false` を返します。
ワードデバイス (`$DM100`) は整数のままで、非ゼロ判定は `$DM100 != 0` と書きます。

書き込み側は値で判定します (非0 → ON)。`true` = 1 / `false` = 0 と決めてあるので、
真偽値でも整数でもそのまま通ります。

### ラダーとの領域の住み分け

対象機 (KV-5000) の EM は EM0-EM65535 の 65536 点です。このうち
**EM20000 - EM39999 の 20000 ワードがラダー側で faRuby 用に確保**されています。
1インスタンス 5000 ワードなので最大 4 インスタンスまで置けます。

```
faRuby 用に確保   EM20000 - EM39999
  インスタンス0   EM20000 - EM24999
  インスタンス1   EM25000 - EM29999
  インスタンス2   EM30000 - EM34999
  インスタンス3   EM35000 - EM39999
```

**`memory.base` はラダーのデバイス割り付けで判断してください。**
コンソールの `memmap` で faRuby が占有する範囲を確認できます。

> **EM の内容を読んで判断することはできません。** このデバイスは初期化
> されないため、0 でも未使用とは限らず、非ゼロでも使用中とは限りません。
> 実際、EM65536 以降 (範囲外) を読むと 512 ワード周期で同じ値が返り、
> 範囲内と区別がつかない見え方をします。

### レジスタファイル

VM レジスタ R[n] は値スロット 1 個 (4 ワード) を占めます。

```
R[n] の型タグ = layout.reg_type_addr(n)   # スロット先頭
R[n] の値     = layout.reg_addr(n)        # スロット先頭 + 1 を .L で
```

既定設定では EM20032-EM20351 です。

| VM レジスタ | スロット先頭 | 値アドレス |
|------------|------------|-----------|
| R[0] (self) | EM20032 | EM20033.L |
| R[1] | EM20036 | EM20037.L |
| R[2] | EM20040 | EM20041.L |
| ... | ... | ... |
| R[79] | EM20348 | EM20349.L |

### バイトコード領域

バイトコードは 1 バイト / 1 ワードで格納します (簡易方式)。
既定設定では EM20352-EM23351。

フェッチは Z レジスタ間接アドレッシング (`Z1 = PC + バイトコード先頭` →
`EM0:Z1`) で行い、PC をインクリメントします。

### 定数プール

値スロット形式です。型タグはコンパイル時に確定するため codegen が書き込みます。
既定設定では EM23352-EM24151 (200 エントリ)。

### デバイスマッピングテーブル

グローバル変数と PLC デバイスの対応を格納します。各シンボルにつき 4 ワード:

```
+0 = device_type   (0-9)
+1 = device_address
+2 = access_type   (ワードデバイスのアクセス幅)
+3 = 予備
```

既定設定では EM24152-EM24551 (100 シンボル)。

| デバイスタイプ | ID | 種別 | アクセス | 用途 |
|-------------|-----|------|---------|------|
| EM | 0 | ワード | .L (32ビット) | 拡張データメモリ |
| DM | 1 | ワード | .L (32ビット) | データメモリ |
| ZF | 2 | ワード | .L (32ビット) | ファイルレジスタ |
| R | 3 | ビット | 個別ビット (0/1) | 内部リレー |
| MR | 4 | ビット | 個別ビット (0/1) | 補助リレー |
| B | 5 | ビット | 個別ビット (0/1) | リンクリレー |
| L | 6 | ビット | 個別ビット (0/1) | ラッチリレー |
| ~~CR~~ | ~~7~~ | ~~ビット~~ | — | コントロールリレー (インデックス扱い不可、非対応) |
| T | 8 | ビット | 個別ビット (0/1) | タイマ |
| C | 9 | ビット | 個別ビット (0/1) | カウンタ |

### ワードデバイスのアクセス幅

**ワードデバイス** (EM, DM, ZF) はアクセス幅をグローバル変数名のサフィックスで指定します。
**既定 (サフィックス無し) は 16 ビット符号付き = 1 ワード**で、PLC の慣習
(DM100 は 1 ワード) と一致します。

| Ruby 記法 | KV サフィックス | access_type | 意味 | 占有 |
|----------|--------------|-------------|------|------|
| `$DM100` | `.S` | 0 | 16ビット符号付き (既定) | 1 ワード |
| `$DM100S` | `.S` | 0 | 同上 (明示) | 1 ワード |
| `$DM100U` | `.U` | 1 | 16ビット符号なし | 1 ワード |
| `$DM100L` | `.L` | 2 | 32ビット符号付き | 2 ワード |
| `$DM100D` | `.D` | 3 | 32ビット符号なし | 2 ワード |
| `$DM100F` | `.F` | 4 | 単精度実数 | 2 ワード |

サフィックスが付くのはワードデバイス (EM, DM, ZF) のみです。ビットデバイスには
幅の概念が無いため付けられません。これにより解析上の曖昧さも回避されます。

- `$L100` はラッチリレー L の 100 番であり、`$DM100L` の `L` サフィックスとは競合しません
  (前置詞が先にマッチするため)
- `$B1F` はリンクリレー B の 16 進アドレス 1F であり、末尾の `F` は実数サフィックスと
  解釈されません (B はビットデバイスなのでサフィックス対象外)

**アドレス衝突は利用者の責任です。** `$DM100L` は DM100 と DM101 の 2 ワードを占有する
ため、同じプログラム内で `$DM101` を使うと値が壊れます。

**実数 (`F`) は型が変換されます。** `$DM100F` を読むとレジスタは `TT_FLOAT` になり、
書き込むときは整数レジスタなら実数へ、実数レジスタを `.S` 等へ書くなら 0 方向へ
切り捨てて変換します。変換はアクセス幅ごとの分岐に入る前に 1 度だけ行い、
分岐の中でレジスタの型を見なくて済むようにしています。

**汎用グローバル変数** (`$foo` 等) は Ruby の値を保持するため常に 32 ビット符号付きです。

**ビットデバイス** (R, MR, B, L, T, C) は個別ビットとしてアクセスします。書き込み時は非0→ON(1)、0→OFF(0) に変換されます。ビットデバイスは `.L` や `.U` での間接アクセスが 16 飛びになるため、個別ビットとして直接アクセスする必要があります。

**注意**: CR (コントロールリレー) はインデックス修飾による間接アクセスができないため非対応です。

Ruby のグローバル変数名から PLC デバイスを特定する命名規則:

| Ruby コード | シンボル | device_type | アドレス |
|------------|---------|-------------|---------|
| `$DM100` | `"$DM100"` | 1 (DM) | 100 |
| `$MR10` | `"$MR10"` | 4 (MR) | 10 |
| `$ZF500` | `"$ZF500"` | 2 (ZF) | 500 |
| `$foo` | `"$foo"` | 0 (EM) | 6000+ (自動割当) |

デバイス名にマッチしないグローバル変数 (`$foo` 等) は汎用グローバル変数領域に自動割当されます。

### 汎用グローバル変数領域

デバイス名にマッチしないグローバル変数の格納先です。値スロット (4 ワード/変数) が
出現順に割り当てられます。デバイス名付きシンボル (`$DM100` 等) はこの領域を消費しません。

```
n 番目のスロット先頭 = EM(6000 + n * 4)
n 番目の値           = EM(6000 + n * 4 + 1).L
```

**デバイスマッピングテーブルには「値ワード」のアドレス (スロット先頭 + 1) を格納します。**
これにより GETGV/SETGV の EM デバイス経路をスロット非対応のまま流用できます。
型タグは値ワードの 1 つ前 (スロット先頭) にあります。

## KV スクリプト VM 実行モデル

### fetch-decode-execute ループ

```
FOR EM20 = 1 TO EM5 (STEPS_PER_CYCLE)
    1. オペコードフェッチ: Z1 = PC + 1000; EM0:Z1 を読み、PC++
    2. デコード: IF/ELSE IF チェーンでオペコード判定
    3. オペランドフェッチ: 形式に応じて追加バイトを読む
    4. 実行: レジスタ操作
    5. STOP/RETURN で BREAK
NEXT
```

### Z レジスタの使い方

KV スクリプトでは Z1-Z12 を間接アドレッシングに使用します。

- Z1 : バイトコードアドレス計算 (PC + 1000) / レジスタ値アドレス計算 (a * 4 + 101)
- Z2 : 第2オペランドのレジスタ・プール値アドレス計算 (b * 4 + 101 / b * 4 + 4001)
- Z3-Z6 : テンポラリ (16ビットオペランド組み立て、デバイステーブル参照)

レジスタ値のアドレスは `* 4 + 101` と、**スロット先頭ではなく値ワードを直接指す**形で
計算します (`+ 100` ではなく `+ 101`)。型タグを参照するようになった時点で
`Z1 - 1` またはスロット先頭を別途計算します。

### スキャンサイクルとの関係

- FOR ループは 1 スキャン内で完了します
- STEPS_PER_CYCLE が大きすぎるとスキャンタイムが延びます
- 推奨初期値: 50

オペランド `b` は IREP シンボルテーブルのインデックス。デバイスマッピングテーブルを参照し、対応する PLC デバイスにアクセスする。ワードデバイスは `access_type` に応じて `.S` / `.U` / `.L` / `.D` を選択する (既定は `.S`)。

## オペコード定義表と 2 つのバックエンド

命令の定義は [tools/opcode_table.rb](../tools/opcode_table.rb) に一本化されています。
ここから PLC 側 VM・シミュレータ・逆アセンブラのすべてが導かれます。

```
              tools/opcode_table.rb   ← 命令の定義 (唯一の情報源)
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   KvsEmitter       SimVm       MRUBY_OPCODES
  (文字列を組立)   (実際に実行)    (名前と形式)
        │              │              │
        ▼              ▼              ▼
  vm_core.kvs   kv_vm_simulator    disasm.rb
```

| ファイル | 役割 |
|---------|------|
| [tools/opcode_table.rb](../tools/opcode_table.rb) | 命令定義 (唯一の情報源) |
| [tools/kvs_generator.rb](../tools/kvs_generator.rb) | KV スクリプトを組み立てるバックエンド |
| [simulator/sim_vm.rb](../simulator/sim_vm.rb) | EM メモリ上で実行するバックエンド |
| `plc/keyence/vm_core.kvs` | 生成物 (コミット対象) |
| `plc/keyence/vm_init.kvs` | 生成物 (コミット対象) — リセット処理 |

**`plc/keyence/*.kvs` は生成物です。直接編集しないでください。**
命令を追加・変更する場合は `opcode_table.rb` を直してから `rake vm_core` で再生成します。

生成物をコミットするのは、KV Studio に取り込む実体が必要なことと、
差分レビューができることの 2 点が理由です。手で編集していないことは
[test/test_kvs_generator.rb](../test/test_kvs_generator.rb) が検証します
(生成結果とコミット済みファイルのバイト一致)。

### 同じ定義を 2 通りに解釈する

命令定義の本体は「バックエンド」を 1 つ受け取ります。

```ruby
OpcodeDef.new(0x3C, "R[a] = R[a] + R[a+1]") do |vm|
  vm.set_reg(:a, vm.binop(:add, vm.reg(:a), vm.reg_next(:a)))
end
```

- `KvsEmitter` に渡すと、`vm.reg(:a)` は文字列 `"EM0.L:Z1"` を返し、
  副作用としてアドレス計算の行を出力します
- `SimVm` に渡すと、`vm.reg(:a)` は EM メモリから読んだ整数を返します

`vm.if_(cond) { ... }` も同様で、KV 側は常にブロックを実行して `IF...END IF` を
出力し、シミュレータ側は条件が真のときだけブロックを実行します。

この仕組みにより、**片方にだけ命令があるという食い違いが構造的に起きません**。
以前は `OP_LOADNIL` が `vm_core.kvs` にだけ無く、実機で `while` を動かすまで
気づけませんでした。両者を突き合わせる `test_vm_core_parity.rb` も不要になり、
[test/test_opcode_table.rb](../test/test_opcode_table.rb) が
「全命令が両バックエンドで実行できること」を直接検証します。

命令本体には **PLC 機種固有の名前を書きません**。デバイス名・インデックス
レジスタ・型サフィックスはバックエンドの管轄です。この境界は
`test_opcode_table_has_no_device_names` が守ります。

### なぜ生成にしたか

手書き時代は同じイディオムが大量に散らばっており、修正が全箇所に及んでいました。

| 変更 | 影響箇所 |
|------|---------|
| 型サフィックスの位置 (`EM0:Z1.L` → `EM0.L:Z1`) | 91 箇所 |
| 値スロットのストライド (2 → 4 ワード) | 45 箇所 |
| オペランドフェッチの定型 | 58 箇所 (約 174 行) |

生成器ではこれらが `KvsEmitter` の 1 メソッドに集約されているため、
同種の変更は 1 箇所で済みます。`OP_LOADNIL` がシミュレータにだけあって
`vm_core.kvs` に無い、といった実装漏れも定義表に無ければ起きません。

### 命令形式とオペランドの対応

オペランドのフェッチコードは命令形式から自動生成されます。
オペランドは順に **EM7 (a) / EM8 (b) / EM9 (c)** へ格納されます。

| 形式 | オペランド |
|------|-----------|
| Z | なし |
| B | a (1バイト) |
| BB | a, b (各1バイト) |
| BBB | a, b, c (各1バイト) |
| S | a (2バイト) |
| BS | a (1バイト), b (2バイト) |
| BSS | a (1バイト), b, c (各2バイト) |

> **注**: 生成方式への移行時に `OP_JMP` (形式 S) のオペランド格納先が
> EM8 → EM7 に変わりました。オペランド `a` は EM7、という規則に揃えたためです。
> 動作は同一で、`status` コマンドのデバッグ表示のみが変わります。

### 未解決: KV Studio の変換上限

スクリプトが大きくなると KV Studio で変換できなくなる可能性があります。
現状 631 行で問題は出ていませんが、命令追加 (特に Float 対応で
GETGV/SETGV が 30 分岐になる場合や `OP_SEND` の追加) で肥大化します。

`KvsGenerator#generate` は `{ ファイル名 => 内容 }` を返す形にしてあり、
分割が必要になった際に複数ファイルを返せます。ただし fetch-decode-execute
ループを跨いで分割する方法は未検討です (FOR ループ内に全命令の分岐が
必要なため、単純にファイルを割ることはできません)。**実際に変換エラーが
出てから検討する**方針です。

## mruby バージョン対応

### 現在の対応バージョン

**mruby 3.3.0** (RITE バイナリ形式 `"0300"`)

### mruby 4.0 への移行メモ

mruby 4.0.0 (2026年4月リリース) では以下の非互換変更があり、対応が必要になる。

#### RITE バイナリ形式

- バージョンが `"0300"` → `"0400"` に変更。バイナリ互換性なし
- ヘッダー構造自体は同一 (20バイト)
- セクション識別子 (`IREP`, `END\0` 等) は変更なし
- **影響箇所**: `tools/mrb_parser.rb` のヘッダーバージョンチェック

#### オペコード番号の変更

13個の新オペコードが enum の途中に挿入されたため、挿入位置以降の全オペコード番号がずれる。LOAD 系 (0x00-0x0F付近) は変化なしだが、SEND/RETURN/算術系は番号が変わる。

主な新オペコード:

- `OP_SEND0`, `OP_SSEND0`: 引数なしメソッド呼び出し (高速化)
- `OP_RETSELF`, `OP_RETNIL`, `OP_RETTRUE`, `OP_RETFALSE`: 1バイト特殊 return
- `OP_ADDILV`, `OP_SUBILV`: ローカル変数の加減算融合命令
- `OP_BLKCALL`: ブロック直接呼び出し

リネーム: `OP_LOADT` → `OP_LOADTRUE`, `OP_LOADF` → `OP_LOADFALSE`

**影響箇所**: [tools/opcode_table.rb](../tools/opcode_table.rb) の `MRUBY_OPCODES` のみ。

オペコード番号はここにしか書かれていません。PLC 側 VM・シミュレータ・
逆アセンブラはすべてこの表から導かれるため、番号を直して `rake vm_core` を
実行すれば全体が追従します。

#### OP_ENTER の変更

ビットレイアウトが 23bit → 24bit に拡張 (`n1:m5:o5:r1:m5:k5:d1:b1`)。マイルストーン1では未使用だが、メソッド呼び出し対応時に影響する。

#### 対応方針

1. ~~**vm_core.kvs の自動生成**~~ — **実装済み** (第 1 段階)
2. ~~**シミュレータ・disasm も定義表から**~~ — **実装済み** (第 2 段階)。情報源が 1 つになり `test_vm_core_parity.rb` は削除
3. **オペコード定義の分離**: バージョン別の `MRUBY_OPCODES` を用意し、RITE ヘッダーのバージョンで自動切替
4. **ops.h からの自動生成**: mruby ソースの `include/mruby/ops.h` を解析して `MRUBY_OPCODES` を生成する方式も検討
