# ブロックの計画

ロードマップ [項目 4](roadmap.md) の設計メモです。まだ実装していません。

## 何が必要か

`times` / `upto` / `loop` にブロックを渡せるようにします。

```ruby
sum = 0
3.times do |i|
  sum = sum + i
end
$DM100 = sum
```

## 逆アセンブルで分かったこと

mrbc 3.3.0 の出力です。

```
[top] nlocals=2 nregs=4 syms=["times", "$DM100"] children=1
  OP_LOADI_0 [1]          sum = 0
  OP_LOADI_3 [2]          レシーバ 3
  OP_BLOCK   [3, 0]       R[3] = 子 irep 0 から作ったブロック
  OP_SENDB   [2, 0, 0]    R[2].times { R[3] }
  ...
  [top.0] nlocals=3 nregs=6 syms=[] children=0
    OP_ENTER     [262144]     引数 1 個 (|i|)
    OP_GETUPVAR  [3, 1, 0]    外側の R[1] (= sum) を読む
    OP_MOVE      [4, 1]
    OP_ADD       [3]
    OP_SETUPVAR  [3, 1, 0]    外側の R[1] へ書く
    OP_RETURN    [3]
```

設計に効く発見が 5 つあります。

**1. `3.times` は「ブロックを呼ぶ組み込みメソッド」です。** `OP_SENDB` は
呼び出しの仕組みでしかなく、繰り返すのは `Integer#times` の側です。mruby では
C で書かれています。**`OP_BLOCK` と `OP_SENDB` を実装しただけでは何も回りません。**
`times` / `upto` / `loop` を VM 側の反復として実装する必要があります。

**2. VM は再帰できないため、反復をフレームの状態として持つ必要があります。**
生成コードは fetch-execute のループ 1 本です。「ブロックを 3 回呼ぶ」を素直に
書く場所がありません。反復用のフレームに「今何回目か」「上限」を持たせ、
ブロックの `OP_RETURN` で次の回に入り直す形になります。

**3. 入れ子のブロックは 1 段より上を見ます。**

```
2.times do |i|
  2.times do |j|
    s = s + 1        → OP_GETUPVAR [3, 1, 1]   ← 第3オペランドが階層
  end
end
```

`OP_GETUPVAR [a, b, c]` の `c` は遡る段数です。1 段だけの対応では、この
**よくある形が動きません。** フレームに「定義元のフレーム番号」を持たせ、
段数ぶん辿る必要があります。

**4. 引数の数を検査してはいけません。** 引数を書かないブロックは
`OP_ENTER [0]` ですが、`times` は 1 個渡します。Ruby はブロックの引数の数に
寛容で、足りなければ `nil`、余れば捨てます。メソッドの `OP_ENTER` は数を
突き合わせるので、**ブロックかどうかで振る舞いを分ける**必要があります。

**5. `break` は `OP_BREAK` (0x3A) です。** 反復を途中で止めるので、ブロックから
戻るだけでなく**反復そのものを終わらせ**、`break` の値を呼び出し全体の値に
します。`loop` は `break` でしか終わらないため、`loop` を入れるなら必須です。

`loop` は `OP_SSENDB` (self への呼び出し) で、`3.times` の `OP_SENDB` とは
別命令です。

## 決めること

irep の並べ方と領域の分け合い方は [irep の構造](architecture.md#irep-の構造)
に図があります。ブロックの本体も `def` と同じく子 irep になります。

### ブロックの値

`OP_BLOCK` が作る値は、本体の irep だけでは足りません。外側の変数を読むために
**定義元のフレーム**も要ります。値スロットは 2 ワードあるので、`TT_PROC` の
下位に irep 番号、上位に定義元のフレーム番号を入れます (デバイス参照と同じ手)。

### フレームの拡張

現在の呼び出しフレームは 4 ワードです。ブロックのために増やす必要があります。

| ワード | 内容 | 現在 |
|-------|------|------|
| 戻り先 PC | | あり |
| 戻り先 irep | | あり |
| 戻り先レジスタ窓 | 呼び出し元の窓 | あり |
| 自分のレジスタ窓 | `OP_GETUPVAR` の行き先 | **追加** |
| 定義元フレーム番号 | 階層を辿る鎖 | **追加** |
| 種別 | 通常の呼び出しか反復か | **追加** |
| 反復の現在値 / 上限 | `times` の状態 | **追加** (2 ワード) |
| ブロックの irep / 定義元 | 呼び直すため | **追加** (2 ワード) |

**4 ワードから 12 ワード程度になります。** `max_frames` を 16 のままにしても
64 → 192 ワードで、128 ワード増えます。

### メモリ — 解決済み

メソッド呼び出しまで入れた時点で、1 インスタンス 5000 ワードの端数は
**8 ワード**しか残っていませんでした。128 ワード増やす余地はありません。

そこで**先に固定領域を FM へ移しました** ([アーキテクチャ](architecture.md#fm-と-zf))。
実行中に変わらない 4128 ワードを移した結果、EM 側は 864 ワード
(1 インスタンス 1000 ワード) になり、端数が 136 ワードできました。
フレームを 4 → 12 ワードに増やしても収まります。

### 反復の実装

`times` を例にすると、`OP_SENDB` は次のことをします。

1. 反復フレームを積む (戻り先・現在値 0・上限 = レシーバ・ブロックの irep と定義元)
2. レジスタ窓を `R[a]` までずらし、`R[1]` に 0 を置く
3. ブロックの irep に移り、PC = 0

ブロックの `OP_RETURN` は、積まれているフレームが反復なら:

- 現在値 + 1 が上限未満 → `R[1]` を更新して PC = 0 に戻す (もう一周)
- 上限に達した → フレームを外し、レシーバを値にして呼び出し元へ

`OP_BREAK` は上限に関係なくフレームを外し、`break` の値を返します。

`upto` は上限と初期値が変わるだけ、`loop` は上限が無い (`break` 待ち) だけで、
同じ枠に収まります。

## 進め方

1. **固定領域を FM へ** — バイトコード・定数プール・シンボル表・IREP テーブルを
   FM に移す。動作は変わらないので、既存のテストがすべて通れば正しい —
   **実装済み**
2. **フレームの拡張と upvar** — `OP_BLOCK` / `OP_GETUPVAR` / `OP_SETUPVAR` —
   **実装済み**
3. **反復** — `times` / `upto` / `loop` と `OP_SENDB` / `OP_SSENDB`
4. **`break`** — `OP_BREAK`。`loop` はこれが無いと終わらない

1 は他と独立していて、先に済ませるほど後が楽です。2 以降は分けて検証しにくい
かもしれません (メソッドの段階 2・3 と同じ事情) が、まず 1 を確実に終えます。

### 段階 1 でしたこと

- 領域を「実行中に変わる (EM)」と「変わらない (FM)」に分けた
- 固定領域の位置は VM 状態に **FM の絶対アドレス**で持つ。FM は 0-32767 で
  16 ビットに収まるため Z に載り、インスタンスごとの先頭を足す必要がない。
  結果として命令フェッチの項が 1 つ減った
- スクリプトの先頭で `FRSET(3)`、末尾で `FRSET(0)`
- ホストからは ZF の絶対アドレス (98304 + FM アドレス) で転送する。
  `memory_image` (EM) と `fixed_image` (FM) の 2 本立てになった
- EM は 1 インスタンス 5000 → 1000 ワードになった

実機で確認済みです。

- **バンク 3 の FM0 は ZF98304** でした。ホストが ZF98304 以降に書いた内容を
  スクリプトが FM0 以降で読めています (仮定でしたが正しかった)
- メソッド呼び出しの 19 件が変わらず通る
- 実行速度は 33,984 命令/秒、スキャン周期 1.47 ms。移行前 (34,191 命令/秒、
  1.46 ms) からほぼ変わりません。**バイトコードを FM から読むようにしても
  速度は落ちませんでした。**

### 段階 2 でしたこと

- フレームを 4 → 10 ワードに拡張。自分のレジスタ窓・定義元フレーム・種別・
  反復の現在値と上限 (32 ビット) を追加した
- `OP_BLOCK` はブロックの値に **本体の irep と定義元のフレーム**を詰める。
  値スロットの 2 ワードを使う (デバイス参照と同じ手)
- `OP_GETUPVAR` / `OP_SETUPVAR` は定義元の鎖を段数ぶん辿る。トップレベルは
  `FRAME_NONE` で表し、レジスタ領域の先頭に解決する
- レジスタ窓をずらす処理を `push_frame` に寄せた。フレームに自分の窓を
  記録する必要ができたため

**`FOR` の中で `BREAK` すると `FOR` を抜けるだけ**で命令ループから出られません。
鎖を辿る途中のエラーは印を立てて `FOR` の外で判定します。テストで固定しました。

反復がまだ無いため、Ruby のプログラムからは到達できません。バイトコードを
直接置いた単体テストで確かめています。

## 先送りする論点

**`each` と Array**。`each` は Array が要るため、ロードマップ項目 5・6 の後です。
`times` / `upto` / `loop` は Integer だけで動くので先に入れられます。

**`next`**。ブロックの中の `next` は `OP_RETURN` になるはずですが未確認です。
反復フレームの扱いがそのまま使えるか、実装時に逆アセンブルで確かめます。

**Proc オブジェクト**。`&blk` で受け取る、`Proc.new`、`yield` は範囲外です。
`yield` はメソッドに渡されたブロックを呼ぶ命令 (`OP_BLKPUSH`) が要ります。
