# 確認の進め方

**シミュレータでは再現できない不具合が何度も出ています。** 16 ビット符号
なしの一周、`INC` が 32 ビットかどうか、機種ごとの実数→整数の丸め方、
絶対アドレスと添字の食い違い — どれも実機で初めて壊れました。**VM を直したら
実機で通してから完了にします。**

## PC 上のテスト

```bash
rake test         # 両方
rake test:plc     # キーエンス・三菱と、共通のところ
rake test:i8080   # i8080 バックエンド
```

生成結果の突き合わせ、コード生成、シミュレータでの実行が入ります。生成物が
手で編集されていないかもここで見ます。

**PLC と i8080 で分けてあります。要るものが違うためです。** PLC 側は mrbc
だけで動きますが、i8080 側は r8080 エミュレータと、asm80 でアセンブルした
`vm_main.hex` が要ります。

| | 要るもの | 無いとき |
|---|---|---|
| `test:plc` | mrbc | mrbc を使うものだけ飛ぶ |
| `test:i8080` | mrbc / r8080 / vm_main.hex | **飛ばす** (落とさない) |

r8080 は隣のリポジトリ (`../r8080/lib`) を見ます。別の場所なら
`R8080_PATH` で指せます。**無い環境では i8080 のテストが全部飛び、
`rake test` は通ります。**

```
git clone https://github.com/katsuyoshi/r8080.git ../r8080
```

### 走り終わったら待たない

**`rake test:i8080` は 444 秒から 12 秒になりました。** 速くなった分はすべて
**走り終わった後の空ループ**です。

VM は STATUS が RUNNING でなくなると `vm_loop` から `vm_halt` へ抜けますが、
そこは **LED の表示を 3 秒見せるための待ち**で、`8080` 命令にして
**1,048,576 回** (4 × 65536 × 4 命令) 回ってからモニタへ飛びます。実機では
要る待ちですが、エミュレータでは丸損です。**1 本 106 万命令のうち 98%** が
ここでした (PC の分布を取って確認)。

`I8080Board#run` が STATUS を 64 命令ごとに見て、RUNNING でなくなったら
そこで止めます。**`vm_halt` は VM 状態を 1 ワードも書かない**ので結果は
変わりません (147 本・830 assertions が同じまま)。

**r8080 のクロック設定では速くなりません。** 調整は `I8080#run` の中に
あり、`sleep` するのは**実行が目標クロックより速いとき**だけです。faRuby の
board は `execute` を直に呼ぶのでそこを通らず、1 MHz と 1 GHz で測っても
差は出ませんでした (2505 ms 対 2484 ms)。そもそも実測は **42.6 万命令/秒**
なので、1 MHz でも眠る余地がありません。

### 飛ばす設計の代償 — skip の数を見ること

**落とさずに飛ばすので、取りこぼしも正常な skip と同じ顔をします。**
`test_i8080_flip_flop.rb` の 23 本が「mrbc not found」で飛び続けていました
が、mrbc は入っていて、**そのファイルの探索先に Windows の置き場を入れ忘れて
いただけ**でした。他のテストは同じ mrbc で走っていたので、失敗の数を見ている
限り手がかりがありません。

**`rake test:i8080` の skip が 0 でないときは、何が飛んだのかまで見てください**
(`--verbose`)。要るものが本当に無いのか、探すところを間違えているのかは、
数字だけでは区別が付きません。

**分け方はファイル名です。** `test/test_i8080_*.rb` が i8080 側で、残りが
PLC 側。i8080 を読み込むのに別の名前を付けると PLC 側に混ざって
r8080 が無い環境で落ちるので、`test_rake_tasks.rb` がそれを見ています。

## 実機での確認

```bash
rake hw
```

**[test/ruby_programs/](../test/ruby_programs/) を順に PLC で走らせ、見出しに
書いた期待値と突き合わせます。** 相手は `connections.current` の PLC で、
`rake hw CONNECTION=KV_X500` のように選べます。1 本だけなら
`rake hw ONLY=test_16` です。

**期待値はプログラムの見出しに書きます。** 別に表を持つと、片方だけ直して
気づかない形になります。

```ruby
# 対象機種: KV-5000        省略するとどの機種でも走らせる
#
# 期待値:
#   $DM520F = 3.0    実数の加算 2.5 + 0.5
#   $DM526  = 3      実数をワードデバイスへ書くと0方向へ切り捨て
```

**機種で触れるデバイスが違うので、走らせる相手も分かれます。** タイマ・
カウンタは KV-5000 だけ、`_melsec` の付いたものは三菱 2 機種だけです。

**`*.devices.rb` はプログラムではありません。** デバイスの割り付け表で、
`# devices:` 行で指したプログラムの読み方だけを変えます。一覧から外して
あるので、走らせる本数には数えません。期待値にも割り付けた名前を書けます。

## 手で確かめるもの

### 電源を入れ直したときの再始動

**`rake hw` では自動化できません。** 電源を切る操作が要るためです。

使うのは [test_39_restart.rb](../test/ruby_programs/test_39_restart.rb) です。
`$DM1030` に走り出した回数を数えて `loop` に入り、**終わりません**。DM は
電源を切っても残るので、入れ直して 1 増えていれば先頭を通ったことになります。
終わらないので STATUS は実行中のままで、「実行中だった」状態を作れます。

```
faruby> compile test/ruby_programs/test_39_restart.rb
faruby> dev DM1030 0     # 走り出した回数を 0 に戻す
faruby> load
faruby> run
faruby> dev DM1030       # 1 になる
```

ここで PLC の電源を切り、入れ直します。

| 見るもの | 期待 |
|---------|------|
| `status` | **実行中**。停止になっていない |
| `dev DM1030` | **2**。先頭を通った |
| `dev DM1031` | 2。ループが回っている |
| ERROR | 0 |

**止めてから切った場合も確かめます。** `stop` してから電源を入れ直し、
`status` が停止のまま、`DM1030` が増えないこと。実行中だったものだけ走り直す
形なので、この 2 つで判断そのものを確かめられます。

**4 機種で確認済みです** (実行中 → 1 から 2、停止 → 2 のまま)。
生成する言語 (KV スクリプト / ST) と起動の接点 (CR2008 / SM402) の組み合わせを
すべて通っています。

**ただし三菱は可変領域が保持されている必要があります。** `STATUS` も
メソッド表も `$FARUBY_TICKS` も可変領域 (D) にあり、**三菱の D は既定で
残りません。** 保持されていない Q で電源を入れ直したところ、`STATUS` が 0、
`NUM_IREPS` が 0、メソッド表と変数が全部 0、`$FARUBY_TICKS` は電源投入からの
127 秒でした (固定領域 ZR のバイトコードは残っていました)。

**走り直す判断が `STATUS = 1` なので、消えると成立しようがありません。**
この確認をするときは、先に可変領域が保持の対象になっているかを見てください。
キーエンスの EM は既定で残ります。

**`$FARUBY_TICKS` は 0 に戻りません。** EM / D に残る値から続けて数えます
(同じ確認で分かりました)。止めている間も進みます。

## 数えている値

| 機種 | 一致した値 | 走った本数 | クラス |
|------|----------|----------|--------|
| KV-5000 | **268** | **29** | 入り |
| KV-X500 | **266** | **28** | 入り |
| MELSEC Q | **104** | **15** | 前 |
| MELSEC iQ-R | 258 | 27 | 前 |

KV-5000 が 2 つ多いのはタイマ・カウンタのぶんです。ほかの 3 機種では
そのデバイスを触れません (VM の違いではありません)。

**Q が少ないのは文字列・配列・ハッシュを載せていないからです** (doc/melsec.md)。
258 → 104 で、12 本が飛びます。**Q とキーエンス機では「実機で証明済み」
の範囲が違います。**

「前」は `test_44_classes` を足す前に測った数です。どの機種でも走るので、
通し直せば 8 増えます。足したのは、**クラスを実機で一度も通していなかった**
からです — そのせいで下に書いた不具合を `rake hw` が見逃しました。

飛ばす理由は 3 つに分かれ、`rake hw` が区別して出します。

| 理由 | 本数 |
|------|-----|
| 機能が無効 (Q だけ) | 12 |
| ほかの機種専用 | 33 |
| 期待値を書いていない | 15 |

**4 機種は同時に起動できないので、機種を入れ替えながら通します。** 繋がらない
ときは PLC ではなく PC 側の経路を先に見てください (ping と素の TCP 接続は
この PLC では当てにならず、通っている相手にも失敗を返します)。

**PLC の中身を変えていないなら、メーカー 1 機種ずつで足ります。** 生成物が
同じなら機種の違いは出ないので、違いが出るとすればメーカー間 (デバイスの
名前と番号の数え方) だけです。

**取り込んでも変換・書き込みを忘れると古いコードが走り続けます。** `@` を
入れたとき三菱の 2 機種でそうなり、未知のオペコード (ERROR=26) で止まり
ました。**新しい本体なら 26 は 22 に書き替わるので、ERROR=26 が出た時点で
古いコードだと分かります。** 生成物を疑う前にここを確かめてください。

**古いコードに見える症状が、生成コードの不具合だったことがあります。**
クラスを入れたとき KV-5000 だけ `a.value` が `main` の 0 行目を引きました。
`OP_DEF` はクラスの行に正しく書けており、プールの見出しにもクラス番号が
入っていたので、取り込み漏れだと考えました。**`rake transfer` で 13 本すべて
一致していたので、それが誤りだと分かりました。**

原因は、**レシーバのアドレスを Z に載せる行が組み込みメソッドの枝の中に
あったこと**です。ユーザー定義の枝はその行を通らないため、Z に残っていた
バイトコードのアドレスをタグとして読み、クラスでもオブジェクトでもないと
見えて 0 行目に落ちていました。三菱は添字で直に指すので出ません —
**KV だけが落ちる不具合がまた 1 つ**です。

同じ間違いは生成の時点で止まります。アドレスを載せた行がどの枝の中だったかを
覚え、別の枝から使おうとしたら `GeneratorError` にします (tools/devices.rb)。

**実機で見分けるには、同じ名前のメソッドを `main` とクラスの両方に置きます。**
0 行目に落ちても、名前が重なっていなければ「まだ def が実行されていない」
(ERROR=3) で止まりますが、**重なっていれば黙って `main` の方を呼びます。**
`test_44_classes.rb` がそれをしています。

**どのファイルが古いかは `rake transfer`** で分かります (KV Studio で
ニーモニックを書き出してから)。コミットの差分から数えると、どこまで
取り込んだか覚えていない場合に合いません。

**VM を直したときは話が別で、4 機種とも通します。** 生成する言語 (KV スクリプト /
ST) と機種ごとの違いがそこで出ます。`loop` では KV-5000 だけが落ちる不具合
(前処理ごとに Z に覚えたアドレスを捨てていなかった) と、MELSEC だけが落ちる不具合
(`OP_SSENDB` が STAGES から漏れていた) が別々に出ました。

`test_37_ticks` の 5 つは**時間が進んでいること**を見るもので、値そのものは
実行のたびに変わります。経った時間が 0 より大きいか、10 の倍数か、その間に
クロックパルスが両方の状態を取ったか、という形に直して数えています。
