# 確認の進め方

**シミュレータでは再現できない不具合が何度も出ています。** 16 ビット符号
なしの回り込み、`INC` が 32 ビットかどうか、機種ごとの実数→整数の丸め方、
絶対アドレスと添字の食い違い — どれも実機で初めて壊れました。**VM を直したら
実機で通してから完了にします。**

## PC 上のテスト

```bash
rake test
```

生成結果の突き合わせ、コード生成、シミュレータでの実行が入ります。生成物が
手で編集されていないかもここで見ます。

## 実機での確認

```bash
rake hw
```

**[test/ruby_programs/](../test/ruby_programs/) を順に PLC で走らせ、見出しに
書いた期待値と突き合わせます。** 相手は `connections.current` の PLC で、
`rake hw CONNECTION=KV_X500` のように選べます。1 本だけなら
`rake hw ONLY=test_16` です。

**期待値はプログラムの見出しに書きます。** 別に表を持つと、片方だけ直して
気づかない形になります。

```ruby
# 対象機種: KV-5000        省略するとどの機種でも走らせる
#
# 期待値:
#   $DM520F = 3.0    実数の加算 2.5 + 0.5
#   $DM526  = 3      実数をワードデバイスへ書くと0方向へ切り捨て
```

**機種で触れるデバイスが違うので、走らせる相手も分かれます。** タイマ・
カウンタは KV-5000 だけ、`_melsec` の付いたものは三菱 2 機種だけです。

**`*.devices.rb` はプログラムではありません。** デバイスの割り付け表で、
`# devices:` 行で指したプログラムの読み方だけを変えます。一覧から外して
あるので、走らせる本数には数えません。期待値にも割り付けた名前を書けます。

## 手で確かめるもの

### 電源を入れ直したときの再始動

**`rake hw` では自動化できません。** 電源を切る操作が要るためです。

使うのは [test_39_restart.rb](../test/ruby_programs/test_39_restart.rb) です。
`$DM1030` に走り出した回数を数えて `loop` に入り、**終わりません**。DM は
電源を切っても残るので、入れ直して 1 増えていれば先頭を通ったことになります。
終わらないので STATUS は実行中のままで、「実行中だった」状態を作れます。

```
faruby> compile test/ruby_programs/test_39_restart.rb
faruby> dev DM1030 0     # 走り出した回数を 0 に戻す
faruby> load
faruby> run
faruby> dev DM1030       # 1 になる
```

ここで PLC の電源を切り、入れ直します。

| 見るもの | 期待 |
|---------|------|
| `status` | **実行中**。停止になっていない |
| `dev DM1030` | **2**。先頭を通った |
| `dev DM1031` | 2。ループが回っている |
| ERROR | 0 |

**止めてから切った場合も確かめます。** `stop` してから電源を入れ直し、
`status` が停止のまま、`DM1030` が増えないこと。実行中だったものだけ走り直す
形なので、この 2 つで判断そのものを確かめられます。

**4 機種で確認済みです** (実行中 → 1 から 2、停止 → 2 のまま)。
生成する言語 (KV スクリプト / ST) と起動の接点 (CR2008 / SM402) の組み合わせを
すべて通っています。

**`$FARUBY_TICKS` は 0 に戻りません。** EM / D に残る値から続けて数えます
(同じ確認で分かりました)。止めている間も進みます。

## 数えている値

| 機種 | 一致した値 |
|------|----------|
| KV-5000 | 240 |
| KV-X500 | 246 |
| MELSEC Q | 238 |
| MELSEC iQ-R | 246 |

KV-5000 が 2 つ多いのはタイマ・カウンタのぶんです。ほかの 3 機種では
そのデバイスを触れません (VM の違いではありません)。

**4 機種は同時に起動できないので、機種を入れ替えながら通します。** 繋がらない
ときは PLC ではなく PC 側の経路を先に見てください (ping と素の TCP 接続は
この PLC では当てにならず、通っている相手にも失敗を返します)。

**PLC の中身を変えていないなら、メーカー 1 機種ずつで足ります。** 生成物が
同じなら機種の違いは出ないので、違いが出るとすればメーカー間 (デバイスの
名前と番号の数え方) だけです。`test_41` (添字で引ける範囲、8 つ) は
KV-X500 と iQ-R で通していて、KV-5000 と Q の数はそれを入れる前のものです。

**VM を直したときは話が別で、4 機種とも通します。** 生成する言語 (KV スクリプト /
ST) と機種ごとの違いがそこで出ます。`loop` では KV-5000 だけが落ちる不具合
(前置きごとに Z の控えを捨てていなかった) と、MELSEC だけが落ちる不具合
(`OP_SSENDB` が STAGES から漏れていた) が別々に出ました。

`test_37_ticks` の 5 つは**時間が進んでいること**を見るもので、値そのものは
実行のたびに変わります。経った時間が 0 より大きいか、10 の倍数か、その間に
クロックパルスが両方の状態を取ったか、という形に直して数えています。
