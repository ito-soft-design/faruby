# Ruby と PLC の違い

faRuby は Ruby の意味論を PLC のスクリプト言語の上で再現します。両者は同じ演算に
見えて結果が違うことがあり、そのままにすると**エラーにならないまま値だけが狂います**。

この文書は、見つかった食い違いと、どう埋めたかの記録です。

## 差異を 2 つの層に分ける

対応する PLC が増えると、差異は性質の違う 2 種類に分かれます。混ぜて書くと
機種を追加するときに何を確認すればよいのか分からなくなるため、層を分けています。

| 層 | 内容 | 機種が増えたら | 対処が入る場所 |
|----|------|--------------|--------------|
| 層1 | Ruby の言語仕様と、PLC 一般の演算モデルの差 | 変わらない | [tools/opcode_table.rb](../tools/opcode_table.rb) (命令の意味) |
| 層2 | その機種のスクリプト言語・CPU 固有の制約 | **実機で確認し直す** | バックエンド ([tools/kvs_generator.rb](../tools/kvs_generator.rb) 等) |

層1 は「Ruby がそう決めているから合わせる」話で、命令の意味そのものです。
層2 は「この PLC ではこう書かないと動かない」話で、命令をどう綴るかの話です。
[オペコード定義表と 2 つのバックエンド](architecture.md#オペコード定義表と-2-つのバックエンド)
の境界と一致しています。

## 対処の原則

1. **既定は Ruby に合わせる。** Ruby のつもりで書いたコードが Ruby と違う動きを
   するのがいちばん困ります。
2. **合わせられない場合は明示的に違える。** 理由と影響をこの文書に書きます。
3. **黙って違わない。** 静かに壊れるより、エラーで止まるほうがましです。
4. **判断の根拠は実機で取る。** 推測で直すと逆に壊します。実際、確認せずに直して
   いたら誤った補正を入れていた項目があります (後述の整数除算)。

## 層1: 言語仕様の差 (機種によらない)

| 項目 | Ruby | PLC の一般的な流儀 | faRuby |
|------|------|------------------|--------|
| 真偽判定 | 偽は `nil` と `false` だけ。**`0` は真** | 0 = OFF = 偽 | Ruby に合わせる (型タグで判定) |
| `nil` / `false` / `0` | すべて別物 | 区別が無い | Ruby に合わせる (型タグで区別) |
| 整数除算の丸め | 切り下げ (`-7 / 2` は `-4`) | 0 方向へ切り捨て (`-3`) | Ruby に合わせる (補正を入れる) |
| 実数の 0 除算 | `Infinity` / `NaN`。例外にならない | 演算エラー | Ruby に合わせる (ビット列を直接書く) |
| 整数の桁 | 多倍長 | 固定幅 | **違える** (32 ビットで打ち切り) |
| 実数の精度 | 倍精度 | 機種による | **違える** (単精度) |
| 例外 | ある | ない | **違える** (VM をエラー停止させる) |
| 実行の中断 | しない | スキャン単位で制御が戻る | `steps_per_cycle` 命令ずつ分割 |

### 真偽判定と nil の区別

Ruby で偽になるのは `nil` と `false` だけです。**`0` も空文字列も真**です。

型タグを入れる前は値だけで判定していたため、次の食い違いがありました。

| 式 | Ruby | 導入前の faRuby |
|---|---|---|
| `if 0` | 真 | 偽 |
| `nil == false` | 偽 | 真 |
| `false == 0` | 偽 | 真 |

`nil` / `false` / `0` / `self` がすべて値 0 で、`true` が 1 だったためです。
値スロットに型タグを持たせて解決しました。詳細は
[型タグ](architecture.md#型タグ-tt_)。

タグの番号は偽の 2 つ (`TT_NIL`, `TT_FALSE`) が真より小さくなるよう並べてあり、
真偽判定は 1 比較で済みます。

#### 例外: ビットデバイスの読み取り

`$MR10` のようなビットデバイスは、Ruby の整数として 1 / 0 を返すと
`if $MR10` が**常に成立します** (0 も真のため)。PLC のプログラムでいちばん
よく書く形が使えなくなるので、ビットデバイスは `true` / `false` を返します。

書き込みは値で判定します (非 0 → ON)。`true` を 1、`false` と `nil` を 0 と
決めてあるので、真偽値でも整数でもそのまま通ります。

### 整数除算の丸め

Ruby の整数除算は切り下げ、多くの PLC・CPU は 0 方向への切り捨てです。

```
-7 / 2   Ruby: -4    KV スクリプト: -3
```

生成コードは、符号が異なり余りが出る場合に 1 を引いて合わせます。

この項目は「PLC のままでよい」と判断しかけたところ、**シミュレータが Ruby の `/`
をそのまま使っていて既に切り下げていた**ことが分かり、どちらかを必ず直す必要が
あると判明しました。Ruby に合わせれば実機側だけを直せば済み、シミュレータは
無変更で済みます。

`%` は mruby ではメソッド呼び出しにコンパイルされ、faRuby は `OP_SEND` を
実装していないため動きません。剰余の符号規則を考える必要はありません。

### 実数の 0 除算

Ruby の `1.0 / 0` は `Infinity` で例外になりません。PLC は演算エラーを出します。

除数が 0 のときは除算を実行せず、IEEE754 のビット列を直接書き込みます。
こうすれば PLC にエラーを残さず Ruby の結果になります。

| 条件 | 結果 |
|------|------|
| 被除数 > 0 | `+Infinity` |
| 被除数 < 0 | `-Infinity` |
| 被除数 = 0 | `NaN` |

書き込んだ `Infinity` をそのまま演算に使えることも実機で確認しました
(`Infinity + 1.0` は `Infinity` になり、CR2012 は出ません)。

整数どうしの 0 除算は Ruby でも `ZeroDivisionError` なので、VM をエラー停止させます。

### 合わせていない項目

**整数の桁。** Ruby の整数は多倍長ですが、faRuby は 32 ビット符号付きです。
桁あふれは検出せず切り捨てます。PLC のデバイスが固定幅である以上、多倍長を
持ち込む意味が薄いためです。

**実数の精度。** Ruby は倍精度、faRuby は単精度です。値スロットの 2 ワードに
収めるためで、PLC のデバイスも単精度が普通です。シミュレータは演算のたびに
単精度へ丸めて実機に合わせます。

**例外。** faRuby に例外機構はありません。0 除算や未知のデバイス種別は VM の
`ERROR` に code を書いて停止します。`begin`/`rescue` は使えません。

**型検査。** `1 + true` は Ruby では TypeError ですが、faRuby は値をそのまま
計算します。例外を持たないため、止めるか黙って計算するかの二択になり、
後者を選んでいます。

## 層2: 機種ごとに確認すること

**新しい PLC に対応するときは、この一覧を実機で確認してください。**
どれも「エラーにならないまま結果が変わる」たぐいのもので、
仕様書を読むだけでは分かりません。

| # | 確認項目 | 外すとどうなるか |
|---|---------|----------------|
| 1 | 既定の演算幅と符号 | 負値や大きな値が黙って化ける |
| 2 | 型サフィックスの記法と結合の順序 | 32 ビットのつもりが 16 ビットになる |
| 3 | インデックス修飾の可否・刻み幅・ワード順 | 間接アドレッシングが全滅する |
| 4 | 整数除算の丸め方向 | 負の除算だけ結果が違う |
| 5 | 実数の表現と混在演算の昇格 | 実数の実装量が大きく変わる |
| 6 | 実数の 0 除算の挙動 | PLC にエラーが残る |
| 7 | 使用できるインデックスレジスタの本数 | 変換エラー、またはラダーとの取り合い |
| 8 | 入れ子ループと `BREAK` の作用範囲 | 複数インスタンスの制御が壊れる |
| 9 | ループの `STEP` | インデックスレジスタを余分に使う |
| 10 | 変換器が弾く書き方 | 取り込み時に初めて分かる |

### Keyence KV-5000 (実測)

すべて実機で確認済みです。

| # | 項目 | 結果 | faRuby の対処 |
|---|------|------|-------------|
| 1 | 既定の演算幅 | `EM` はサフィックス無しで **16 ビット符号なし** | 負値や 65535 超は 32 ビットスクラッチ経由で扱う |
| 2 | サフィックスの位置 | 正: `EM0.L:Z1` / 誤: `EM0:Z1.L` | 誤記はエラーにならず 16 ビットに退化する。デバイス側に付ける規則を [tools/kvs_generator.rb](../tools/kvs_generator.rb) に閉じ込め、テストで検出 |
| 2 | 使えるサフィックス | `.S` `.U` `.L` `.D` `.F` | `access_type` として保持 |
| 3 | インデックス修飾 | 読み・書き・32 ビット・実数すべて可。刻み幅は `.L` でも 1 ワード、下位ワードが先 | 値スロットの参照に使用 |
| 4 | 整数除算 | 0 方向へ切り捨て (`-7 / 2` = `-3`、`-7 / 3` = `-2`) | 切り下げになるよう補正 |
| 5 | 整数 → 実数 | `.F = .L` は**数値変換**される (ビットコピーではない) | 混在演算をそのまま書ける |
| 5 | 実数 → 整数 | `.L = .F` は 0 方向へ切り捨て | デバイス書き込みの型合わせに使用 |
| 5 | 混在演算 | 自動で昇格する (`2.5 + 3` = `5.5`) | IEEE754 を手で組み立てる必要なし |
| 6 | 実数の 0 除算 | **軽度エラー CR2012**。代入先は更新されず、スキャンは継続 | 除算を実行せずビット列を直接書く |
| 6 | `Infinity` を含む演算 | 通る (`Infinity + 1.0` = `Infinity`) | そのまま扱える |
| 7 | インデックスレジスタ | Z1-Z12 のうち **Z11 と Z12 は使用不可** (特別な用途がある) | Z1-Z9 を使い、Z10 はラダー用に残す |
| 7 | Z の値域と演算 | 32767 を超えても折り返さない。`EM` を含む式や Z 自身を項にできる | ブロック先頭の計算に使用 |
| 8 | 入れ子 `FOR` の `BREAK` | **内側のループだけ**を抜ける | 「このインスタンスを止めて次へ進む」がそのまま書ける |
| 9 | `FOR ... STEP` | 使える | ブロック先頭と外側ループ変数を Z9 一本で兼ねる |
| 10 | 定数 0 での除算 | **変換器が弾く** | 生成コードで定数 0 を除数にすることはないため制約にならない |

その他、確認の過程で分かったこと。

- `EM` は初期化されません。読んで 0 でも未使用とは限らず、非ゼロでも使用中とは
  限りません。空き領域はラダーのデバイス割り付けで判断します。
- 範囲外 (EM65536 以降) を読むと 512 ワード周期で同じ値が返ります。

### 三菱 MELSEC (未調査)

未対応です。着手する際は上の一覧をラダー・構造化テキストで確認してください。
とくに次の点は KV と違う可能性が高く、設計に影響します。

- インデックスレジスタの本数と、ユーザープログラムとの取り合い
- 型の指定方法 (KV のサフィックスに相当するもの)
- 入れ子ループと中断の作用範囲
- 実数の表現

## 確認の進め方

機種依存の項目は、一時的なスクリプトを PLC に転送して結果をホストから読む方法で
確認しています。

1. 確認したい式を並べたスクリプトを書き、結果を空き領域へ書き出す
2. KV Studio に取り込んで転送する
3. ホストから読み、期待値と比べる
4. 済んだらスクリプトを削除する

手順の注意点です。

- **出力は 2 ワードずつ空けて配置する。** 32 ビット値が隣の出力を潰します。
  実際にこれで 1 項目を誤判定しました。
- **期待値をスクリプトのコメントに書いておく。** 後から読み返すときに効きます。
- **読み取り側の幅を合わせる。** 符号なしで読んで `-4` を `65532` と誤読しました。
- **1 つの確認で 1 つのことだけを見る。** 複数の要素が絡むと、どれが原因か
  分かりません。

過去のプローブは git の履歴に残っています (`probe_instances.kvs`、`probe_float.kvs`)。

## 静かに壊れた実例

いずれもエラーにならないまま値だけが狂った例です。この種の不具合は
実機で動かすまで見つかりません。

| 症状 | 原因 | 気づいたきっかけ |
|------|------|----------------|
| `300 * 300` が `24464` | `.L` がインデックスレジスタに結合し 16 ビットに退化 (91 箇所) | 32 ビット演算の実機確認 |
| 負の値が巨大な正の値になる | `EM` がサフィックス無しで 16 ビット符号なし | 負値のロード |
| `a = 2.5` が `0` | `.mrb` の実数リテラルだけがリトルエンディアン | 実数の実機確認前のシミュレータ実行 |
| `while i < 200` が一度も回らない | `OP_LOADI` のオペランドを符号付きとして扱っていた | 0 除算の確認で 200 回ループを書いたとき |
| `while` が必ずエラー | `OP_LOADNIL` が生成物にだけ無い | 実機で `while` を動かしたとき |

`OP_LOADI` の件は、命令表の名前が `OP_LOADI8` になっていたことが誤りの元でした。
mruby の `ops.h` は `OPCODE(LOADI, BB)` で、実装 (`vm.c`) は
`SET_FIXNUM_VALUE(regs[a], b)` と符号拡張しません。負値は `OP_LOADINEG` の
担当です。名前に「8ビット符号付き」という誤った前提が入り込んでいました。

**命令表は mruby の `ops.h` と突き合わせてください。** 突き合わせた際、
`OP_KEY_P` と `OP_UNDEF` の命令形式も違っていました。どちらも未実装ですが、
形式が違うと逆アセンブラがその命令以降を読み違えます。

最後の 1 件をきっかけに、命令定義を 1 つの表にまとめて生成する構成へ移行しました。
[なぜ生成にしたか](architecture.md#なぜ生成にしたか)を参照してください。

`.mrb` の実数リテラルは PLC ではなく mruby 側の話ですが、同じ性質を持つため
ここに挙げています。RITE 形式の整数や長さはビッグエンディアンなのに、
実数だけは mruby の `dump.c` がネイティブのバイト順で書き出します。
ビッグエンディアンとして読むと `2.5` が `5.375e-321` になります。
