# ロードマップ

何を作るかと、なぜその順序なのかの記録です。

## 現在できること

- 整数 (32ビット符号付き) と実数 (単精度) の四則演算・比較
- 整数のビット演算 (`&` `|` `^` `~` `<<` `>>`)
- `nil` / `true` / `false` と数値の区別。真偽判定は Ruby と同じ
- `if` / `while` による分岐と繰り返し
- グローバル変数と PLC デバイスの読み書き (アクセス幅の指定を含む)
- インスタンス変数 (`@foo`)。クラス変数 (`@@foo`) は未対応
- 組み込みメソッド 28 個。一覧は [README](../README.md#組み込みメソッド)
- メソッドの定義と呼び出し (引数・再帰・途中の `return`・`obj.foo`)
- ブロックと反復 (`times` / `upto` / `each` / `break` / `loop`)
- 配列 (リテラル・添字・`length` / `size` / `<<` / `push` / `each`)
- ハッシュ (リテラル・添字・`length` / `key?` / `keys` / `values` / `each`)
- 文字列 (リテラル・デバイスとの読み書き・`==` / `+` / 式展開・
  `length` / `empty?` / `<<` / `[]`)
- 単項の符号 (`-x` / `+x`)
- 時間 (`$FARUBY_TICKS` と 3 つのクロックパルス。ラダーは要らない)
- 複数プログラムの並行実行

**4 機種で動きます** — KV-5000 / KV-X500 / MELSEC Q / MELSEC iQ-R。
実機で一致した値は 240 / 246 / 238 / 246 です。

実装済みの命令は 62 個です。詳細は [対応オペコード一覧](opcodes.md)。

**ロードマップの項目はすべて片付きました。** 残っているのは
[独立した項目](#独立した項目) と、文字列の加工 (`*` / `sub` / 書式化) です。

## 依存関係

```
動的デバイスアクセス ── 独立。ヒープもメソッドも不要
組み込みメソッド ────── OP_SEND の限定実装。呼び出しフレーム不要
メソッド定義・呼び出し ── 子 irep + 呼び出しフレーム
        │
      ブロック ──────── each / times / upto
        │
   ヒープ設計 ────── Array ── Hash ── String
                                    ↑ ここまで実装済み
```

## なぜ Array / String / Hash が先ではないのか

**リテラルと添字以外はすべてメソッド呼び出しだからです。** 逆アセンブルで
確認した結果です。

```
[1, 2, 3]      → OP_ARRAY2     専用命令
e[0]           → OP_GETIDX     専用命令
"hi"           → OP_STRING     専用命令
a.length       → OP_SEND       メソッド呼び出し
a.push(4)      → OP_SEND
a.each { }     → OP_BLOCK + OP_SENDB
```

Array を入れても、作って添字で読むだけで `length` も `push` も `each` も
動きません。メソッド呼び出しとヒープの両方が揃って初めて実用になります。

## 1. 動的デバイスアクセス — 実装済み

デバイスアドレスがコンパイル時に確定するため、実行時に計算したアドレスの
デバイスを読み書きできませんでした。センサ群やレシピデータをまとめて扱う、
PLC ではごく普通の処理ができない状態でした。

```ruby
i = 0
while i < 10
  $DM[600 + i] = 0
  i = i + 1
end
```

アドレスを外した `$DM` を「デバイス族」とし、添字を付けて実行時に決めます。
`OP_GETIDX` / `OP_SETIDX` は専用命令なのでメソッド呼び出しもヒープも不要でした。

決めた内容は [デバイス参照](architecture.md#デバイス参照-tt_device) にあります。

- 幅サフィックスは `$DML[i]`。正式名を略記より先に解析するため一意に決まる
- `$DM100[i]` は不可。`$DM100` はスカラとしても使われ、どちらも同じ
  `OP_GETGV` になるため VM 側で区別できない
- 範囲チェックあり。EM は範囲外を読むと 512 ワード周期で値が返るため
- 添字はデバイス番号。MR400 は 64。`plc_access` の `PlcDevice` と同じ規則

## 2. 組み込みメソッド — 実装済み

`a != b` が書けませんでした。`OP_SEND` にコンパイルされるためです
(`if a == b` の else で代用していました)。`!` / `%` と
`abs` / `to_i` / `to_f` / `floor` / `round` も同じです。利用者が最初に
つまずくのはおそらくここでした。

逆アセンブルで確認した形です。

```
a != b     → OP_SEND [4, sym(!=), 1]     引数1個
!a         → OP_SEND [3, sym(!),  0]     引数なし
a % b      → OP_SEND [4, sym(%),  1]
a.abs      → OP_SEND [3, sym(abs), 0]
3.times {} → OP_BLOCK + OP_SENDB          ← 子 irep が要る。項目 4
```

`7 % 3` のような定数どうしは mrbc が畳み込むため `OP_SEND` になりません。
変数を挟んだときだけ現れます。

受け手の型とメソッド名の組み合わせを限定して `OP_SEND` を実装しました。
呼び出しフレームは作りません。引数は `R[a+1]` から連続して並び、結果は
`R[a]` に返るためです。

メソッド名はシンボル表にあり、シンボル表は既にデバイスマッピングテーブルの
索引として転送していました。**ホスト側で名前を小さな整数に解決して渡すため、
VM は文字列比較をせず整数の分岐だけで済みます。** シンボル表の 4 ワード目を
「デバイス族フラグ」から「シンボル種別」に広げ、メソッド名のエントリでは
1 ワード目にメソッド番号、3 ワード目に引数の数を入れています。メモリ配置は
変わっていません。

未対応のメソッドはコンパイル時ではなく実行時に `ERROR` で止まります
(受け手の型が実行時にしか分からないため)。

- 数値レシーバを要求するメソッドを連続した番号に並べ、型検査を 1 比較に
  収めている (真偽判定のタグ順と同じ手)
- `%` は整数どうしのみ。実数は型エラー
- `&` / `|` / `^` / `~` / `<<` / `>>` は後から入れた。`<<` は整数なら
  左シフト、文字列と配列なら継ぎ足し (Ruby と同じ)

実機で確認済みです ([test_18_methods.rb](../test/ruby_programs/test_18_methods.rb))。
シミュレータでは再現できない次の 2 つも通っています。

- 整数と実数の混在比較 (`EM16.L:Z9 <> EM1.F:Z1`)。`floor` の端数判定に使う
- 実数リテラルを含む式 (`EM1.F:Z1 + 0.5`)。`round` に使う

### エラーコード

| code | 意味 |
|------|------|
| 1 | 0 除算 (`/` と `%`) |
| 2 | 添字アクセス (デバイス参照でも配列でもない、または範囲外) |
| 3 | 未対応のメソッド、または引数の数が合わない |
| 4 | レシーバまたは引数の型が扱えない |
| 5 | 呼び出しが深すぎる (フレームまたはレジスタが足りない) |
| 6 | 引数の数または形が扱えない (省略可能・可変長・キーワードは未対応) |
| 7 | `OP_METHOD` / `OP_BLOCK` が指す子 irep が無い |
| 8 | 上位の変数に届かない (指定された段数だけ遡れなかった) |
| 9 | ブロックの扱いが不正 (ブロックでない値を渡した、反復の外で `break` した) |
| 10 | 配列の領域が足りない (プールを使い切った、要素数が容量を超えた) |

## 3. メソッド定義・呼び出し — 実装済み

設計と実装の記録は [メソッド定義・呼び出しの計画](method_calls.md) にあります。

`def` が書けます。引数・再帰・途中の `return`・メソッド内からのデバイス
アクセス・レシーバを書く呼び出し (`obj.foo`) が動きます。省略可能引数・
可変長引数・キーワード引数は未対応です。

**`obj.foo` は `OP_SSEND` の重複を消したときに動くようになりました。**
self をレシーバ位置に置いてから `OP_SEND` へ落ちる形にすると、どちらも同じ
経路を通ります (mruby と同じ)。組み込みメソッドの振り分けが 2 度展開されて
いたのも同時に消え、KV は 16% 縮みました。

呼び出しの深さは `memory.max_frames` (既定 16) とレジスタ領域で決まり、
超えるとエラーで停止します。PLC はメモリが固定なので、上限で止めるしか
ありません。

`def` は `OP_TCLASS` + `OP_METHOD` + `OP_DEF` で、**子 irep** を必要とします。
以前 `plc_codegen` はトップレベルの irep しか転送していなかったため、仕組みごと
未対応でした。入れたもの:

- 子 irep の転送とアドレス付け (IREP テーブル)
- 呼び出しフレーム (戻り先 PC・irep・レジスタ基点の退避)
- `OP_SSEND` (レシーバを書かない呼び出しはこちらになる)
- `OP_ENTER` (引数の数の検査)
- `OP_RETURN` のフレーム復帰
- メソッド表 (ホスト側で振った ID → irep)

工数の大半は**メモリ配置の作り直し**でした。バイトコード・定数プール・シンボル表
が irep ごとになり、生成コードで定数だったアドレスが VM 状態経由の間接参照に
変わりました。

## 4. ブロック — 実装済み

設計と実装の記録は [ブロックの計画](blocks.md) にあります。

`times` と `upto` にブロックを渡せます。入れ子・`break`・メソッドの中・
ブロックの中からのメソッド呼び出しが動きます。

```ruby
sum = 0
3.times do |i|
  sum = sum + i
end
```

`OP_SENDB` は呼び出しの仕組みでしかなく、**繰り返すのは `Integer#times` の側**
です。VM は再帰できないため、反復フレームに「今何回目か」と「上限」を持たせ、
ブロックの `OP_RETURN` で次の回に入り直します。

実機で確認済みです ([test_20_blocks.rb](../test/ruby_programs/test_20_blocks.rb))。
実行速度は 32,449 命令/秒、スキャン周期 1.54 ms です。

`loop` も入りました。`OP_SSENDB` (self への呼び出し) で `OP_SENDB` とは
別命令なので、self をレシーバ位置に置く前処理として足しています。
`yield` とブロック引数 (`&blk`) は未対応です。
`each` は Array と一緒に項目 5 で入りました。

## 5. ヒープ設計

設計メモは [ヒープの計画](heap.md) にあります。

Array / String / Hash に共通する置き場所です。固定数のスロットを持つプールを
用意し、**順に渡して返さない (GC 無し)、使い切ったらエラー**から始めます。

GC が難しいのは停止時間が読めないからですが、faRuby は**ヒープが固定長で根も
小さい**ため、必要になれば上限の計算できるマークスイープを後から足せます。
案 2 (エラー) と案 3 (回収) の間に Ruby としての意味の違いは無く、エラーが
出なくなるだけです。

逆アセンブルの結果、**既存の仕組みにかなり載る**ことが分かりました。
`OP_GETIDX` / `OP_SETIDX` は実装済みで枝を足すだけ、`length` / `<<` / `push`
は `OP_SEND`、`each` は `OP_SENDB` です。新しく要るのは `OP_ARRAY` /
`OP_ARRAY2` と実体の置き場所です。

リテラル・添字・`length` / `size` / `<<` / `push` / `each` が動きます。
実機で確認済みです
([test_21_arrays.rb](../test/ruby_programs/test_21_arrays.rb))。
実行速度は 32,711 命令/秒、スキャン周期 1.53 ms で、配列を入れる前から
変わっていません。

```ruby
a = [11, 22, 33]
$DM100 = a[1]     # 22
a[1] = 99

s = 0
a.each do |v|
  s = s + v
end
```

## 6. Array / String / Hash

3 つとも実装済みです。実体は共通の配列プールに置き、返さないので
使い切ったら止まります。詳細は [ヒープの設計](heap.md)、
[ハッシュの計画](hash.md)、[文字列の計画](string.md)。

String は**バイト列を変換しません**。ソースの文字コードがそのまま
デバイスへ出ます。種別を 1 ワード覚えておき、`length` と `[]` を
文字単位にしています。

```ruby
FARUBY_STR_FILL = 0x20    # 固定長の余りを空白で埋める

s = "あいう"
$DM100 = s                # 終端付き
$DM200T10 = s             # 10 バイトの固定長
$DM300 = s.length         # 3。バイト数の 9 ではない
$DM400 = s[0]             # "あ"
```

残るのは `*` (繰り返し) と `sub` / `upcase` などの加工、書式化です。
どれも新しいスロットを取るので、使う場面を見てから決めます。

## 独立した項目

| 項目 | 内容 |
|------|------|
| インスタンスを増やす | `memory.instances` を増やして EM20000-EM39999 を使い切る。1 インスタンス 2000 ワードなので 10 個まで。設定変更と再取り込みのみでコード変更は不要 |
| ~~Symbol~~ | 実装済み。値はホストが名前ごとに振った通し番号で、irep をまたいでも `==` で比べられる。Hash のキーに使う。詳細は [ハッシュの計画](hash.md) |
| ~~STEP_COUNT~~ | 実装済み。VM の最初のコミットから領域と `status` の表示はあったが、生成コードが更新しておらず常に 0 だった。`INC` で数えるようにした。費用は 1.5% |
| ~~固定領域を ZF へ~~ | 実装済み。実行中に変わらない領域を FM (バンク 3 の ZF) に移し、EM 側は 1 インスタンス 1000 ワードになった。詳細は [アーキテクチャ](architecture.md#fm-と-zf) |
| ~~実数のオーバーフロー検査~~ | **入れないと決めた。** 検出はできる (上位ワードの指数部を整数として見る) が、実数演算のたびに走る割に実数を使うプログラムが多くないため。利用者が避ける前提。測定結果と理由は [Ruby との違い](differences.md#検査を入れないと決めた) |
| ~~MELSEC 対応~~ | 実装済み。Q と iQ-R で 223 個ずつ実機一致。ST 1 本にまとまるのでラダーが要らない。実機で分かったことは [MELSEC 対応の計画](melsec.md) |
| mruby 4.0 対応 | オペコード番号の変更に追従。影響は `MRUBY_OPCODES` のみ |
| ~~PLC 起動時に先頭から実行する~~ | 実装済み。**走らせ直すかどうかは電源が切れたときの状態で決める** — 実行中だったら先頭から、停止・完了・エラーならそのまま止めておく。設定を足さなかったのは、これが利用者の意図とふつう一致するから。起動の合図は初回スキャンのみ ON の接点 (KV は CR2008、MELSEC は SM402。**4 機種すべて実機で確認済み** — 実行中のまま切ると走り出した回数が 1 増え、停止してから切ると増えない)。初期化するのは実行位置・状態・エラー・歩数・レジスタ・フレーム・配列プール・汎用グローバル変数で、**メソッド表とバイトコードは残す** (`load` し直さずに済む)。初期化はリセット要求と同じ処理を呼ぶ。**リセット要求に乗せる形は採らなかった** — 要求の枝は STATUS を停止にするので、「初期化のあと実行中へ戻す」ことを覚えておく語が VM 状態に 1 つ要る。初期化を 2 回展開する代わりに語を増やさずに済ませた (初期化はスキャンごとの経路ではないので費用は無視できる)。**電源が切れる前のリセット要求は落とす** — 残すと走らせ直した直後に止めてしまう。使い方は [README](../README.md#電源を入れ直したとき) |
| ~~時間を測る (tick カウンタ)~~ | 実装済み。`$FARUBY_TICKS` が数え始めてからのミリ秒 (**電源を入れ直しても 0 に戻らない**。EM / D に残る値から続ける。実機で確認)、`$FARUBY_CLOCK_10MS` / `_100MS` / `_1S` がクロックパルスそのもの。生成スクリプトが 10ms クロックの立ち上がりをスキャンごとに数える。**読み出しに枝を足していない** — ticks は普通のデバイス読み (32 ビット)、パルスは値スロットなので汎用グローバルの経路に載る。パルスを 1 / 0 の整数にしなかったのは Ruby では 0 も真だから。時刻源は機種が持つ (KV は CR2004/2005/2006、MELSEC は SM409/410/412。**4 機種すべて実機で確認済み**)。**値スロットはブロック先頭から 4 の倍数に置く** — 三菱は `VMSLOT[添字]` で指し、添字を「ワード数 / 4」で求めるためで、ずれると手前のスロットを読む (実機で起きた)。**スキャンタイムが 5ms を超えると取りこぼす。** 使い方は [README](../README.md#時間) |
| ~~デバイスの割り付け表~~ | 実装済み。抽象的な名前を実デバイスに割り付け、設備が変わってもプログラムを直さずに済むようにした。**実行時の費用はゼロ** — 種別と番号は実行時にシンボル表から引いているので、表の項目に割り付け先を入れれば実デバイスを直に書いたのと同じバイトコードになる。読む場所は [device_syntax.rb](../tools/device_syntax.rb) の `parse_symbol` 1 箇所で、`load` も `dev` も `sim` も `rake hw` も同じ読み方になる。**置き場所はプログラムの隣** ([device_map.rb](../tools/device_map.rb))。最初は接続先 (`connections:`) の下に YAML で置いたが、**割り付けは PLC ではなくプログラムのもの**なので移した (同じ PLC に別のプログラムを載せれば割り付けも変わる)。プログラムの先頭 1 行 `# devices: line1.devices.rb` で指す。表は Ruby で、読むときに `Kernel.load` で**本当に実行する** — 連番の配線を `16.times { \|i\| map "in_#{i}", "R#{i}" }` と書けるのが YAML にしなかった理由。`require` ではなく `load` なのは、同じ表を読み直せるようにするため。**表は任意で、表に無い名前は今までどおり実デバイスとして読む。** 幅は名前を引いてから付ける (`$y0L` は表の `y0L` を先に探し、無ければ `y0` に `.L`)。転送前に止めるのは 5 つ: 表が見つからない / 同じ名前を 2 度 / 割り付け先が読めない / 実デバイスと重なる名前 / 使い方が割り付け先と食い違う。**実デバイスと重なるかは機種で違う** — 三菱には X / Y があるので `x0` は実デバイス (テストで固定した)。`warn_unmapped!` で実デバイスの直書きを知らせる。**添字は付けられない** — `$x0[i]` は整数のビット取り出しになる。シンボル表は `$x0` という名前しか持たず、添字を付けたかどうかはバイトコードを追わないと分からないので、コンパイル時に弾くのは見送った。**4 機種で実機確認済み** — `test_40` の 5 つ (ビット・ワード・幅付き・繰り返しで生成した項目・実デバイスとの混在) が一致。**プログラム本文はキーエンス版と三菱版で 1 文字も変わらず、違うのは割り付け表だけ。**ホスト側だけの仕組みなので生成物は変わらないが、**シンボル表に入る種別と番号が違えば黙って別のデバイスを書く**ので実機で見た。使い方は [README](../README.md#デバイスの割り付け) |
| ~~割り付け表で変数も実デバイスにする~~ | 実装済み。**割り付け表を入れた時点で通っていた** — 足すものは何も無く、`map "timer1", "DM100"` と書けばシンボル表の項目がデバイスになるだけ。汎用グローバルの枠 (`max_globals` 100) も使わない。**「失われるもの」の見立ては外れていた。** 型タグが無いので配列・文字列は持てないと書いていたが、**デバイスの既存の決まりがそのまま効く** — 配列は連続デバイスへ並び (`[1,2,3]` → `DM1060-1062`)、文字列は文字で入り (`"abc"` → `0x6162 0x6300`)、実数は 0 方向へ切り捨て。実際に通して確かめた ([test_end_to_end.rb](../test/test_end_to_end.rb))。**本当に残る落とし穴は 2 つだけ**で、どちらも `nil` が持てないことから来る: (1) `$flag = nil` は黙って 0 になる (2) **`$once \|\|= 7` が一度も代入されない** — デバイスから読んだ 0 は Ruby では真なので。**同じプログラムが割り付け表の有無で違う結果になるのはこの形だけ。** テストで留めてある。性質が変わる点の見立ては当たっていて、利点にもなる: **`load` で消えない** (汎用グローバルはスロットを 0 で潰される) / **インスタンスをまたいで共有できる** / **ラダーや表示器から見える**。次は下の `nil` の検査 |
| ~~割り付けた名前を添字で引く~~ | 実装済み。`map "iai_regs", "D100", 8` と書くと `$iai_regs[0]` が D100、`[7]` が D107 になる。**VM には足すものが無かった** — `$DM[i]` のデバイス族と同じ形で、基点が 0 でないだけ。添字はデバイス番号にそのまま足され、種別と基点はどちらも実行時にシンボル表から引いているので、`parse_mapped` が族として返すだけで通った (`entry` の `family ? 0` という基点の決め打ちを外した)。**数えるのはワード** (`$DM[i]` と同じ)。幅を付けても 1 つ飛びにはならない。ビットデバイスの範囲も作れて、**番号はメーカーの数え方** — `MR110` は番号 26 なので `$bits[6]` は `MR200` (チャンネルをまたぐ)、三菱の `M110` は `M116`。コンソールの `dev iai_regs` は中身を並べる (表示アドレスに戻すため `address_of` を足した)。転送前に止まるのは、ワード数が整数でない / 1 未満 / 範囲の終わりが 65535 を越えたとき。**`Integer(1.5)` が 1 になるので整数だけを受ける** (通すと 1 ワードずれる)。KV-X500 と iQ-R で `test_41` の 8 つが一致。**PLC の中身を変えていないのでメーカー 1 機種ずつで足りる** (生成物が同じなら機種の違いは出ず、違いが出るとすればデバイスの名前と番号の数え方だけ)。使い方は [README](../README.md#添字で引ける範囲) |
| 範囲外の添字を止める | `$iai_regs[8]` が黙って隣の D108 を書く。**デバイス参照 (TT_DEVICE) が持てるのは基点と種別・幅だけ**で、ワード数が入る場所が無い。値ワードの下位が基点 (16 ビット)、上位が `種別 + 幅 * 16` で、文字列デバイスは幅に桁数が入るため上位も空いていない。入れるなら (1) シンボル表のエントリを 4 → 5 ワードにする (固定領域の配置が全部ずれ、4 機種の生成と実機確認をやり直す) (2) 値スロットの予備ワードを使う (`OP_MOVE` が 4 ワード目まで複製することになり、複製のたびに費用がかかる) (3) 種別の語にワード数を詰める (シンボル参照の毎回通る分岐を触る)。**桁の決まった添字だけなら逆アセンブルから見つけられる** — `OP_GETGV` → 添字の `OP_LOADI` → `OP_GETIDX` / `OP_SETIDX` の並びを見る形で、飛び先が絡むと当てにならないので「見つけたら警告」までが安全。費用の小さい順に (3) → 静的な検査 → (1) |
| `nil` の代入をコンパイル時に弾く | 実デバイスに `nil` を入れると黙って 0 になり、読み直すと Ruby では真になる。**`$once \|\|= 7` が一度も代入されない形が実害**で、汎用グローバルなら 7 が入る。リテラルの `= nil` はバイトコード (`OP_LOADNIL` の行き先) から見つけられるので、ほかの領域と同じくコンパイル時に止めたい。`\|\|=` そのものは `OP_JMPIF` の形なので、デバイスを読んでいる枝を見つければ警告は出せる見込み |
| ~~`loop` を入れる~~ | 実装済み。`OP_SSENDB` (0x2E) を「self をレシーバ位置に置いて `OP_SENDB` の枝へ落ちる」前処理として足し、`loop` をメソッド表に入れた。レシーバは self (`TT_OBJECT`) で、`METHOD_RECEIVER_GROUPS` の末尾に区分を足したので既存のメソッド番号は振り直していない。**上限の無い反復はフレームの種別を 1 つ足して比較を飛ばす** — 上限を 2147483647 にする手は採らなかった (何日か回すと終わってしまい、年単位で動く PLC に合わない)。**R[0] をトップレベルの self にする必要もあった** — mruby は `OP_LOADSELF` を書かずに R[0] が self である前提で呼び出すため、空のままだと `TT_EMPTY` でレシーバの型検査に落ちる。`loop` が最初の「self をレシーバに取る組み込みメソッド」だったために出てきた穴。メモリ配置は変えていないが、生成物は 4 機種とも出し直しが要る。詳細は [ブロックの計画](blocks.md) |
| 現在時刻を読む | カレンダー (年月日時分秒) を Ruby から読む。ログに時刻を残す用途。**差分の判定には向かない** — 桁の繰り下がりと日またぎがあり、faRuby に `Time` も日付演算も無い。時間の判定は上の tick に任せる |
| ~~汎用グローバルの個数を検査する~~ | 実装済み。`validate!` に「変数の数」を足し、`$foo` と `@foo` が分け合う枠 (`max_globals`、既定 100) を転送前に見る。**既定の設定では先にシンボル数で止まることが分かった** — どちらも 100 で、変数は必ずシンボルを 1 つ使うため。効くのは `max_symbols` を増やした配置で、順番で隠れていても検査そのものは要る (テストで固定した) |

## 次に考えること

**オブジェクト。** インスタンス変数 (`@`) は入りました
([インスタンス変数の計画](instance_vars.md))。残っているのはクラスで、
`OP_CLASS` / `OP_EXEC` / `OP_SCLASS` と `new`、メソッド探索が要ります。

**固定メモリに何をどれだけ置くかの判断になります。** `TT_OBJECT` は今は
印だけで中身がありません。クラスごとのインスタンス変数の並び、インスタンスの
領域の上限、メソッド探索 (今はシンボル表のメソッド番号で直に振り分けている)
をどうするかが決まっていません。

**`@` の側は作り替えになります。** いまは「self が 1 つしか無い」ので名前
ごとに 1 枠ですが、`Foo.new` が 2 つできた時点で「どの self のものか」で
行き先が変わります。直すのは `OP_GETIV` / `OP_SETIV` の 2 命令と、シンボル
表の項目の意味だけです。

**クラス変数 (`@@`) はクラスと一緒に考えます。** いまはコンパイル時に
止めています。手間は `@@` そのものではなく継承で決まります — 継承が無ければ
クラスごとに 1 枠で済み、継承を入れると親まで遡って探すところが要ります。

## 当面やらないこと

**例外 (`begin` / `rescue`)。** faRuby に例外機構はありません。0 除算などは
VM の `ERROR` に code を書いて停止します。PLC のプログラムで例外による制御が
必要になる場面は考えにくく、優先度は低いままです。
