# ロードマップ

何を作るかと、なぜその順序なのかの記録です。

## 現在できること

- 整数 (32ビット符号付き) と実数 (単精度) の四則演算・比較
- 整数のビット演算 (`&` `|` `^` `~` `<<` `>>`)
- `nil` / `true` / `false` と数値の区別。真偽判定は Ruby と同じ
- `if` / `while` による分岐と繰り返し
- グローバル変数と PLC デバイスの読み書き (アクセス幅の指定を含む)
- クラス (`class` / `new` / `initialize` / オブジェクトごとの `@foo` /
  クラスごとの `@@foo`)。継承は未対応
- 定数 (`FOO = 1`)。`C::LIMIT` の形は未対応
- 組み込みメソッド 32 個。一覧は [README](../README.md#組み込みメソッド)
- メソッドの定義と呼び出し (引数・再帰・途中の `return`・`obj.foo`)
- ブロックと反復 (`times` / `upto` / `each` / `break` / `loop`)
- 配列 (リテラル・添字・`length` / `size` / `<<` / `push` / `each`)
- ハッシュ (リテラル・添字・`length` / `key?` / `keys` / `values` / `each`)
- 文字列 (リテラル・デバイスとの読み書き・`==` / `+` / 式展開・
  `length` / `empty?` / `<<` / `[]`)
- 単項の符号 (`-x` / `+x`)
- 時間 (`$FARUBY_TICKS` と 3 つのクロックパルス。ラダーは要らない)
- 複数プログラムの並行実行

**4 機種で動きます** — KV-5000 / KV-X500 / MELSEC Q / MELSEC iQ-R。
実機で一致した値は 260 / 258 / **104** / 258 です。**Q が少ないのは
文字列・配列・ハッシュを載せていないから**で、VM の違いではありません
([doc/melsec.md](melsec.md))。

実装済みの命令は 67 個です。詳細は [対応オペコード一覧](opcodes.md)。

**ロードマップの項目はすべて片付きました。** 残っているのは
[独立した項目](#独立した項目) と、文字列の加工 (`*` / `sub` / 書式化) です。

## 依存関係

```
動的デバイスアクセス ── 独立。ヒープもメソッドも不要
組み込みメソッド ────── OP_SEND の限定実装。呼び出しフレーム不要
メソッド定義・呼び出し ── 子 irep + 呼び出しフレーム
        │
      ブロック ──────── each / times / upto
        │
   ヒープ設計 ────── Array ── Hash ── String
                                    ↑ ここまで実装済み
```

## なぜ Array / String / Hash が先ではないのか

**リテラルと添字以外はすべてメソッド呼び出しだからです。** 逆アセンブルで
確認した結果です。

```
[1, 2, 3]      → OP_ARRAY2     専用命令
e[0]           → OP_GETIDX     専用命令
"hi"           → OP_STRING     専用命令
a.length       → OP_SEND       メソッド呼び出し
a.push(4)      → OP_SEND
a.each { }     → OP_BLOCK + OP_SENDB
```

Array を入れても、作って添字で読むだけで `length` も `push` も `each` も
動きません。メソッド呼び出しとヒープの両方が揃って初めて実用になります。

## 1. 動的デバイスアクセス — 実装済み

デバイスアドレスがコンパイル時に確定するため、実行時に計算したアドレスの
デバイスを読み書きできませんでした。センサ群やレシピデータをまとめて扱う、
PLC ではごく普通の処理ができない状態でした。

```ruby
i = 0
while i < 10
  $DM[600 + i] = 0
  i = i + 1
end
```

アドレスを外した `$DM` を「デバイス族」とし、添字を付けて実行時に決めます。
`OP_GETIDX` / `OP_SETIDX` は専用命令なのでメソッド呼び出しもヒープも不要でした。

決めた内容は [デバイス参照](architecture.md#デバイス参照-tt_device) にあります。

- 幅サフィックスは `$DML[i]`。正式名を略記より先に解析するため一意に決まる
- `$DM100[i]` は不可。`$DM100` はスカラとしても使われ、どちらも同じ
  `OP_GETGV` になるため VM 側で区別できない
- 範囲チェックあり。EM は範囲外を読むと 512 ワード周期で値が返るため
- 添字はデバイス番号。MR400 は 64。`plc_access` の `PlcDevice` と同じ規則

## 2. 組み込みメソッド — 実装済み

`a != b` が書けませんでした。`OP_SEND` にコンパイルされるためです
(`if a == b` の else で代用していました)。`!` / `%` と
`abs` / `to_i` / `to_f` / `floor` / `round` も同じです。利用者が最初に
つまずくのはおそらくここでした。

逆アセンブルで確認した形です。

```
a != b     → OP_SEND [4, sym(!=), 1]     引数1個
!a         → OP_SEND [3, sym(!),  0]     引数なし
a % b      → OP_SEND [4, sym(%),  1]
a.abs      → OP_SEND [3, sym(abs), 0]
3.times {} → OP_BLOCK + OP_SENDB          ← 子 irep が要る。項目 4
```

`7 % 3` のような定数どうしは mrbc が畳み込むため `OP_SEND` になりません。
変数を挟んだときだけ現れます。

受け手の型とメソッド名の組み合わせを限定して `OP_SEND` を実装しました。
呼び出しフレームは作りません。引数は `R[a+1]` から連続して並び、結果は
`R[a]` に返るためです。

メソッド名はシンボル表にあり、シンボル表は既にデバイスマッピングテーブルの
索引として転送していました。**ホスト側で名前を小さな整数に解決して渡すため、
VM は文字列比較をせず整数の分岐だけで済みます。** シンボル表の 4 ワード目を
「デバイス族フラグ」から「シンボル種別」に広げ、メソッド名のエントリでは
1 ワード目にメソッド番号、3 ワード目に引数の数を入れています。メモリ配置は
変わっていません。

未対応のメソッドはコンパイル時ではなく実行時に `ERROR` で止まります
(受け手の型が実行時にしか分からないため)。

- 数値レシーバを要求するメソッドを連続した番号に並べ、型検査を 1 比較に
  収めている (真偽判定のタグ順と同じ手)
- `%` は整数どうしのみ。実数は型エラー
- `&` / `|` / `^` / `~` / `<<` / `>>` は後から入れた。`<<` は整数なら
  左シフト、文字列と配列なら継ぎ足し (Ruby と同じ)

実機で確認済みです ([test_18_methods.rb](../test/ruby_programs/test_18_methods.rb))。
シミュレータでは再現できない次の 2 つも通っています。

- 整数と実数の混在比較 (`EM16.L:Z9 <> EM1.F:Z1`)。`floor` の端数判定に使う
- 実数リテラルを含む式 (`EM1.F:Z1 + 0.5`)。`round` に使う

### エラーコード

| code | 意味 |
|------|------|
| 1 | 0 除算 (`/` と `%`) |
| 2 | 添字アクセス (デバイス参照でも配列でもない、または範囲外) |
| 3 | 未対応のメソッド、または引数の数が合わない |
| 4 | レシーバまたは引数の型が扱えない |
| 5 | 呼び出しが深すぎる (フレームまたはレジスタが足りない) |
| 6 | 引数の数または形が扱えない (省略可能・可変長・キーワードは未対応) |
| 7 | `OP_METHOD` / `OP_BLOCK` が指す子 irep が無い |
| 8 | 上位の変数に届かない (指定された段数だけ遡れなかった) |
| 9 | ブロックの扱いが不正 (ブロックでない値を渡した、反復の外で `break` した) |
| 10 | 配列の領域が足りない (プールを使い切った、要素数が容量を超えた) |

## 3. メソッド定義・呼び出し — 実装済み

設計と実装の記録は [メソッド定義・呼び出しの計画](method_calls.md) にあります。

`def` が書けます。引数・再帰・途中の `return`・メソッド内からのデバイス
アクセス・レシーバを書く呼び出し (`obj.foo`) が動きます。省略可能引数・
可変長引数・キーワード引数は未対応です。

**`obj.foo` は `OP_SSEND` の重複を消したときに動くようになりました。**
self をレシーバ位置に置いてから `OP_SEND` へ落ちる形にすると、どちらも同じ
経路を通ります (mruby と同じ)。組み込みメソッドの振り分けが 2 度展開されて
いたのも同時に消え、KV は 16% 縮みました。

呼び出しの深さは `memory.max_frames` (既定 16) とレジスタ領域で決まり、
超えるとエラーで停止します。PLC はメモリが固定なので、上限で止めるしか
ありません。

`def` は `OP_TCLASS` + `OP_METHOD` + `OP_DEF` で、**子 irep** を必要とします。
以前 `plc_codegen` はトップレベルの irep しか転送していなかったため、仕組みごと
未対応でした。入れたもの:

- 子 irep の転送とアドレス付け (IREP テーブル)
- 呼び出しフレーム (戻り先 PC・irep・レジスタ基点の退避)
- `OP_SSEND` (レシーバを書かない呼び出しはこちらになる)
- `OP_ENTER` (引数の数の検査)
- `OP_RETURN` のフレーム復帰
- メソッド表 (ホスト側で振った ID → irep)

工数の大半は**メモリ配置の作り直し**でした。バイトコード・定数プール・シンボル表
が irep ごとになり、生成コードで定数だったアドレスが VM 状態経由の間接参照に
変わりました。

## 4. ブロック — 実装済み

設計と実装の記録は [ブロックの計画](blocks.md) にあります。

`times` と `upto` にブロックを渡せます。入れ子・`break`・メソッドの中・
ブロックの中からのメソッド呼び出しが動きます。

```ruby
sum = 0
3.times do |i|
  sum = sum + i
end
```

`OP_SENDB` は呼び出しの仕組みでしかなく、**繰り返すのは `Integer#times` の側**
です。VM は再帰できないため、反復フレームに「今何回目か」と「上限」を持たせ、
ブロックの `OP_RETURN` で次の回に入り直します。

実機で確認済みです ([test_20_blocks.rb](../test/ruby_programs/test_20_blocks.rb))。
実行速度は 32,449 命令/秒、スキャン周期 1.54 ms です。

`loop` も入りました。`OP_SSENDB` (self への呼び出し) で `OP_SENDB` とは
別命令なので、self をレシーバ位置に置く前処理として足しています。
`yield` とブロック引数 (`&blk`) は未対応です。
`each` は Array と一緒に項目 5 で入りました。

## 5. ヒープ設計

設計メモは [ヒープの計画](heap.md) にあります。

Array / String / Hash に共通する置き場所です。固定数のスロットを持つプールを
用意し、**順に渡して返さない (GC 無し)、使い切ったらエラー**から始めます。

GC が難しいのは停止時間が読めないからですが、faRuby は**ヒープが固定長で根も
小さい**ため、必要になれば上限の計算できるマークスイープを後から足せます。
案 2 (エラー) と案 3 (回収) の間に Ruby としての意味の違いは無く、エラーが
出なくなるだけです。

逆アセンブルの結果、**既存の仕組みにかなり載る**ことが分かりました。
`OP_GETIDX` / `OP_SETIDX` は実装済みで枝を足すだけ、`length` / `<<` / `push`
は `OP_SEND`、`each` は `OP_SENDB` です。新しく要るのは `OP_ARRAY` /
`OP_ARRAY2` と実体の置き場所です。

リテラル・添字・`length` / `size` / `<<` / `push` / `each` が動きます。
実機で確認済みです
([test_21_arrays.rb](../test/ruby_programs/test_21_arrays.rb))。
実行速度は 32,711 命令/秒、スキャン周期 1.53 ms で、配列を入れる前から
変わっていません。

```ruby
a = [11, 22, 33]
$DM100 = a[1]     # 22
a[1] = 99

s = 0
a.each do |v|
  s = s + v
end
```

## 6. Array / String / Hash

3 つとも実装済みです。実体は共通の配列プールに置き、返さないので
使い切ったら止まります。詳細は [ヒープの設計](heap.md)、
[ハッシュの計画](hash.md)、[文字列の計画](string.md)。

String は**バイト列を変換しません**。ソースの文字コードがそのまま
デバイスへ出ます。種別を 1 ワード覚えておき、`length` と `[]` を
文字単位にしています。

```ruby
FARUBY_STR_FILL = 0x20    # 固定長の余りを空白で埋める

s = "あいう"
$DM100 = s                # 終端付き
$DM200T10 = s             # 10 バイトの固定長
$DM300 = s.length         # 3。バイト数の 9 ではない
$DM400 = s[0]             # "あ"
```

残るのは `*` (繰り返し) と `sub` / `upcase` などの加工、書式化です。
どれも新しいスロットを取るので、使う場面を見てから決めます。

## 独立した項目

| 項目 | 内容 |
|------|------|
| インスタンスを増やす | `memory.instances` を増やして EM20000-EM39999 を使い切る。1 インスタンス 4000 ワードなので 5 個まで。設定変更と再取り込みのみでコード変更は不要。**三菱は固定領域が ZR 8K しかないので 1 つだけ** |
| ~~Symbol~~ | 実装済み。値はホストが名前ごとに振った通し番号で、irep をまたいでも `==` で比べられる。Hash のキーに使う。詳細は [ハッシュの計画](hash.md) |
| ~~STEP_COUNT~~ | 実装済み。VM の最初のコミットから領域と `status` の表示はあったが、生成コードが更新しておらず常に 0 だった。`INC` で数えるようにした。費用は 1.5% |
| ~~固定領域を ZF へ~~ | 実装済み。実行中に変わらない領域を ZF のバンク 3 に移し、EM 側は 1 インスタンス 1000 ワードになった。当初は `FRSET` でバンクを選んで FM で指していたが、**バンクの先頭を基点にした相対指定**に変えた。詳細は [アーキテクチャ](architecture.md#固定領域はバンクの先頭からの相対で指す) |
| ~~実数のオーバーフロー検査~~ | **入れないと決めた。** 検出はできる (上位ワードの指数部を整数として見る) が、実数演算のたびに走る割に実数を使うプログラムが多くないため。利用者が避ける前提。測定結果と理由は [Ruby との違い](differences.md#検査を入れないと決めた) |
| ~~MELSEC 対応~~ | 実装済み。Q と iQ-R で 223 個ずつ実機一致。ST 1 本にまとまるのでラダーが要らない。実機で分かったことは [MELSEC 対応の計画](melsec.md) |
| mruby 4.0 対応 | オペコード番号の変更に追従。影響は `MRUBY_OPCODES` のみ |
| ~~PLC 起動時に先頭から実行する~~ | 実装済み。**走らせ直すかどうかは電源が切れたときの状態で決める** — 実行中だったら先頭から、停止・完了・エラーならそのまま止めておく。設定を足さなかったのは、これが利用者の意図とふつう一致するから。起動の合図は初回スキャンのみ ON の接点 (KV は CR2008、MELSEC は SM402。**4 機種すべて実機で確認済み** — 実行中のまま切ると走り出した回数が 1 増え、停止してから切ると増えない)。初期化するのは実行位置・状態・エラー・歩数・レジスタ・フレーム・配列プール・汎用グローバル変数で、**メソッド表とバイトコードは残す** (`load` し直さずに済む)。初期化はリセット要求と同じ処理を呼ぶ。**リセット要求に乗せる形は採らなかった** — 要求の枝は STATUS を停止にするので、「初期化のあと実行中へ戻す」ことを覚えておく語が VM 状態に 1 つ要る。初期化を 2 回展開する代わりに語を増やさずに済ませた (初期化はスキャンごとの経路ではないので費用は無視できる)。**電源が切れる前のリセット要求は落とす** — 残すと走らせ直した直後に止めてしまう。**三菱は可変領域が保持されていないと働かない** — 走り直す判断は `STATUS = 1` だが、`STATUS` も メソッド表も可変領域 (D) にあり、**三菱の D は既定で残らない**。保持していない Q で電源を入れ直したら `STATUS` も `NUM_IREPS` も 0、`$FARUBY_TICKS` は電源投入からの 127 秒だった (固定領域 ZR のバイトコードは残っていた)。キーエンスの EM は既定で残るので、4 機種で確認できていたのは三菱側が保持の対象になっていた間だけ。使い方は [README](../README.md#電源を入れ直したとき) |
| ~~時間を測る (tick カウンタ)~~ | 実装済み。`$FARUBY_TICKS` が数え始めてからのミリ秒 (**電源を入れ直しても 0 に戻らない**。EM / D に残る値から続ける。実機で確認)、`$FARUBY_CLOCK_10MS` / `_100MS` / `_1S` がクロックパルスそのもの。生成スクリプトが 10ms クロックの立ち上がりをスキャンごとに数える。**読み出しに枝を足していない** — ticks は普通のデバイス読み (32 ビット)、パルスは値スロットなので汎用グローバルの経路に載る。パルスを 1 / 0 の整数にしなかったのは Ruby では 0 も真だから。時刻源は機種が持つ (KV は CR2004/2005/2006、MELSEC は SM409/410/412。**4 機種すべて実機で確認済み**)。**値スロットはブロック先頭から 4 の倍数に置く** — 三菱は `VMSLOT[添字]` で指し、添字を「ワード数 / 4」で求めるためで、ずれると手前のスロットを読む (実機で起きた)。**スキャンタイムが 5ms を超えると取りこぼす。** 使い方は [README](../README.md#時間) |

**オブジェクト。** インスタンス変数 (`@`) は入りました

**固定メモリに何をどれだけ置くかの判断になります。** `TT_OBJECT` は今は
印だけで中身がありません。クラスごとのインスタンス変数の並び、インスタンスの
領域の上限、メソッド探索 (今はシンボル表のメソッド番号で直に振り分けている)
をどうするかが決まっていません。

**`@` の側は作り替えになります。** いまは「self が 1 つしか無い」ので名前
ごとに 1 枠ですが、`Foo.new` が 2 つできた時点で「どの self のものか」で
行き先が変わります。直すのは `OP_GETIV` / `OP_SETIV` の 2 命令と、シンボル
表の項目の意味だけです。

## 4. クラス変数と定数 — 実装済み

**まとめて入れました** (2026-11-26)。置き場を新しく作らずに済みました。

**どちらも汎用グローバルの値スロットです。** `$foo` と同じ場所なので、
VM に足したのは前処理 2 つ (`OP_GETCV` / `OP_SETCV` が `OP_GETGV` /
`OP_SETGV` の枝へ落ちる。`OP_GETIV` と同じ形) と、`OP_GETCONST` /
`OP_SETCONST` の種別による振り分けだけです。**領域は 1 ワードも増えません。**

| | 枠の鍵 | 行き先 |
|---|---|---|
| `$foo` / `@foo` (トップレベル) | 名前 | 汎用グローバル |
| `@@n` | **クラス番号 + 名前** | 汎用グローバル |
| `FOO` | 名前 | 汎用グローバル |
| `FARUBY_*` | — | VM 状態 (従来) |

**クラス変数の鍵にクラス番号を付けるのが要点です。** `@@n` の場所は名前では
なく「どのクラスの `@@n` か」で決まります。継承が無いので遡る探索は要らず、
**インスタンス変数より簡単**でした (あちらはオブジェクトごとに場所が違う)。

### 直した不具合 — 定数が黙ってクラス番号を返していた

`class_numbers` がクラス名を `OP_CLASS` と **`OP_GETCONST` の両方**から
集めていました。定数の読みも `OP_GETCONST` なので、**`FOO = 7` の `FOO` が
クラスとして登録され、`$DM0 = FOO` が 7 ではなく 1 を書いて完了していました**
(エラーも出ません)。クラス名は `OP_CLASS` だけから集めます — faRuby に
クラスを外から持ち込む経路は無く、必ず同じプログラムの `class X` で
定義されるためです。

**i8080 も同じ間違いをしていました。** 両方直しました。

### 止めるもの

### `C::LIMIT` を入れるとしたら

**VM 側は 2 行で済みます。** `OP_GETMCNST` (0x1F) / `OP_SETMCNST` (0x20) は
どちらも `BB` 形式で `OP_GETCONST` / `OP_SETCONST` と同じで、意味も
`R[a] = R[a]::symbols[b]` です。**シンボル表が正しい枠を指していれば、
既存の枝がそのまま正解を書きます** (`R[a]` の古い中身は捨ててよい)。
`@@` と同じ前処理の別名にできます。

```ruby
defs << OpcodeDef.new(0x1F, "R[a] = R[a]::定数 (OP_GETCONST の枝へ)", enters: 0x1D)
defs << OpcodeDef.new(0x20, "R[a]::定数 = R[a+1] (OP_SETCONST の枝へ)", enters: 0x1E)
```

**2 行でも生成物は変わります。** `rake vm_core` を回して 5 機種すべてに
書き込み直しが必要で、「ホスト側だけ」では終わりません。

**難しいのはツール側です。** 表は「irep ごと・名前ごとに 1 エントリ」なので、
同じ irep の `C::LIMIT` と `D::LIMIT` が同じエントリを共有します。
1 つのエントリに 2 つのアドレスは入りません。

```
irep 0  symbols=["C", "D", "LIMIT"]
  OP_GETCONST    a=4 b=0  => symbols[0]="C"      ← 受け手を R4 に載せる
  OP_GETMCNST    a=4 b=2  => symbols[2]="LIMIT"  ← C::LIMIT
  OP_GETCONST    a=4 b=1  => symbols[1]="D"
  OP_GETMCNST    a=4 b=2  => symbols[2]="LIMIT"  ← D::LIMIT も同じ枠
  OP_GETCONST    a=4 b=2  => symbols[2]="LIMIT"  ← 素の LIMIT も同じ枠
```

| | 中身 | 手間 | `C::LIMIT` と `D::LIMIT` |
|---|---|---|---|
| A. 別名で通す | 検査を外し `CONST_OPCODES` に 2 つ足すだけ | 小 | **同じ値になる** |
| B. 枠を分ける | 受け手のクラスを静的に決め、シンボル表にクラス付きのエントリを足して `operand b` を書き換える | 中 | 別の値 |

**B はツール側だけで閉じます。** バイトコードを PLC に書くのはホストなので
`operand b` は書き換えられます (`BB` なので 1 バイト、1 irep 255 シンボル
まで)。受け手のクラスは**直前に同じレジスタへ載せている `OP_GETCONST` /
`OP_CLASS`** から取れます (上の `a=4` が揃っているのがそれです)。枠の鍵は
`@@` と同じ「クラス番号 + 名前」でよく、**新しいメモリ領域は要りません。**
`k = C; k::LIMIT` のように受け手が静的に決まらない形は、今と同じく
コンパイル時に止めます。

**採るなら B です。** A だと `C::LIMIT` と書けるのに中身が混ざるので、
**今の「書けば止まる」より悪くなります** — 黙って別の値を返すのが、
この機能で直したばかりの不具合そのものだからです。

**急ぎません。** 今も `LIMIT` と書けば動き、止まるときはコンパイル時に
メッセージが出ます。名前が衝突して実際に困ってから入れるほうが
割に合います。

## ハッシュの each を i8080 にも — 実装済み

PLC には最初からありましたが、**i8080 にはフレーム種別が `EACH` (配列) まで
しかなく、`h.each` が「未対応のブロックメソッド」で止まっていました。**
`any?` を入れる前にここを揃えました。

**ツール側は 1 行も変えていません。** `each` は配列でもハッシュでも同じ
`METHOD_EACH` に落ちるので、VM が `TT_HASH` を受けるようにするだけです。

```ruby
h = {1 => 10, 2 => 20}
h.each do |k, v|   # ブロックには鍵と値の 2 つ
  ...
end
```

**見出しの +1 (count) がどちらも「反復の回数」でした。** 配列なら要素数、
ハッシュならペア数なので、上限の出し方を分ける必要がありません。違うのは
ブロックへ渡す値だけで、そこを `each_block_args` に出して
`sendb_each` (1 回目) と `advance_iteration` (2 回目以降) の両方から
呼んでいます。**以前は 1 回目の値を `sendb_each` に書き写していました。**

| | |
|---|---|
| `FRAME_KIND_HASH_EACH = 3` | **番号は PLC 版と揃えました** |
| `sendb_each` | `TT_ARRAY` / `TT_HASH` で種別を決める |
| `each_block_args` | 配列は `data + index*4`、ハッシュは `data + index*8` と その +4 |
| `advance_iteration` | `HASH_EACH` も `adv_each_load` へ |

**`vm_constants.a80` は生成物です。** 手で `EQU` を足しても
`rake i8080:build` の最初の工程 (`rake i8080:constants`) が上書きします。
足す場所は [tools/i8080_constants_gen.rb](../tools/i8080_constants_gen.rb) と
[tools/i8080_memory_layout.rb](../tools/i8080_memory_layout.rb) です。

確かめ方は test_i8080_vm.rb の 6 本 (鍵と値・空・1 ペア・容量いっぱいの
4 ペア・`break`・**配列の each を壊していないこと**) です。
最後の 1 本は、同じ枝を通るようにしたので入れてあります。

## any? / all? / none? — 実装済み

```ruby
if sensors.any? { |s| s > 100 }
  $MR100 = true
end
```

**新しいのはブロックの戻り値を見ることだけです。** ほかの反復はブロックの
値を捨てます — `each` はレシーバがそのまま呼び出しの値になり、`loop` は
`break` でしか終わりません。述語は毎回の値が答えになりうるので、
`OP_RETURN` で見ます。

**置き場は増えていません。** 答えは R[0] (レシーバの位置) に書きます。
**打ち切る瞬間はもう要素を取り出さない**ので、レシーバを潰してよいからです。
R[0] は呼んだ側の R[a] と同じ場所なので、それが呼び出しの値になります。

| 止める条件と返す値 | 真で止める | 止まったら | 尽きたら |
|---|---|---|---|
| `any?` | ○ | true | false |
| `all?` | × (偽で止める) | false | true |
| `none?` | ○ | false | true |

**尽きたときの値は止まったときの逆**です。3 つとも反対なので、片方だけを
`MemoryLayout::PREDICATE_RULES` に持たせ、生成コードもシミュレータも
そこから作っています。

### 足したもの

| | |
|---|---|
| メソッド番号 | **末尾に足しました** (PLC は 29-31)。番号を振り直さずに済むよう、受け手の区分の末尾を「配列・ハッシュ」にして受けます |
| フレーム種別 | `ANY` / `ALL` / `NONE` (6-8)。**`FRAME_KIND_ANY` 以上が「ブロックの値を見る反復」** |
| VM 状態 +59 | `PRED_STOP`。打ち切るかどうかの旗で、**1 命令の中でしか生きません** |

**渡す値は種別で分けていません。** `each` は配列とハッシュで別の種別を
持っていますが、述語は 3 つ × 2 型で 6 つになってしまいます。代わりに
**R[0] (レシーバ) の型タグ**で決めます — 反復の間 R[0] にレシーバが
残っているので、新しい場所は要りません。i8080 では**スロットの見出しの
種別** (`COL_TYPE_HASH`) を見ています。

### 踏んだところ

**空のコレクションで `any?` が真になりました。** 1 回も回らないときは
フレームを積まないので、答えを書く場所が別です。書かないとレシーバの配列が
そのまま返り、**Ruby では配列は真なので常に真**になります。`all?` と
`none?` は期待値が true なので、**書き忘れていても通ってしまいます** —
3 つまとめて入れたおかげで `any?` だけが落ち、気づけました。

**生成器が「別の枝でアドレスを載せた」と止めました。** ふつうの `return` も
同じ R[a] / R[0] を使うので、スロットの鍵を分ける必要がありました。

**鍵を分けても Z は分かれていませんでした。** これは実機 (KV-X500) で
14 値のうち 7 値がずれて分かりました。

```
Z2 := EM7:Z9 * 4 + EM32:Z9 + Z9;   ' ブロックの戻り値 R[a]
Z2 := 0 + EM32:Z9 + Z9;            ' R[0] が同じ Z2 を上書き
IF EM0:Z2 > 2 THEN                 ' レシーバの型タグを見ている
```

`slot_ref` の既定が **`[:reg, :a]` 以外すべて Z2** だからです。

```ruby
z ||= key == [:reg, :a] ? Z_PRIMARY : Z_SECONDARY
```

配列もハッシュもタグが 2 より大きいので**レシーバはいつも真**になり、
`any?` が常に真、`all?` も常に真 (偽で止まらない)、`none?` が常に偽でした。
直し方は Z1 を名指しするだけです (この時点で命令の取り出しは終わっていて、
フレームは Z3)。

**シミュレータと三菱では出ません。** どちらも添字でスロットを指すので
「どの Z に何が載っているか」という問題が存在しません。**クラスと定数のとき
の Z1 と同じ形**で、[実機で確認したこと (KV-5000)](#実機で確認したこと-kv-5000)
に書いた不具合の 2 回目です。

次に捕まえるテストを test_kvs_generator.rb に入れました。**隣り合う 2 行で
同じ Z を読まずに載せ直していたら落ちます。** 枝をまたぐ形 (IF と ELSE で
同じ Z に別の値) と、自分を読んで書き直す形 (`Z7 = Z7 / 2`) は正しいので
除いてあります。

**全角ダッシュが windows-31j に入りませんでした** (U+2014)。生成コードの
コメントに書いたためで、`test_生成物は_windows31j_に収まる` が捕まえました。

### 確かめ方

- [test/test_predicates.rb](../test/test_predicates.rb) 22 本
  (打ち切り・空・`0` は真・`nil` は偽・ハッシュ・入れ子・ほかの反復を
  壊していないこと)
- test_i8080_vm.rb に 15 本
- [test_47_predicates.rb](../test/ruby_programs/test_47_predicates.rb)
  14 値。**ブロックは 1 つの irep** で上限が 16 なので、入る数に限りが

### 実機で確認したこと

| 機種 | 値 | `test_47` |
|---|---|---|
| KV-5000 | **300** | 14 値 |
| KV-X500 | **298** | 14 値 |
| iQ-R | **298** | 14 値 (Z を分ける前の版) |
| ND8080 | — | **12 値** |

KV-5000 が 2 値多いのはタイマ・カウンタの試験がこの機種専用だからです。

**KV-X500 が 7 値ずれて不具合が出ました。** 上の「踏んだところ」の Z の
取り違えです。直した後に 298 値すべて一致しました。

**ND8080 は三項演算子で整数に落として読み戻します。** i8080 の真偽値は
値を持たない (型タグが `TT_TRUE` / `TT_FALSE` で値は 0) ので、そのままでは
真と偽を数で見分けられません。101-112 にすると**どちらの枝を通ったか**が
分かります。`$g4` だけは回数 (打ち切れば 30、回り切ると 60) です。

**ハッシュの `any?` が動くのは `h.each` を先に入れたからです。** フレーム
種別 `HASH_EACH` が無かった時点では、ハッシュをレシーバにすると
「未対応のブロックメソッド」で止まっていました。

## Array.new / Hash.new — 実装済み

```ruby
a = Array.new(8)              # nil が 8 個
b = Array.new(8, true)        # true が 8 個
c = Array.new(8) { |i| i * 2 }
h = Hash.new                  # {} と同じ
```

### 組み込みクラスという種別

**`Array` は利用者の定数として登録されていました。** `OP_CLASS` に
出てこない大文字の名前は定数になるので、値スロットが未代入 (nil) のまま
`.new` を呼び、レシーバの型違い (`ERROR=4`) で止まっていました。

| | |
|---|---|
| シンボル種別 | `SYMBOL_KIND_BUILTIN_CLASS` (PLC 8 / i8080 4)。**種別の空間はバックエンドごとに別です** |
| 型タグ | `TT_BUILTIN_CLASS` (14)。**`TT_CLASS` の隣**なので `new` の受け手の検査は 13-14 の 1 範囲 |
| メソッド表 | **行を持ちません。** `new` で作るものが違うだけで、ほかのメソッドは引けません |

### ブロック形

**`any?` で作った仕組みがそのまま使えました。** ブロックの値を見る反復で、
違うのは「答えにする」か「要素へ書く」かだけです。

- **渡すのは添字**です (`times` と同じ)。R[0] は配列なので、種別で
  見分けないとコレクションの枝に落ちて要素を渡してしまいます
- 配列は**フレームを積む前に確保して R[a] に置きます**。反復の間 R[0] が
  配列を指し、尽きればそれがそのまま呼び出しの値になります
- **先に nil で埋めます。** `break` で途中で抜けても、書いていない要素を
  値スロットとして読まれないようにするためです

### 容量

**PLC は 12 要素、i8080 は 8 要素**です (1 スロットに収まる数)。

**定数で超えると転送する前に止まります。** 実行時にも `ERROR=10` で
止まりますが、プログラムに数が書いてあれば送る前に分かります。見るのは
[tools/array_new_check.rb](../tools/array_new_check.rb) で、両方の
バックエンドが上限だけ差し替えて使います。**変数の大きさは見えません** —
見逃す側に倒しています (誤って止めないため)。

### Hash.new は引数を取れません

**`Hash.new(0)` の既定値を覚える場所がありません。** 見出しの空きは
PLC が 1 ワード、i8080 が 2 バイトで、値スロット (タグ + 32 ビット) は
入りません。16 ビット整数に限れば入りますが、「既定値が無い」と
「既定値が 0」を区別する 1 ビットも要ります。`Hash.new { |h, k| }` は
さらに別物で、鍵が無いたびにブロックを呼ぶ仕組みが要ります。

### 踏んだところ

**i8080 でブロックの 1 回目で打ち切られました。** `FRAME_KIND_ARRAY_FILL`
(9) が `FRAME_KIND_ANY` (6) 以上なので、述語の判定が**下限だけ見て
`none?` として扱った**ためです (真で打ち切り、R[0] に false を書く)。

```
スロット 0: 02 02 04 00 05 00 01 00   ← 1 回目は正しく書けている
R1        : 02 00 00 00              ← 配列が TT_FALSE に潰された
```

**PLC 生成器とシミュレータは無事でした。** 一方は種別ごとの等値比較を
並べ、もう一方は表で引くためです。**下限だけで判定していたのは i8080
だけ**で、上限を `NONE` で締めました。並びの約束も「ANY 以上」から
「ANY-NONE の範囲」に書き直してあります。

**`new` は唯一、ブロック付きでもなしでも呼べる組み込みです。** 両方の
一覧に入れないと、片方が呼べなくなります (最初に `BLOCK_METHODS` だけに
入れて、ブロック無しの `Array.new(8)` が `ERROR=3` になりました)。

**ブロックの位置を表の引数の数で数えていました。** `new` だけは表が 0 で
実際は 1 以上なので、大きさを載せた場所をブロックとして見ていました
(`ERROR=9`)。渡された数で数えます。

**`.nil?` は値として書けません。** 条件式の中なら mruby が畳みますが、
値にすると `OP_SEND :nil?` になり、組み込みに無いので止まります。

### 述語の枝を 1 つにまとめました (2026-11-27)

**同じ 180 行が 3 つ並んでいました。** `any?` / `all?` / `none?` は
メソッド番号ごとに枝を開いていましたが、中身は `blockless_predicate` が
Z5 を見て答えを分ける**同じコード**です。番号ごとに分ける意味がありません。

```
ELSE IF Z5 = 29 THEN    ' any?
  IF Z5 = 29 THEN ... END IF
  IF Z5 = 30 THEN ... END IF   ← 決して真にならない
  IF Z5 = 31 THEN ... END IF   ←
ELSE IF Z5 = 30 THEN    ' all? — 中身は同じ
ELSE IF Z5 = 31 THEN    ' none? — 同じ
```

**条件は `Z5 >= 29` の 1 つだけ**です。述語の番号は連続していて**しかも
末尾**なので、上限は要りません。その前提は `dispatch_branches` が見ていて、
崩れたら生成時に止まります (test_kvs_generator.rb にも 2 本)。

**「AND が無いから上限を書けない」と書いていました。間違いです。**
利用者の訂正 (2026-11-27): KV スクリプトで比較を `AND` でつなげられます。
**括弧が要るだけ**で、`AND` の優先度が比較より高いためです。

```
IF (Z5 >= 29) AND (Z5 <= 31) THEN     ' 書ける
```

元は 2026-09-06 の `numeric_flag_into` のコメントで、以後そのまま信じて
入れ子の IF で範囲を見ていました。**生成物に 50 か所あり、1 か所 2 行**
(内側の IF と END IF) 浮きます。レシーバの型検査は上下を別々の IF で
弾いているので、`OR` でまとめるとさらに縮みます。

**上限が要らないのは番号の並びのおかげ**で、ここは AND の話とは関係ありません。

恒等ブロックの道では `each` / `loop` / `new` の種別判定も 1 度も真に
ならないので、`identity` のときは出しません。

**KV-5000 の実機で 323 値すべて一致しました** (2026-11-27)。`vm_09_group5.kvs`

### 実機で確かめました (2026-11-27 / ND8080)

**「反応はすごくいい」** — 利用者の体感。1 周 1 秒だったものが、点滅
10 回で約 3.6 秒 (1 周 180 ms 前後) になりました。**走査はもう出てきません。**

内訳をクロック数で測ると、残っているのは描画そのものです。

| | 1 周 | 差 |
|---|---|---|
| 空のループ | 3.9 ms | — |
| + 点滅の描画 | 92.7 ms | **+88.8** |
| + `none?` | 96.4 ms | +3.7 |

**点滅 1 回は点灯と消灯の 2 周**なので、実機の 360 ms は
「描画 93 ms × 2 = 186 ms」と「`getkey 250` 回 ≈ 174 ms」に分かれます。
**描画が下限**で、点滅を速くしたいなら `BLINK_INTERVAL` を下げます
(下限の 186 ms までは詰められます)。

**`none?` は 3.7 ms。** 恒等ブロックで 8 要素を回してもほとんど値段が
付きません。

### 残っているのはインタプリタです

描画 1 回 71 ms の中身は、**走査ではなく VM の解釈**です。

```
1 描画 ≒ 95 VM 命令 × 約 0.75 ms (1 命令が約 1,500 クロック)
```

**走査をこれ以上削っても、ここから先はあまり出ません。** 速くするなら
命令 1 つの値段を下げる話になり、別の仕事です。

**例題は普通の Ruby のままです。** `a << "#"` と `puts a` を書き換えず、
**VM 側だけで 6.4 倍**にしました。

### 重い方は特定できていません

**実機での様子 (利用者)**

- **1 周がおよそ 1 秒。**
- **待ち回数を変えても、その分だけ時間が詰まらない。**

**待ち回数は原因ではありません。** `getkey 1000 → 250` で描画が 4 倍の
頻度になるから重いと見ましたが、**回数を戻しても反応は変わりませんでした。**

**この 2 つは走査を指しています。** 回数に比例しないのは、1 周の時間が
待ちではなく**確保ごとの固定の仕事**で決まっているからです。

**走査 1 回は実機で 51 ms** と測れました (下の「測った値」)。描画 1 回が
9 確保なので **460 ms**、点滅で 2 回描けば約 0.9 秒で、**報告された
1 周 1 秒と合います。**

**前の版との差も説明が付きました。** 「前の簡易版」はプログラムではなく
**走査の簡易版**のことで、軽かったのは 11-25 より前だからです。表示の
部分は前も今も同じ 9 スロットで、変わったのは 1 回の走査の値段です。

**残っている筋**

- **前の版 (`d79d345`) は軽かった**という証言。表示の部分は前の版と
  同じで、違うのは定数 2 つ・`Array.new` 2 行・`all?` の形だけ
- **VM が今日大きくなっています** (定数・述語・`Array.new`)。
  プログラムではなく VM 側が原因かもしれません

**ここから下は直す前の見立てです** (2026-11-27 に実施済み)。いちばん効くのは
走査 1 回の中身ではなく、**走査が走る回数**でした。

```
いま  : ARRAY_SP が上限に張り付き、確保 1 回ごとに全走査
あと  : 走査のあと空き枠を全部覚え、尽きるまでそこから配る
```

描画 1 回で 9 回確保するので、**いまは 1 回の描画で 9 回走査**します。
空き枠を覚えれば **7 回の描画につき 1 回**になり、走査の回数が 60 分の 1
ほどに落ちます。1 周 1 秒なら十数 ms の見込みです。**PLC も同じ設計**
(`EM39` が張り付く) なので、同じ直しが両方に効きます。

**先に実機で裏を取れます。** 描画から確保を外した版を回し、1 周が縮むかを
見ます (`setseg` は整数だけで確保しない)。**これは測るためだけの版で、
例題をこう書き換える話ではありません** (上のとおり)。

```ruby
SEG_ON  = 0x63
SEG_OFF = 0x5C
@states = Array.new(8, true)
loop do
  8.times { |i| setseg i, (@states[i] ? SEG_ON : SEG_OFF) }
end
```

**縮めば走査で確定**します。縮まなければ別の固定費を探します。
VM 側なら、今日足した分 (`vm_send.a80` のディスパッチが伸びた・
`vm_hash.a80` が増えた) を疑います。`getkey` と `puts` は鎖の手前に
あるので、鎖の長さでは説明が付きにくいところです。

### 測った値 — 走査 1 回が実機で 51 ms

**プールを使い切ると、以後の確保 1 回ごとに全走査が走ります。**
`ARRAY_SP` は上限に張り付いたままで、空いた 1 枠を使うだけだからです。

| 周 | 中身 | クロック | 実機 | 1 周あたり |
|---|---|---|---|---|
| 60 | 確保なし | 393,423 | 192 ms | 3.20 ms |
| 60 | 確保あり | 471,160 | 230 ms | 3.83 ms |
| 150 | 確保なし | 785,645 | 384 ms | 2.56 ms |
| **150** | **確保あり** | **10,187,886** | **4,975 ms** | **33.16 ms** |

```
走査が走った回数   ≒ 88 回 (150 - 62)
走査に使った時間   ≒ 4,496 ms
走査 1 回         ≒ 51 ms   ← 実機
描画 1 回 (9 確保) ≒ 460 ms
```

**「1 周およそ 1 秒」という実機の報告と桁が合います** (点滅で 2 回描けば
約 0.9 秒)。**PLC は 1 回 0.16–0.43 ms** なので、**120〜320 倍**です。
崖はプールの境目 (64) にぴったり出ます。

**測り方 — クロック数で測ります。** `r8080` の `cpu.state` が 8080 の
クロック数を数えているので (命令ごとに `@state += 7` など)、**2.048 MHz
で割れば実機の時間**になります。エミュレータの実時間と違い、そのまま
実機に移せます。

```ruby
board = FaRuby::I8080Board.new
board.load_hex(hex)
cpu = board.instance_variable_get(:@cpu)
board.run
cpu.state / 2_048_000.0      # 実機の秒
```

**VM 命令数 (`Steps`) では見えません** — 走査は確保という 1 命令の中で
走るためです。測る題材は次の 2 本で、周回数を 60 (走査なし) と 150
(走査あり) で比べます。

```ruby
$g1 = 0
150.times { |i| $g1 = i }            # 確保なし
150.times { |i| a = ""; $g1 = i }    # 確保あり
```

### 書き方で避けるのはやりません

`flip_flop.rb` の `print_digits` は **1 回で 9 スロット**使います
(`a = ""` とリテラル `"#"` / `"o"` / `" "` が 8 個)。7 回呼べばプールが
尽き、そこから先は 1 回の表示ごとに 9 回の全走査です。

`setseg(pos, pattern)` なら確保はゼロにできます (`DISPLAY_BASE + pos` へ
直接書く。整数だけ)。**が、これは採りません。**

**`a << "#"` と `puts a` は普通の Ruby で、それが書けることが faRuby の
値打ちです。** セグメントのビットを手で置くなら faRuby を使う意味が
ありません。**確保を避ける書き方に逃げるのは、直す対象をプログラム側へ
押し付けているだけです。**

**文字列をループで作って間に合うようにするのが VM 側の仕事**で、
そのための直しが下の「空いた枠を覚えて配る」です。

### ブロック無しの述語 — 実装済み (2026-11-27)

```ruby
@states.none?        # 真が 1 つも無いか
[1, nil].all?        # 偽が混ざっていないか
h.any?               # 空でないか
```

**`a.all?` は `a.all? { |x| x }` と同じです。** そこで**中身をそのまま
返すブロック (恒等ブロック) を渡したもの**として反復に入れます。
反復・フレーム・判定はブロック付きと同じ道で、**規則を 2 度書きません。**

| | |
|---|---|
| 恒等ブロック | `OP_RETURN R[1]` の **2 バイト** |
| 置き場 | **最後の irep**。PLC は `num_ireps - 1`、i8080 は `IDENTITY_IREP_STORE` (0x82FF) |
| 出すとき | **ブロック無しの述語を呼んでいるときだけ** (irep を 1 枠使う。`max_ireps` は 16) |

**反復は R[1] に要素を置くので、それを返せばブロックの値になります。**
`predicate_decision` がそのまま判定し、空のときの答えも既にある道で
決まります。

**ハッシュだけは反復しません。** Ruby はブロック無しのとき `[鍵, 値]` の
配列を見るので、**中身がどうであれ常に真**です (`any?` は空でないか、
`all?` は常に真、`none?` は空か)。鍵をそのまま渡すと
`{nil => 1}.all?` が偽になってしまいます。

**i8080 では `NUM_IREPS` が使えませんでした。** 欄はありますが**ホストが
書いていません** (PLC だけが使う欄でした)。VM 状態は起動時にゼロクリア
されるので HEX で書いても消えます。`INIT_METHOD_ID` と同じく、IREP 表の
末尾 (0x82FF) に置いて読みます。**0 は「恒等ブロックは無い」です。**

確かめ方は test_predicates.rb に 15 本、test_i8080_vm.rb に 13 本。

**ND8080 の実機で 17 値すべて一致しました** (2026-11-27、`STATUS=2`
`ERROR=0`)。ハッシュの 3 つ (組は常に真) とブロック付きとの併存も
含みます。**PLC 側は生成しただけで、実機でしか確かめられません。**

### 沈黙して止まっていた理由 — ラベルと定数の衝突 (2026-11-27 解決)

**`jmp vm_error` が 47 箇所すべて 3 番地へのジャンプでした。**

```
1D8B   D2 03 00    JNC vm_error     ← 飛び先 0x0003
```

`vm_constants.a80` に `VM_ERROR EQU 03h` があり、**asm80 は大文字小文字を
区別しない**ため、ラベル `vm_error` ではなく**定数の値 3 が飛び先**に
なっていました。アセンブルは通り、警告も出ません。

**つまり i8080 の VM は一度もエラーを報告していませんでした。** STATUS も
ERROR も書かないまま 0x0003 へ飛び、モニタへ戻ります。**未対応のメソッドを
踏むと「クラッシュ」に見えるのはこれです。** ブロック無しの `all?` で
見つけました (`STATUS=1` / `ERROR=0` のまま停止)。

**ラベルを `vm_fail` に改名して直しました** (`C3 03 00` → `C3 58 1D`)。
いまは `STATUS=3` / `ERROR=47` と出ます。

**飛び先が解決するかどうかの検査では捕まりません** — どちらも実在する
名前だからです。`test_i8080_labels.rb` に**ラベルと EQU の総当たり**を
足しました (427 × 183)。わざと `vm_running:` を作ると両方の場所を
行番号付きで名指しして落ちます。衝突はこの 1 件だけでした。

**見つけ方。** 板の `run` は PC が VM コード域の外に出たら止めるので、
**止まる 1 歩前の PC** を見れば飛び先の出どころが分かります。

```ruby
cpu = board.instance_variable_get(:@cpu)
# 1 命令ずつ回して PC を 30 個ぶん残す → .lst で引く
```

## 当面やらないこと

**例外 (`begin` / `rescue`)。** faRuby に例外機構はありません。0 除算などは
VM の `ERROR` に code を書いて停止します。PLC のプログラムで例外による制御が
必要になる場面は考えにくく、優先度は低いままです。
