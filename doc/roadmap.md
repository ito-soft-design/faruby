# ロードマップ

何を作るかと、なぜその順序なのかの記録です。

## 現在できること

- 整数 (32ビット符号付き) と実数 (単精度) の四則演算・比較
- `nil` / `true` / `false` と数値の区別。真偽判定は Ruby と同じ
- `if` / `while` による分岐と繰り返し
- グローバル変数と PLC デバイスの読み書き (アクセス幅の指定を含む)
- 複数プログラムの並行実行

実装済みの命令は 39 個です。詳細は [対応オペコード一覧](opcodes.md)。

## 依存関係

```
動的デバイスアクセス ── 独立。ヒープもメソッドも不要
組み込みメソッド ────── OP_SEND の限定実装。呼び出しフレーム不要
        │
メソッド定義・呼び出し ── 子 irep + 呼び出しフレーム
        │
      ブロック ──────── each / times / upto
        │
   ヒープ設計 ────── Array ── String ── Hash
```

## なぜ Array / String / Hash が先ではないのか

**リテラルと添字以外はすべてメソッド呼び出しだからです。** 逆アセンブルで
確認した結果です。

```
[1, 2, 3]      → OP_ARRAY2     専用命令
e[0]           → OP_GETIDX     専用命令
"hi"           → OP_STRING     専用命令
a.length       → OP_SEND       メソッド呼び出し
a.push(4)      → OP_SEND
a.each { }     → OP_BLOCK + OP_SENDB
```

Array を入れても、作って添字で読むだけで `length` も `push` も `each` も
動きません。メソッド呼び出しとヒープの両方が揃って初めて実用になります。

## 1. 動的デバイスアクセス — 実装済み

デバイスアドレスがコンパイル時に確定するため、実行時に計算したアドレスの
デバイスを読み書きできませんでした。センサ群やレシピデータをまとめて扱う、
PLC ではごく普通の処理ができない状態でした。

```ruby
i = 0
while i < 10
  $DM[600 + i] = 0
  i = i + 1
end
```

アドレスを外した `$DM` を「デバイス族」とし、添字を付けて実行時に決めます。
`OP_GETIDX` / `OP_SETIDX` は専用命令なのでメソッド呼び出しもヒープも不要でした。

決めた内容は [デバイス参照](architecture.md#デバイス参照-tt_device) にあります。

- 幅サフィックスは `$DML[i]`。単独の D デバイスが無いため一意に解析できる
- `$DM100[i]` は不可。`$DM100` はスカラとしても使われ、どちらも同じ
  `OP_GETGV` になるため VM 側で区別できない
- 範囲チェックあり。EM は範囲外を読むと 512 ワード周期で値が返るため
- 添字はデバイス番号。MR400 は 64。`plc_access` の `PlcDevice` と同じ規則

## 2. 組み込みメソッド

**次に取り組む項目です。**

`%` が動きません。`7 % 3` は `OP_SEND` にコンパイルされるためです。
`!=` も同じで、`a != b` は書けません (`if a == b` の else で代用します)。
`abs` / `to_i` / `to_f` / `floor` / `round` も同じです。利用者が最初に
つまずくのはおそらくここです。

受け手の型とメソッド名の組み合わせを限定して `OP_SEND` を実装します。
呼び出しフレームを作らず、その場で計算して返す方式です。工数は小さく、
効果は大きい部類です。

## 3. メソッド定義・呼び出し

`def` は `OP_TCLASS` + `OP_METHOD` + `OP_DEF` で、**子 irep** を必要とします。
現在 `plc_codegen` はトップレベルの irep しか転送していないため、仕組みごと
未対応です。

必要になるもの:

- 子 irep の転送とアドレス付け
- 呼び出しフレーム (戻り先 PC とレジスタ基点の退避)
- `OP_ENTER` (引数の受け取り)
- `OP_RETURN` のフレーム復帰
- メソッド表 (名前 → irep)

再帰の深さをどう制限するか、フレームをどこに積むかが設計上の論点です。
PLC はメモリ固定なので、深さの上限を決めてエラーにする形になります。

## 4. ブロック

`3.times do |i|` は `OP_BLOCK` + `OP_SENDB` です。メソッド呼び出しの上に
乗ります。`each` を使いたい以上、Array より先に必要です。

## 5. ヒープ設計

Array / String / Hash に共通する前提です。**最大の未知数は GC です。**

PLC はメモリが固定で、スキャンタイムに制約があります。mark-sweep や世代別は
停止時間が読めなくなるため、スキャンタイムを守れません。

候補:

- プログラム実行ごとにアリーナを捨てる (GC なし)
- 参照カウント (循環参照を諦める)
- 固定数のオブジェクトスロットを確保し、あふれたらエラー

faRuby のプログラムは短命でスキャンごとに区切られるため、アリーナ方式が
合う可能性があります。設計から始める項目です。

## 6. Array / String / Hash

ヒープとメソッド呼び出しが揃ってから着手します。Array がいちばん単純です。

String は文字コードの扱いを決める必要があります。PLC 側の文字列デバイスと
どうつなぐかも論点です。

## 独立した項目

| 項目 | 内容 |
|------|------|
| 4 インスタンス化 | `memory.instances` を 4 にして EM20000-EM39999 を使い切る。設定変更と再取り込みのみでコード変更は不要 |
| Symbol | 型タグは予約済み。値はシンボル表の索引。Hash のキーとして使うまでは用途が限られる |
| 実数のオーバーフロー検査 | 単精度の範囲を超えると PLC 内部で `Infinity` が生じ、以後の演算がエラーになる。範囲検査を入れるかどうか |
| MELSEC 対応 | [Ruby と PLC の違い](ruby_and_plc.md) の確認項目を実機で通すところから |
| mruby 4.0 対応 | オペコード番号の変更に追従。影響は `MRUBY_OPCODES` のみ |

## 当面やらないこと

**例外 (`begin` / `rescue`)。** faRuby に例外機構はありません。0 除算などは
VM の `ERROR` に code を書いて停止します。PLC のプログラムで例外による制御が
必要になる場面は考えにくく、優先度は低いままです。

**クラス定義。** `OP_CLASS` / `OP_EXEC` が必要です。メソッド定義より先に
必要になる場面が思い当たりません。
