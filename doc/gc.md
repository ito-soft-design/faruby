# コレクションプールの簡易 GC

[ヒープの計画](heap.md) の案 3 にあたる、マークスイープ GC の設計メモです。
i8080 バックエンドで実装・検証済みです。**PLC 版は設計を変えます** —
[PLC 版の設計](#plc-版の設計)が本体で、そこまでは i8080 の記録です。

## 背景

案 2 (順に取り、使い切ったらエラー) で動いていますが、ループの中で
文字列操作を繰り返すプログラムはスロットを使い切ります。

```ruby
# programs/test_builtin.rb — キー押下ごとにスクロール表示
loop do
  getkey
  a << b[i]          # GETIDX: 1 スロット (1 文字の一時文字列)
  a = a[1, 8]        # send_slice: 1 スロット (スライス結果)
  i = (i + 1) % b.length
  puts a
end
```

1 周あたり 2 スロットを消費し、8 周目 (i8080: 16 スロット) で枯渇します。
しかし実際に生きているのは `a` と `b` の 2 スロットだけです。

## アルゴリズム (i8080)

通常の確保で空きが無いとき**だけ**走ります。

```
GC を起動する条件:
  ARRAY_SP >= max_arrays  (PLC)
  col_sp   >= MAX_COL_SLOTS  (i8080)
```

### 1. ビットマップの初期化

16 スロットに対応する 16 ビットのビットマップをゼロクリアします。
ビット n が立っていれば「スロット n は使用中」です。

### 2. ルート走査 — レジスタ

レジスタファイルの全スロットを順に見ます。型タグが TT_STRING (7)、
TT_ARRAY (8)、TT_HASH (9) のいずれかなら、値のスロット番号に対応する
ビットを立てます。

| | i8080 | PLC |
|---|---|---|
| レジスタ数 | 64 | max_regs (既定 80) |
| 1 スロット | 4 バイト | 4 ワード |
| 型タグの位置 | +0 | +0 |
| 値の位置 | +2 (val_lo) | +1 (下位ワード) |

TT_HASH は PLC では鍵と値の**2 スロット**を使います。
値の下位ワードが鍵スロット番号、上位ワードが値スロット番号です。
両方をマークします。

### 3. ルート走査 — グローバル変数

汎用グローバル変数 (`$foo` のような一般変数) もレジスタと同じ形式なので
同じ手順で走査します。

| | i8080 | PLC |
|---|---|---|
| グローバル数 | 64 | max_globals (既定 300) |

デバイス参照 (`$DM` 等) は TT_DEVICE なのでスロットを持たず、スキップされます。

### 4. 空きスロットの探索

ビットマップのビットが立っていないスロットを探します。
見つかればそのスロットのアドレスを返します。
全ビットが立っていれば (全スロット使用中) エラーで停止します。

### 5. (i8080 では未実装) 入れ子の走査

現在の実装は**ルートからの直接参照**だけをマークします。
配列の要素が TT_ARRAY や TT_STRING を持つ場合 (入れ子)、
要素が参照するスロットはマークされません。

```ruby
a = [[1, 2], [3, 4]]   # 外側 1 スロット + 内側 2 スロット = 3 スロット
```

**i8080 のプログラムでは問題になりません。** 入れ子を使うプログラムが
コレクションプールを使い切ることは実用上ほぼ無いためです。

**PLC 版では最初から入れます。** オブジェクトのインスタンス変数と
ハッシュの要素がプールの中から他のスロットを指すので、辿らないと
生きている値を回収します ([ルートだけでは足りない](#1-ルートだけでは足りない))。

## i8080 での実装

### コード配置

`vm_hash.a80` のオーバーフロー領域 (org 0xB500) に `col_gc_alloc` として
配置しています。`col_alloc` から `col_sp >= MAX_COL_SLOTS` のときに
呼ばれます。

### ビットマップ

2 バイト (16 ビット) の `gc_bitmap` と、ビット位置を引くための
8 エントリのテーブル `gc_bit_table` を使います。

```
gc_bitmap:    db 0, 0           ; bitmap[0]=スロット0-7, bitmap[1]=スロット8-15
gc_bit_table: db 01h, 02h, 04h, 08h, 10h, 20h, 40h, 80h
```

### マーク手順

```asm
gc_mark_reg:
  ; HL = スロットの先頭 (+0: 型タグ)
  ; TT_STRING / TT_ARRAY / TT_HASH か判定
  ; val_lo - 1 = スロット番号
  ; gc_bitmap[slot / 8] |= gc_bit_table[slot % 8]
```

### 踏んだ不具合

1. **gc_check_bit が A を破壊する。** `ana m` でビットテストした結果が
   A に入るため、ループカウンタに A を使っていると壊れる。
   **B レジスタをカウンタにする**ことで解消

2. **col_slot_addr が A を破壊する。** スロット番号 × 32 の計算で A が
   変わるため、空きスロットを見つけた後にアドレスを求めると番号が消える。
   **push psw / pop psw** で退避・復帰

3. **col_slot_addr の 8 ビットオーバーフロー。** `add a` を 5 回で × 32 を
   計算していたが、スロット 8 以上で 8 ビットに収まらない (8 × 32 = 256)。
   スロット 8 がスロット 0 のアドレスに、スロット 9 がスロット 1 の
   アドレスにマッピングされ、**GC 以前の通常確保でも文字列が壊れていた**。
   **16 ビット (HL) の `dad h` × 5** に変更して解消

## PLC 版の設計

**そのままでは移せません。** 固定長スロットの順次確保・値スロットの形・
型タグの番号はどれも共通で、下の「適用可能な理由」はそのまま成り立ちますが、
PLC 版は i8080 版に無いものを 3 つ持っています。

| | i8080 | PLC |
|---|---|---|
| 到達範囲 | ルートからの直接参照だけ | **プールの中も辿る** |
| 印の置き場所 | 16 ビットのビットマップ | **スロットの見出し** |
| 確保 | `col_alloc` 1 本 | **9 箇所に展開されている** |

### 適用可能な理由

1. **データ構造が同じ。** 配列プールは i8080 のコレクションプールと同じ
   固定長スロットの順次確保方式 (案 2)

2. **型タグが共通。** `TT_STRING` / `TT_ARRAY` / `TT_HASH` の番号は
   `vm_constants.rb` で一元管理されており、PLC と i8080 で同じ

3. **停止時間が計算できる。** [ヒープの計画](heap.md) で整理した通り、
   走査対象が固定長なので上限が事前に分かる

### 1. ルートだけでは足りない

**i8080 の「ルートからの直接参照だけ」を PLC で使うと、エラーも出さずに
値が変わります。** PLC 版はプールの中から他のスロットを指すものを 3 つ
持っているためです。

| 指す側 | 指される側 | 例 |
|-------|----------|---|
| オブジェクト | 値スロット 12 個が**インスタンス変数** | `@name = "abc"` |
| ハッシュ | 鍵配列・値配列の**要素** | `{ a: "x" }` |
| 入れ子の配列 | 要素 | `a << b` (実行時にできる。静的には分からない) |

レジスタから届くオブジェクトはマークされますが、その `@name` の文字列は
マークされません。回収して次の確保で配り直すので、**生きている文字列が
別の値に変わります。** [ヒープの計画](heap.md)が案 1 を捨てたのと同じ理由
(「PLC で黙って違う答えを出すのは、止まるより悪い」) で、これは選べません。

**だから到達性まで辿ります。** 固定長・固定数なので、i8080 の段階 5
(未実装の入れ子走査) を最初から入れても上限は計算できます。

#### 参照の形は 4 つ

マークするときに型タグで分けます。**オブジェクトだけ値の作りが違います。**

| 型タグ | 値スロットの読み方 | スロット番号 |
|-------|-----------------|------------|
| `TT_STRING` (7) | +1 (下位ワード) | そのまま |
| `TT_ARRAY` (8) | +1 (下位ワード) | そのまま |
| `TT_HASH` (9) | +1 が鍵の配列、+2 が値の配列 | そのまま。**2 つとも** |
| `TT_OBJECT` (10) | +1 (下位ワード) | **- 1。0 は `main` でスロットを持たない** |

`TT_OBJECT` が +1 されているのは、トップレベルの self (`main`) を値 0 で
表すためです (`TT_CANONICAL_VALUE`)。**引き忘れると隣のスロットをマークし、
本当のスロットを回収します。** デバイス参照 (`TT_DEVICE`) はスロットを
持たないので飛ばします。

### 2. 印はビットマップではなくスロットの見出しに置く

**ビットマップは 1 ワードに入りません。** i8080 は 16 スロットですが PLC の
`max_arrays` は 32 で、置き場所も VM 状態の空きが +59 の 1 ワードだけです
([VM 状態領域](architecture.md))。

**スロットの見出しに 3 ワードの予備があります。** 見出しは 4 ワードで、
使っているのは +0 (配列なら要素数、オブジェクトならクラス番号) だけです。

| 見出し | いま | GC を入れた後 |
|-------|------|-------------|
| +0 | 要素数 / クラス番号 | そのまま |
| +1 | 予備 | **印。0 = 未到達、それ以外は到達したときの型タグ** |
| +2 | 予備 | **走査済みの印** |
| +3 | 予備 | そのまま |

こちらにする利点が 3 つあります。

- **ビットシフトが要りません。** 注意点に挙げていた「三菱はワード単位の
  操作が主」が消えます。読み書きはワードの代入と比較だけです
- **`max_arrays` を増やしても効きません。** ビットマップなら 32 を超えた
  時点でワードが足ります
- **印に型タグを入れれば、走査のときに中身の読み方が分かります。**
  スロット自身は自分の型を持っていません (+0 は要素数)。文字列の中身を
  値スロットとして読むと、バイト列を番号と見て無関係なスロットをマークします

**印は確保のときではなくマークのときに書きます。** 指している値スロットの
型タグをそのまま写すだけなので、確保側 9 箇所の中身に手を入れずに済みます。

### 3. 作業領域は予備から取る。VM 状態は動かさない

走査には 6 ワードほどの作業場所が要ります。使う Z レジスタは確保の場所ごとに
違うので、文字列の比較と同じようにデバイスのワードを使います (`FOR` の
ループ変数はデバイスでもよい)。

**VM 状態を 72 から広げると、後ろの領域が全部ずれます。** レジスタ・
メソッド表・汎用グローバル・配列プールのアドレスが動き、4 機種とも
配置の作り直しになります。

**配列プールの後ろの予備 328 ワードから取れば、何も動きません。** 末尾に
12 ワードの領域を足すだけで、予備が 316 ワードに減り、1 インスタンスは
4,000 ワードのままです。

| | いま | GC を入れた後 |
|---|---|---|
| 配列プール | +2008 - +3671 | そのまま |
| GC 作業領域 | — | **+3672 - +3683 (12 ワード)** |
| 予備 (端数調整) | +3672 - +3999 (328) | +3684 - +3999 (316) |

| 作業ワード | 用途 |
|-----------|------|
| +0 | 走査中のスロット番号 (`FOR` のループ変数) |
| +1 | **これから使うスロット。** 回収したものか `ARRAY_SP` か |
| +2 | 走査中の型タグ。見出しの印にそのまま入れる |
| +3 | 確保中のスロット + 1 (下記)。**まだ使っていない** |
| +4 | この周で印が増えたか (伝播を続けるかの判定) |
| +5, +6 | 借りた Z6・Z7 の退避先 |
| +7 | 何周目か |
| +8 | 走査中のスロットの見出しのアドレス |
| +9, +10 | 中身を見るときの要素番号とその上限 |
| +11 | 予備 |

**「これから使うスロット」を通すのが要でした。** 確保の 9 箇所はどれも
`ARRAY_SP` を直に読んでいたので、回収が返したスロットを使えません。
`alloc_check` がここに答えを置き、見出しの組み立ても値スロットへの
書き込みもここから読む形にしました。`ARRAY_SP` を進めるのは**順に渡した
ときだけ**です (`これから使うスロット = ARRAY_SP` の比較 1 回)。

### アルゴリズム

通常の確保で空きが無いとき**だけ**走ります。

```
(* 1. 印を消す *)
FOR slot := 0 TO max_arrays - 1 DO
  見出し(slot).MARK := 0;  見出し(slot).SCANNED := 0;
END_FOR;

(* 2. ルート — 全レジスタと全汎用グローバル。確保中のスロットも *)
FOR i := 0 TO max_regs + max_globals - 1 DO
  mark(値スロット i);           (* 型タグで 4 つに分ける *)
END_FOR;
mark_slot(GC_PINNED);

(* 3. 到達性の伝播。番号の大きい方から *)
REPEAT
  changed := 0;
  FOR slot := max_arrays - 1 DOWNTO 0 DO
    IF 見出し(slot).MARK <> 0 AND 見出し(slot).SCANNED = 0 THEN
      見出し(slot).SCANNED := 1;
      CASE 見出し(slot).MARK OF
        TT_ARRAY:  FOR e := 0 TO 要素数 - 1 DO mark(要素 e) END_FOR;
        TT_OBJECT: FOR e := 0 TO max_array_len - 1 DO mark(値スロット e) END_FOR;
        TT_STRING: (* 中身はバイト列。辿らない *)
      END_CASE;
    END_IF;
  END_FOR;
UNTIL changed = 0;

(* 4. 空きを探す *)
FOR slot := 0 TO max_arrays - 1 DO
  IF 見出し(slot).MARK = 0 THEN RETURN slot; END_IF;
END_FOR;
(* 全スロット到達 → エラー 10 *)
```

`mark` は「型タグを見て、スロット番号のある形なら見出しの印を立て、
立っていなければ `changed` を上げる」だけです。**付いている印は上から
書きません** — ハッシュ経由で配列として印を付けたものを別の型に
変えてしまうためです。

**`BREAK` は使いません。** 伝播が落ち着いた後の周は、`changed` を見て
中身を飛ばすだけにしています (比較 1 回)。`BREAK` は内側の `FOR` を
抜けるだけなので動きはしますが、**エラーで命令ループを抜ける `BREAK` と
見分けが付かなくなります** — 生成コードを見張るテストがそこを見ており、
実際に引っかかりました。空きスロットの探索も同じ理由で比較にしています。

**ハッシュの 2 スロットは `TT_ARRAY` として印を付けます。** 鍵配列・値配列は
中身が値スロットの並びで、ふつうの配列と同じ読み方だからです。片方だけ
回収すると壊れるので、`TT_HASH` を見たら必ず両方をマークします。

#### 走査の向きは昇順にした

**入れ子は内側が先に確保されるので、外側より小さい番号になります。**
`[[1,2],[3,4]]` は内側 2 本 (`OP_ARRAY2`) が先で、外側が後です。だから
大きい番号から走査すればふつうの入れ子が 1 周で収まる — という見込みで
設計しましたが、**実装では昇順にしました。**

降順の `FOR` が要るためです。`STEP -1` は実機で確かめていませんし、三菱の
`BY -1` と綴りも違います。番号を裏返す (`max - 1 - i`) には作業ワードが
もう 1 つ要ります。**昇順だとふつうの入れ子が 2 周になるだけ**で、最悪は
どちらも `max_arrays` 周です。1 周あたり 32 スロットの印の読みなので、
**実測してから考える**ことにしました。

### 確保を 1 本にまとめる — ここが前提作業

**i8080 は `col_alloc` 1 本ですが、PLC の生成器は確保のたびに展開しています。**
`ARRAY_SP >= max_arrays` の検査が 9 箇所にあり、使う Z レジスタも場所ごとに
違います。

| 生成器のメソッド | 何を確保するか |
|----------------|--------------|
| `new_array` | `OP_ARRAY` / `OP_ARRAY2` |
| `new_string` | `OP_STRING` |
| `add_strings` | `OP_STRCAT` / `+` |
| `new_hash` | `OP_HASH` (**2 スロット**) |
| `new_object` | `new` |
| `load_string_from_device` | `$DM100T6` の読み出し |
| `load_string_index` | `s[i]` (1 文字) |
| `slice_into` | `s[i, n]` / `a[i, n]` |
| `hash_column_into` | `keys` / `values` |

**先に 1 つの生成ヘルパーへ寄せます。** いま重複している上限検査もそこへ
集まります。GC を 9 箇所に展開するのではなく、ヘルパー 1 つが展開する形に
しておけば、後から中身を変えるのも 1 箇所です。

#### `new_hash` の「連続した 2 スロット」が崩れる

いまの `new_hash` は `ARRAY_SP` と `ARRAY_SP + 1` を**隣り合わせで**取り、
値配列の見出しを「鍵の見出し + スロットの大きさ」で求めています。

```
Z2 = ARRAY_SP * スロットの大きさ + プール先頭
Z3 = Z2 + スロットの大きさ        (* 値の配列はすぐ後ろ *)
```

**GC が返す空きスロットは連続しません。** 2 回確保して、それぞれの番号から
見出しを求める形に直します。値スロットの側は +1 に鍵、+2 に値のスロット番号を
別々に持っているので、**番号が離れていても読む側は変わりません。** 直すのは
確保と見出しの求め方だけです。

### 確保したスロットをレジスタへ書くまで守る

**`new_hash` は 1 つめを取った時点ではまだどのレジスタからも届きません。**
そこで 2 つめの確保が GC を起こすと、1 つめを未到達と見て配り直します。

`GC_PINNED` (作業領域 +4) に確保したスロット番号を入れ、マークのときに
必ず立てます。使い終わったら 0 に戻します。

**ふつうの確保では要りません。** 命令のオペランドはレジスタにあるので、
`add_strings` や `slice_into` の元の文字列は全レジスタ走査で届きます。
要るのは「1 つの命令で 2 つ以上確保する」ところだけです。

### レジスタは窓ではなく全部を見る

PLC のレジスタは窓方式で、フレームの深さによってベースが移動します。GC の
走査は **物理的な全スロット** (`reg_file_base` から `max_regs` 分) を対象に
します。窓の外に残っている外側のフレームの値も、戻ったときに使うので
生きています。i8080 も `REG_FILE_BASE` から `MAX_REGS` 分を走査しています。

### `ARRAY_SP` は動かさない

GC が返すのは「特定の空きスロット」で、`ARRAY_SP` は進めません。次の通常
確保は `ARRAY_SP` から続き、尽きていればまた GC を呼びます。
**`ARRAY_SP` を巻き戻すと、まだ生きているスロットを上書きします。**

### 停止時間

**走査する文の数で見積もります。実測はまだありません。** 速度の記録は
節目でしか取っていないので、入れたら測ります。

| | 文の数 |
|---|---|
| 印を消す | 32 |
| ルート走査 | 80 + 300 = 380 スロットの型タグ読み |
| 伝播 (1 周) | 32 スロット + 到達したものの要素 (最大 12) |
| 空き探索 | 最大 32 |
| **ふつう (伝播 1 周)** | **およそ 800 - 1,200** |
| **最悪 (伝播 32 周)** | **およそ 13,700** |

i8080 の見積もり (196 回) と桁が違うのは、**`max_globals` が 100 ではなく
300** で、伝播の周回が入るためです。

ふつうの側は VM 命令 30-60 個ぶんに当たり、`steps_per_cycle` が 50 なので
**GC 1 回でスキャンが 1 周期ぶん伸びる**見込みです。最悪の側はその 10 倍強で、
そのスキャンだけ数ミリ秒伸びます。**通常確保で尽きたときだけ走る**ので
毎スキャンの負荷にはなりませんが、**スキャンタイムの山は設備の要求次第で
問題になり得ます。** 先に実測してから、要るなら伝播に上限を置く話をします。

### 機種ごとの事情

| 機種 | GC を積むか | 理由 |
|------|-----------|------|
| KV-5000 / KV-X500 | 積む | 最大のスクリプトが上限の 25% で余裕がある |
| MELSEC iQ-R | 積む | `vm_02_body.st` が 255KB。**容量を確かめてから** |
| MELSEC Q | **積まない** | 配列・文字列・ハッシュを外しているのでプールを使わない |

**Q は機能を外しているので、GC のコードも落とします** (`features.rb`)。
クラスだけは有効なのでオブジェクトは作れますが、`new` の確保が尽きる
使い方は装置プログラムに無く、尽きたときは今までどおりエラー 10 で
止まります。

### 入れる順

どれも単体テストと生成コードの読みで確かめられます。

1. ~~**確保を 1 つの生成ヘルパーに寄せる**~~ — 済み。振る舞いを変えないので、
   生成物がバイト一致のままであることで確かめた (`alloc_check` /
   `alloc_check_pair` / `alloc_header_into` / `alloc_commit`)
2. ~~**GC 作業領域を配置に足す**~~ — 済み。予備から 12 ワード。既存の
   アドレスは動いていない
3. ~~**マークと空き探索**~~ — 済み
4. ~~**到達性の伝播**~~ — 済み。**3 と一緒に入れました** (下記)
5. **`new_hash` を 2 回確保に直す** と `GC_PINNED`
6. **4 機種ぶん再生成して実機** — VM を触るので 1 機種では足りない

#### 3 と 4 を分けられなかった

**段階 3 だけを入れると、黙って値が変わる窓が開きます。** ルートだけの
マークは配列の要素を辿らないので、`a << "x"` を繰り返す形で生きている
文字列を回収します。段階 3 を入れた時点でテストがそれを捉えました
(`a[0] == "ab"` が成り立たなくなる)。

止まるより悪いものを一度でもコミットに入れたくないので、伝播まで
まとめて入れました。**分けた単位は「確かめられるか」でしたが、
「途中の状態が安全か」も単位の条件でした。**

### 確かめ方

i8080 のテストと同じ形を PLC でも置きます。

```ruby
a = "abcdefgh"
10.times do
  a << "z"
  a = a[1, 8]
end
```

GC が無ければ 20 スロット以上要るので、32 スロットを超えるまで回数を
増やして確かめます。加えて PLC 版でしか起きない 5 つを見ます。

| 見るもの | 落ちていたら何が起きるか |
|---------|----------------------|
| オブジェクトの `@` が生き残る | `@name` が別の値に変わる |
| ハッシュの要素が生き残る | 鍵や値が変わる |
| 入れ子の配列が生き残る | 内側が変わる |
| `TT_OBJECT` の **-1** | 隣のスロットをマークし、本物を回収する |
| ハッシュの 2 スロットが離れていても動く | 値配列が読めない |

## テスト

i8080 では以下のテストで検証しています:

```ruby
def test_gc_string_loop
  # 10 回ループで毎回 slice + string literal → GC なしなら 20+ スロット必要
  src = <<~RUBY
    a = "abcdefgh"
    10.times do
      a << "z"
      a = a[1, 8]
    end
    b = a
  RUBY
  board = run_ruby(src)
  assert_equal :finished, board[:result]
  assert_equal "zzzzzzzz", board[:board].reg_string(2)
end
```

PLC に適用する際も、同様のパターン (ループ内で文字列操作を繰り返し、
16 スロットを超える確保が必要になるケース) でテストします。
