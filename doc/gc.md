# コレクションプールの簡易 GC

[ヒープの計画](heap.md) の案 3 にあたる、マークスイープ GC の設計メモです。
i8080 バックエンドで実装・検証済みで、PLC にも適用できます。

## 背景

案 2 (順に取り、使い切ったらエラー) で動いていますが、ループの中で
文字列操作を繰り返すプログラムはスロットを使い切ります。

```ruby
# programs/test_builtin.rb — キー押下ごとにスクロール表示
loop do
  getkey
  a << b[i]          # GETIDX: 1 スロット (1 文字の一時文字列)
  a = a[1, 8]        # send_slice: 1 スロット (スライス結果)
  i = (i + 1) % b.length
  puts a
end
```

1 周あたり 2 スロットを消費し、8 周目 (i8080: 16 スロット) で枯渇します。
しかし実際に生きているのは `a` と `b` の 2 スロットだけです。

## アルゴリズム

通常の確保で空きが無いとき**だけ**走ります。

```
GC を起動する条件:
  ARRAY_SP >= max_arrays  (PLC)
  col_sp   >= MAX_COL_SLOTS  (i8080)
```

### 1. ビットマップの初期化

16 スロットに対応する 16 ビットのビットマップをゼロクリアします。
ビット n が立っていれば「スロット n は使用中」です。

### 2. ルート走査 — レジスタ

レジスタファイルの全スロットを順に見ます。型タグが TT_STRING (7)、
TT_ARRAY (8)、TT_HASH (9) のいずれかなら、値のスロット番号に対応する
ビットを立てます。

| | i8080 | PLC |
|---|---|---|
| レジスタ数 | 64 | max_regs (既定 80) |
| 1 スロット | 4 バイト | 4 ワード |
| 型タグの位置 | +0 | +0 |
| 値の位置 | +2 (val_lo) | +1 (下位ワード) |

TT_HASH は PLC では鍵と値の**2 スロット**を使います。
値の下位ワードが鍵スロット番号、上位ワードが値スロット番号です。
両方をマークします。

### 3. ルート走査 — グローバル変数

汎用グローバル変数 (`$foo` のような一般変数) もレジスタと同じ形式なので
同じ手順で走査します。

| | i8080 | PLC |
|---|---|---|
| グローバル数 | 64 | max_globals (既定 100) |

デバイス参照 (`$DM` 等) は TT_DEVICE なのでスロットを持たず、スキップされます。

### 4. 空きスロットの探索

ビットマップのビットが立っていないスロットを探します。
見つかればそのスロットのアドレスを返します。
全ビットが立っていれば (全スロット使用中) エラーで停止します。

### 5. (未実装) 入れ子の走査

現在の実装は**ルートからの直接参照**だけをマークします。
配列の要素が TT_ARRAY や TT_STRING を持つ場合 (入れ子)、
要素が参照するスロットはマークされません。

```ruby
a = [[1, 2], [3, 4]]   # 外側 1 スロット + 内側 2 スロット = 3 スロット
```

**現在のプログラムでは問題になりません。** 入れ子を使うプログラムが
コレクションプールを使い切ることは実用上ほぼ無いためです。
必要になった場合は、マーク済みスロットの中身を再帰的に走査する
ステップを追加します。

## i8080 での実装

### コード配置

`vm_hash.a80` のオーバーフロー領域 (org 0xB500) に `col_gc_alloc` として
配置しています。`col_alloc` から `col_sp >= MAX_COL_SLOTS` のときに
呼ばれます。

### ビットマップ

2 バイト (16 ビット) の `gc_bitmap` と、ビット位置を引くための
8 エントリのテーブル `gc_bit_table` を使います。

```
gc_bitmap:    db 0, 0           ; bitmap[0]=スロット0-7, bitmap[1]=スロット8-15
gc_bit_table: db 01h, 02h, 04h, 08h, 10h, 20h, 40h, 80h
```

### マーク手順

```asm
gc_mark_reg:
  ; HL = スロットの先頭 (+0: 型タグ)
  ; TT_STRING / TT_ARRAY / TT_HASH か判定
  ; val_lo - 1 = スロット番号
  ; gc_bitmap[slot / 8] |= gc_bit_table[slot % 8]
```

### 踏んだ不具合

1. **gc_check_bit が A を破壊する。** `ana m` でビットテストした結果が
   A に入るため、ループカウンタに A を使っていると壊れる。
   **B レジスタをカウンタにする**ことで解消

2. **col_slot_addr が A を破壊する。** スロット番号 × 32 の計算で A が
   変わるため、空きスロットを見つけた後にアドレスを求めると番号が消える。
   **push psw / pop psw** で退避・復帰

3. **col_slot_addr の 8 ビットオーバーフロー。** `add a` を 5 回で × 32 を
   計算していたが、スロット 8 以上で 8 ビットに収まらない (8 × 32 = 256)。
   スロット 8 がスロット 0 のアドレスに、スロット 9 がスロット 1 の
   アドレスにマッピングされ、**GC 以前の通常確保でも文字列が壊れていた**。
   **16 ビット (HL) の `dad h` × 5** に変更して解消

## PLC への適用

### 適用可能な理由

1. **データ構造が同じ。** 配列プールは i8080 のコレクションプールと同じ
   固定長スロットの順次確保方式 (案 2)

2. **ルートが同じ構造。** レジスタと汎用グローバル変数が同じ値スロット
   形式で、走査対象が明確

3. **型タグが共通。** TT_STRING / TT_ARRAY / TT_HASH の番号は
   vm_constants.rb で一元管理されており、PLC と i8080 で同じ

4. **停止時間が計算できる。** [ヒープの計画](heap.md) で整理した通り、
   走査対象が固定長なので上限が事前に分かる

### 停止時間の見積もり

GC 1 回の走査量:

```
レジスタ:    80 スロット × (型タグ読み + 条件分岐 + ビット操作)
グローバル: 100 スロット × 同上
スロット探索: 16 スロット × ビットテスト
合計:       196 回の型タグ読み + 16 回のビットテスト
```

KV-5000 での 1 命令 ≈ 50μs とすると、各ステップが数命令として
**GC 1 回 ≈ 1-2ms** 程度。スキャンタイム 1.5ms の 1 周期分に
収まる見込みです。これは通常確保でプールが尽きたときだけ走るため、
毎スキャンの負荷にはなりません。

### 実装の指針

#### ビットマップ

PLC は 16 ビットワードなので、1 ワードで 16 スロットを表現できます。
VM 状態領域のスクラッチ (Z4-Z9 相当) に置きます。

#### マーク関数

```
(* 擬似コード *)
gc_bitmap := 0;

(* レジスタ走査 *)
FOR i := 0 TO max_regs - 1 DO
  tag := EM[reg_base + i * 4];
  IF tag = TT_STRING OR tag = TT_ARRAY THEN
    slot := EM[reg_base + i * 4 + 1];  (* 値の下位ワード *)
    gc_bitmap := gc_bitmap OR SHL(1, slot);
  ELSIF tag = TT_HASH THEN
    key_slot := EM[reg_base + i * 4 + 1];
    val_slot := EM[reg_base + i * 4 + 2];
    gc_bitmap := gc_bitmap OR SHL(1, key_slot) OR SHL(1, val_slot);
  END_IF;
END_FOR;

(* グローバル走査 — 同じ手順 *)

(* 空きスロット探索 *)
FOR slot := 0 TO max_arrays - 1 DO
  IF (gc_bitmap AND SHL(1, slot)) = 0 THEN
    (* このスロットは未使用 → 再利用 *)
    RETURN slot;
  END_IF;
END_FOR;
(* 全スロット使用中 → エラー *)
```

#### 生成コードへの組み込み

`kvs_generator.rb` で配列確保の箇所 (`ARRAY_SP >= max_arrays`) を変更:

```
現在:  ARRAY_SP >= max_arrays → エラーコード 10
変更後: ARRAY_SP >= max_arrays → GC サブルーチン呼び出し
        → 空きが見つかればそのスロットを使う
        → 見つからなければエラーコード 10
```

案 2 と案 3 の間に**意味の違いが無い**ため、既存のプログラムは
そのまま動きます。エラーで止まっていたケースが止まらなくなるだけです。

#### 注意点

1. **レジスタ窓のベース。** PLC のレジスタは窓方式で、フレームの深さに
   よってベースが移動します。GC 走査は**全レジスタ領域** (reg_base から
   nregs 分ではなく、物理的な全スロット) を対象にする必要があります。
   i8080 では REG_FILE_BASE から MAX_REGS 分を走査しています

2. **ビットシフト。** Keyence KV はビットシフト命令を持っていますが、
   三菱 Q はワード単位の操作が主です。ビットテストに工夫が要る
   可能性があります (テーブル参照で代替可能)

3. **ARRAY_SP のリセット不要。** GC で再利用するスロットは col_sp /
   ARRAY_SP とは独立です。GC が返すのは「特定のスロット」であり、
   ポインタは動かしません。次の通常確保は ARRAY_SP から続きます

4. **Hash の 2 スロット。** PLC の Hash は鍵配列と値配列で 2 スロットを
   使います。GC でどちらか一方だけ回収すると壊れるため、
   マーク時に必ず両方をマークします

## テスト

i8080 では以下のテストで検証しています:

```ruby
def test_gc_string_loop
  # 10 回ループで毎回 slice + string literal → GC なしなら 20+ スロット必要
  src = <<~RUBY
    a = "abcdefgh"
    10.times do
      a << "z"
      a = a[1, 8]
    end
    b = a
  RUBY
  board = run_ruby(src)
  assert_equal :finished, board[:result]
  assert_equal "zzzzzzzz", board[:board].reg_string(2)
end
```

PLC に適用する際も、同様のパターン (ループ内で文字列操作を繰り返し、
16 スロットを超える確保が必要になるケース) でテストします。
