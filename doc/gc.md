# コレクションプールの簡易 GC

[ヒープの計画](heap.md) の案 3 にあたる、マークスイープ GC の設計メモです。
i8080 バックエンドで実装・検証済みです。**PLC 版は設計を変えます** —
[PLC 版の設計](#plc-版の設計)が本体で、そこまでは i8080 の記録です。

## 背景

案 2 (順に取り、使い切ったらエラー) で動いていますが、ループの中で
文字列操作を繰り返すプログラムはスロットを使い切ります。

```ruby
# programs/test_builtin.rb — キー押下ごとにスクロール表示
loop do
  getkey
  a << b[i]          # GETIDX: 1 スロット (1 文字の一時文字列)
  a = a[1, 8]        # send_slice: 1 スロット (スライス結果)
  i = (i + 1) % b.length
  puts a
end
```

1 周あたり 2 スロットを消費し、8 周目 (i8080: 16 スロット) で枯渇します。
しかし実際に生きているのは `a` と `b` の 2 スロットだけです。

## アルゴリズム (i8080)

通常の確保で空きが無いとき**だけ**走ります。

```
GC を起動する条件:
  ARRAY_SP >= max_arrays  (PLC)
  col_sp   >= MAX_COL_SLOTS  (i8080)
```

### 1. ビットマップの初期化

16 スロットに対応する 16 ビットのビットマップをゼロクリアします。
ビット n が立っていれば「スロット n は使用中」です。

### 2. ルート走査 — レジスタ

レジスタファイルの全スロットを順に見ます。型タグが TT_STRING (7)、
TT_ARRAY (8)、TT_HASH (9) のいずれかなら、値のスロット番号に対応する
ビットを立てます。

| | i8080 | PLC |
|---|---|---|
| レジスタ数 | 64 | max_regs (既定 80) |
| 1 スロット | 4 バイト | 4 ワード |
| 型タグの位置 | +0 | +0 |
| 値の位置 | +2 (val_lo) | +1 (下位ワード) |

TT_HASH は PLC では鍵と値の**2 スロット**を使います。
値の下位ワードが鍵スロット番号、上位ワードが値スロット番号です。
両方をマークします。

### 3. ルート走査 — グローバル変数

汎用グローバル変数 (`$foo` のような一般変数) もレジスタと同じ形式なので
同じ手順で走査します。

| | i8080 | PLC |
|---|---|---|
| グローバル数 | 64 | max_globals (既定 300) |

デバイス参照 (`$DM` 等) は TT_DEVICE なのでスロットを持たず、スキップされます。

### 4. 空きスロットの探索

ビットマップのビットが立っていないスロットを探します。
見つかればそのスロットのアドレスを返します。
全ビットが立っていれば (全スロット使用中) エラーで停止します。

### 5. 入れ子の走査 (両方に入りました)

現在の実装は**ルートからの直接参照**だけをマークします。
配列の要素が TT_ARRAY や TT_STRING を持つ場合 (入れ子)、
要素が参照するスロットはマークされません。

```ruby
a = [[1, 2], [3, 4]]   # 外側 1 スロット + 内側 2 スロット = 3 スロット
```

**この判断は取り消し、i8080 にも入れました。** 書いた時点では「入れ子を
使うプログラムがプールを使い切ることはほぼ無い」と見ていましたが、
**文字列を 1 つ持った配列やハッシュ (`["ab"]` / `{ 1 => "ab" }`) も同じ形**
で、そちらは珍しくありません。オブジェクトのインスタンス変数も漏れて
いました。**エミュレータで `a[0]` が `"keep"` から `"xy"` に化けるのを
確認してから**直しました ([i8080 へ移した記録](#i8080-へ戻すときの助言))。

**PLC 版では最初から入れます。** オブジェクトのインスタンス変数と
ハッシュの要素がプールの中から他のスロットを指すので、辿らないと
生きている値を回収します ([ルートだけでは足りない](#1-ルートだけでは足りない))。

## i8080 での実装

### コード配置

`vm_hash.a80` のオーバーフロー領域 (org 0xB500) に `col_gc_alloc` として
配置しています。`col_alloc` から `col_sp >= MAX_COL_SLOTS` のときに
呼ばれます。

### ビットマップ

2 バイト (16 ビット) の `gc_bitmap` と、ビット位置を引くための
8 エントリのテーブル `gc_bit_table` を使います。

```
gc_bitmap:    db 0, 0           ; bitmap[0]=スロット0-7, bitmap[1]=スロット8-15
gc_bit_table: db 01h, 02h, 04h, 08h, 10h, 20h, 40h, 80h
```

### マーク手順

```asm
gc_mark_reg:
  ; HL = スロットの先頭 (+0: 型タグ)
  ; TT_STRING / TT_ARRAY / TT_HASH か判定
  ; val_lo - 1 = スロット番号
  ; gc_bitmap[slot / 8] |= gc_bit_table[slot % 8]
```

### 踏んだ不具合

1. **gc_check_bit が A を破壊する。** `ana m` でビットテストした結果が
   A に入るため、ループカウンタに A を使っていると壊れる。
   **B レジスタをカウンタにする**ことで解消

2. **col_slot_addr が A を破壊する。** スロット番号 × 32 の計算で A が
   変わるため、空きスロットを見つけた後にアドレスを求めると番号が消える。
   **push psw / pop psw** で退避・復帰

3. **col_slot_addr の 8 ビットオーバーフロー。** `add a` を 5 回で × 32 を
   計算していたが、スロット 8 以上で 8 ビットに収まらない (8 × 32 = 256)。
   スロット 8 がスロット 0 のアドレスに、スロット 9 がスロット 1 の
   アドレスにマッピングされ、**GC 以前の通常確保でも文字列が壊れていた**。
   **16 ビット (HL) の `dad h` × 5** に変更して解消

## PLC 版の設計

**そのままでは移せません。** 固定長スロットの順次確保・値スロットの形・
型タグの番号はどれも共通で、下の「適用可能な理由」はそのまま成り立ちますが、
PLC 版は i8080 版に無いものを 3 つ持っています。

| | i8080 | PLC |
|---|---|---|
| 到達範囲 | ルートからの直接参照だけ | **プールの中も辿る** |
| 印の置き場所 | 16 ビットのビットマップ | **スロットの見出し** |
| 確保 | `col_alloc` 1 本 | **9 箇所に展開されている** |

### 適用可能な理由

1. **データ構造が同じ。** 配列プールは i8080 のコレクションプールと同じ
   固定長スロットの順次確保方式 (案 2)

2. **型タグが共通。** `TT_STRING` / `TT_ARRAY` / `TT_HASH` の番号は
   `vm_constants.rb` で一元管理されており、PLC と i8080 で同じ

3. **停止時間が計算できる。** [ヒープの計画](heap.md) で整理した通り、
   走査対象が固定長なので上限が事前に分かる

### 1. ルートだけでは足りない

**i8080 の「ルートからの直接参照だけ」を PLC で使うと、エラーも出さずに
値が変わります。** PLC 版はプールの中から他のスロットを指すものを 3 つ
持っているためです。

| 指す側 | 指される側 | 例 |
|-------|----------|---|
| オブジェクト | 値スロット 12 個が**インスタンス変数** | `@name = "abc"` |
| ハッシュ | 鍵配列・値配列の**要素** | `{ a: "x" }` |
| 入れ子の配列 | 要素 | `a << b` (実行時にできる。静的には分からない) |

レジスタから届くオブジェクトはマークされますが、その `@name` の文字列は
マークされません。回収して次の確保で配り直すので、**生きている文字列が
別の値に変わります。** [ヒープの計画](heap.md)が案 1 を捨てたのと同じ理由
(「PLC で黙って違う答えを出すのは、止まるより悪い」) で、これは選べません。

**だから到達性まで辿ります。** 固定長・固定数なので、i8080 の段階 5
(未実装の入れ子走査) を最初から入れても上限は計算できます。

#### 参照の形は 4 つ

マークするときに型タグで分けます。**オブジェクトだけ値の作りが違います。**

| 型タグ | 値スロットの読み方 | スロット番号 |
|-------|-----------------|------------|
| `TT_STRING` (7) | +1 (下位ワード) | そのまま |
| `TT_ARRAY` (8) | +1 (下位ワード) | そのまま |
| `TT_HASH` (9) | +1 が鍵の配列、+2 が値の配列 | そのまま。**2 つとも** |
| `TT_OBJECT` (10) | +1 (下位ワード) | **- 1。0 は `main` でスロットを持たない** |

`TT_OBJECT` が +1 されているのは、トップレベルの self (`main`) を値 0 で
表すためです (`TT_CANONICAL_VALUE`)。**引き忘れると隣のスロットをマークし、
本当のスロットを回収します。** デバイス参照 (`TT_DEVICE`) はスロットを
持たないので飛ばします。

### 2. 印はビットマップではなくスロットの見出しに置く

**ビットマップは 1 ワードに入りません。** i8080 は 16 スロットですが PLC の
`max_arrays` は 32 で、置き場所も VM 状態の空きが +59 の 1 ワードだけです
([VM 状態領域](architecture.md))。

**スロットの見出しに 3 ワードの予備があります。** 見出しは 4 ワードで、
使っているのは +0 (配列なら要素数、オブジェクトならクラス番号) だけです。

| 見出し | いま | GC を入れた後 |
|-------|------|-------------|
| +0 | 要素数 / クラス番号 | そのまま |
| +1 | 予備 | **印。0 = 未到達、それ以外は到達したときの型タグ** |
| +2 | 予備 | **走査済みの印** |
| +3 | 予備 | そのまま |

こちらにする利点が 3 つあります。

- **ビットシフトが要りません。** 注意点に挙げていた「三菱はワード単位の
  操作が主」が消えます。読み書きはワードの代入と比較だけです
- **`max_arrays` を増やしても効きません。** ビットマップなら 32 を超えた
  時点でワードが足ります
- **印に型タグを入れれば、走査のときに中身の読み方が分かります。**
  スロット自身は自分の型を持っていません (+0 は要素数)。文字列の中身を
  値スロットとして読むと、バイト列を番号と見て無関係なスロットをマークします

**印は確保のときではなくマークのときに書きます。** 指している値スロットの
型タグをそのまま写すだけなので、確保側 9 箇所の中身に手を入れずに済みます。

### 3. 作業領域は予備から取る。VM 状態は動かさない

走査には 6 ワードほどの作業場所が要ります。使う Z レジスタは確保の場所ごとに
違うので、文字列の比較と同じようにデバイスのワードを使います (`FOR` の
ループ変数はデバイスでもよい)。

**VM 状態を 72 から広げると、後ろの領域が全部ずれます。** レジスタ・
メソッド表・汎用グローバル・配列プールのアドレスが動き、4 機種とも
配置の作り直しになります。

**配列プールの後ろの予備 328 ワードから取れば、何も動きません。** 末尾に
12 ワードの領域を足すだけで、予備が 316 ワードに減り、1 インスタンスは
4,000 ワードのままです。

| | いま | GC を入れた後 |
|---|---|---|
| 配列プール | +2008 - +3671 | そのまま |
| GC 作業領域 | — | **+3672 - +3683 (12 ワード)** |
| 予備 (端数調整) | +3672 - +3999 (328) | +3684 - +3999 (316) |

| 作業ワード | 用途 |
|-----------|------|
| +0 | 走査中のスロット番号 (`FOR` のループ変数) |
| +1 | **これから使うスロット。** 回収したものか `ARRAY_SP` か |
| +2 | 走査中の型タグ。見出しの印にそのまま入れる |
| +3 | 確保中のスロット + 1 (下記)。ハッシュが使う |
| +4 | この周で印が増えたか (伝播を続けるかの判定) |
| +5, +6 | 借りた Z6・Z7 の退避先 |
| +7 | 何周目か |
| +8 | 走査中のスロットの見出しのアドレス |
| +9, +10 | 中身を見るときの要素番号とその上限 |
| +11 | 予備 |

**「これから使うスロット」を通すのが要でした。** 確保の 9 箇所はどれも
`ARRAY_SP` を直に読んでいたので、回収が返したスロットを使えません。
`alloc_check` がここに答えを置き、見出しの組み立ても値スロットへの
書き込みもここから読む形にしました。`ARRAY_SP` を進めるのは**順に渡した
ときだけ**です (`これから使うスロット = ARRAY_SP` の比較 1 回)。

### アルゴリズム

**空き表を配り切ったときだけ**走ります。走査のあと、印の付かなかった枠を
順に配ります ([空き表](#空き表にしました-2026-11-28))。

```
(* 1. 印を消す *)
FOR slot := 0 TO max_arrays - 1 DO
  見出し(slot).MARK := 0;  見出し(slot).SCANNED := 0;
END_FOR;

(* 2. ルート — 全レジスタと全汎用グローバル。確保中のスロットも *)
FOR i := 0 TO max_regs + max_globals - 1 DO
  mark(値スロット i);           (* 型タグで 4 つに分ける *)
END_FOR;
mark_slot(GC_PINNED);

(* 3. 到達性の伝播。番号の大きい方から *)
REPEAT
  changed := 0;
  FOR slot := max_arrays - 1 DOWNTO 0 DO
    IF 見出し(slot).MARK <> 0 AND 見出し(slot).SCANNED = 0 THEN
      見出し(slot).SCANNED := 1;
      CASE 見出し(slot).MARK OF
        TT_ARRAY:  FOR e := 0 TO 要素数 - 1 DO mark(要素 e) END_FOR;
        TT_OBJECT: FOR e := 0 TO max_array_len - 1 DO mark(値スロット e) END_FOR;
        TT_STRING: (* 中身はバイト列。辿らない *)
      END_CASE;
    END_IF;
  END_FOR;
UNTIL changed = 0;

(* 4. 印はここから空き表になる。しおりを先頭へ *)
GC_CURSOR := 0;
```

確保の側は走査を呼びません。**空き表から配り、尽きたときだけ呼びます。**

```
(* 確保 — ARRAY_SP が上限に届いた後 *)
take_free;                      (* しおりから、印の無い枠を 1 つ *)
IF GC_FOUND >= max_arrays THEN  (* 空き表が尽きた *)
  走査 (1-4);
  take_free;
  IF GC_FOUND >= max_arrays THEN エラー 10 END_IF;  (* 全スロット到達 *)
END_IF;

(* take_free *)
GC_FOUND := max_arrays;
IF GC_CURSOR < max_arrays THEN
  FOR slot := GC_CURSOR TO max_arrays - 1 DO
    IF GC_FOUND >= max_arrays AND 見出し(slot).MARK = 0 THEN
      GC_FOUND := slot;
    END_IF;
  END_FOR;
END_IF;
GC_CURSOR := GC_FOUND + 1;      (* 見つからなければ上限の先 = 空き表は空 *)
```

`mark` は「型タグを見て、スロット番号のある形なら見出しの印を立て、
立っていなければ `changed` を上げる」だけです。**付いている印は上から
書きません** — ハッシュ経由で配列として印を付けたものを別の型に
変えてしまうためです。

**`BREAK` は使いません。** 伝播が落ち着いた後の周は、`changed` を見て
中身を飛ばすだけにしています (比較 1 回)。`BREAK` は内側の `FOR` を
抜けるだけなので動きはしますが、**エラーで命令ループを抜ける `BREAK` と
見分けが付かなくなります** — 生成コードを見張るテストがそこを見ており、
実際に引っかかりました。空きスロットの探索も同じ理由で比較にしています。

**ハッシュの 2 スロットは `TT_ARRAY` として印を付けます。** 鍵配列・値配列は
中身が値スロットの並びで、ふつうの配列と同じ読み方だからです。片方だけ
回収すると壊れるので、`TT_HASH` を見たら必ず両方をマークします。

#### 走査の向きは昇順にした

**入れ子は内側が先に確保されるので、外側より小さい番号になります。**
`[[1,2],[3,4]]` は内側 2 本 (`OP_ARRAY2`) が先で、外側が後です。だから
大きい番号から走査すればふつうの入れ子が 1 周で収まる — という見込みで
設計しましたが、**実装では昇順にしました。**

降順の `FOR` が要るためです。`STEP -1` は実機で確かめていませんし、三菱の
`BY -1` と綴りも違います。番号を裏返す (`max - 1 - i`) には作業ワードが
もう 1 つ要ります。**昇順だとふつうの入れ子が 2 周になるだけ**で、最悪は
どちらも `max_arrays` 周です。1 周あたり 32 スロットの印の読みなので、
**実測してから考える**ことにしました。

### 確保を 1 本にまとめる — ここが前提作業

**i8080 は `col_alloc` 1 本ですが、PLC の生成器は確保のたびに展開しています。**
`ARRAY_SP >= max_arrays` の検査が 9 箇所にあり、使う Z レジスタも場所ごとに
違います。

| 生成器のメソッド | 何を確保するか |
|----------------|--------------|
| `new_array` | `OP_ARRAY` / `OP_ARRAY2` |
| `new_string` | `OP_STRING` |
| `add_strings` | `OP_STRCAT` / `+` |
| `new_hash` | `OP_HASH` (**2 スロット**) |
| `new_object` | `new` |
| `load_string_from_device` | `$DM100T6` の読み出し |
| `load_string_index` | `s[i]` (1 文字) |
| `slice_into` | `s[i, n]` / `a[i, n]` |
| `hash_column_into` | `keys` / `values` |

**先に 1 つの生成ヘルパーへ寄せます。** いま重複している上限検査もそこへ
集まります。GC を 9 箇所に展開するのではなく、ヘルパー 1 つが展開する形に
しておけば、後から中身を変えるのも 1 箇所です。

#### `new_hash` の「連続した 2 スロット」が崩れる

いまの `new_hash` は `ARRAY_SP` と `ARRAY_SP + 1` を**隣り合わせで**取り、
値配列の見出しを「鍵の見出し + スロットの大きさ」で求めています。

```
Z2 = ARRAY_SP * スロットの大きさ + プール先頭
Z3 = Z2 + スロットの大きさ        (* 値の配列はすぐ後ろ *)
```

**GC が返す空きスロットは連続しません。** 2 回確保して、それぞれの番号から
見出しを求める形に直します。値スロットの側は +1 に鍵、+2 に値のスロット番号を
別々に持っているので、**番号が離れていても読む側は変わりません。** 直すのは
確保と見出しの求め方だけです。

### 確保したスロットをレジスタへ書くまで守る

**`new_hash` は 1 つめを取った時点ではまだどのレジスタからも届きません。**
そこで 2 つめの確保が GC を起こすと、1 つめを未到達と見て配り直します。

`GC_PINNED` (作業領域 +4) に確保したスロット番号を入れ、マークのときに
必ず立てます。使い終わったら 0 に戻します。

**ふつうの確保では要りません。** 命令のオペランドはレジスタにあるので、
`add_strings` や `slice_into` の元の文字列は全レジスタ走査で届きます。
要るのは「1 つの命令で 2 つ以上確保する」ところだけです。

### レジスタは窓ではなく全部を見る

PLC のレジスタは窓方式で、フレームの深さによってベースが移動します。GC の
走査は **物理的な全スロット** (`reg_file_base` から `max_regs` 分) を対象に
します。窓の外に残っている外側のフレームの値も、戻ったときに使うので
生きています。i8080 も `REG_FILE_BASE` から `MAX_REGS` 分を走査しています。

### `ARRAY_SP` は動かさない

GC が返すのは「特定の空きスロット」で、`ARRAY_SP` は進めません。次の確保は
空き表から続き、空き表が尽きていればまた GC を呼びます。
**`ARRAY_SP` を巻き戻すと、まだ生きているスロットを上書きします。**

### 停止時間

**走査する文の数で見積もります。実測はまだありません。** 速度の記録は
節目でしか取っていないので、入れたら測ります。

| | 文の数 |
|---|---|
| 印を消す | 32 |
| ルート走査 | 80 + 300 = 380 スロットの型タグ読み |
| 伝播 (1 周) | 32 スロット + 到達したものの要素 (最大 12) |
| 空き探索 | 最大 32 |
| **ふつう (伝播 1 周)** | **およそ 800 - 1,200** |
| **最悪 (伝播 32 周)** | **およそ 13,700** |

i8080 の見積もり (196 回) と桁が違うのは、**`max_globals` が 100 ではなく
300** で、伝播の周回が入るためです。

ふつうの側は VM 命令 30-60 個ぶんに当たり、`steps_per_cycle` が 50 なので
**GC 1 回でスキャンが 1 周期ぶん伸びる**見込みです。最悪の側はその 10 倍強です。

**ここまでは「確保のたびにフル回収」でした。** `ARRAY_SP` は減らないので、
一度 `max_arrays` に届いたら以後の確保が毎回走査を呼び、1 スキャンに入る
確保の数だけ回収が重なっていました。**2026-11-28 に空き表にして、走る回数を
落としました** (下記)。以下の実測はその前の数字です。

### 実測した停止時間

**命令列を変えずに回収の有無だけを切り替えて測りました。** プログラムから
`ARRAY_SP` を書き戻します — `$EM20039 = 32` なら毎回回収、`= 0` なら一度も
回収しません。1 周 9 命令のループを 4 秒 × 3 回まわし、周回数と `STEP_COUNT`
を同じ時点で読みます。

**KV-X500**

| 生きているスロット | 回収 1 回 | スキャン (回収なし) | スキャン (毎回回収) |
|---|---|---|---|
| 1 | **0.16 ms** | 0.21 ms | 1.09 ms |
| 26 | **0.32 ms** | 0.21 ms | 2.01 ms |

**上の見積もり (VM 命令 30-60 個ぶん) は当たっていました。** 0.16 ms はこの
機種の 38 命令ぶん、0.32 ms は 76 命令ぶんです。

**効くのは 1 回の山ではなく回数です。** 1 周 9 命令なので 50 命令のスキャンに
確保が 5.5 回入り、**スキャンが 0.21 ms から 1〜2 ms へ、5〜10 倍に伸びます。**

**測るときは前のプログラムの生存を消すこと。** 汎用グローバルはプログラムの
読み込みでは消えません。生存 26 個を置いたあとに軽い側を測ると、置いた
グローバルが生きたままなので軽い側が重い側の数字になります。**最初にこれで
2 倍ずれました。** 軽い側の先頭で `$live1 = nil` を入れて揃えています。

**名前は `$x` では駄目でした。** 三菱では X (入力) の族そのものと読まれて
ERROR=22 で止まります。キーエンスでは汎用グローバルとして通るので、機種を
移して初めて出ました ([melsec.md](melsec.md#グローバル変数名もデバイス族に見えてはいけない))。

**iQ-R は見込みと逆でした。** 1 命令に KV-X500 の 30 倍かかる機種なのに
(124 µs 対 4.2 µs)、**回収 1 回はほぼ同じ時間です。**

**iQ-R**

| 生きているスロット | 回収 1 回 | スキャン (回収なし) | スキャン (毎回回収) |
|---|---|---|---|
| 1 | **0.24 ms** | 6.20 ms | 7.56 ms |
| 26 | **0.43 ms** | 6.20 ms | 8.61 ms |

**回収は命令の振り分けを通らないからです。** 1 命令はオペコードの巨大な
分岐を毎回降りますが、回収はただの `FOR` です。**本体が遅い機種ほど回収は
相対的に軽くなります** — スキャンの伸びは KV-X500 で 9.6 倍、iQ-R で 1.4 倍。

**確保を詰めた最悪も測りました (iQ-R)。** `ARRAY_SP` はループの外で 1 度
書けば足ります (回収で返したスロットでは進めないので 32 のままです)。1 周
7 命令・1 スキャンに確保 7.2 回で、**スキャンは 6.20 ms から 9.29 ms** に
なりました。1 周を 4 命令まで詰めても確保は 12.5 回/スキャンが上限なので、
**最悪でもスキャンは倍までです。**

**四則演算の速度は別に測りました。** iQ-R で 9,557 命令/秒 (前回 11,615)。
測ったループは回収のコードを 1 行も通らないので、落ちているのは本体が
太ったこと自体です。ただし前の測定の後にクラスも入っているため、
**この差を回収のせいにはできません** (doc/melsec.md)。

### 空き表にしました (2026-11-28)

**走査を速くしたのではなく、走る回数を落としました。** i8080 で効いた形
(roadmap の「i8080 の反応が重い」) をそのまま PLC へ移しました。

- **印を捨てずに空き表として使う。** 走査のあと、印の付かなかった枠を順に
  配ります。走査が「確保ごとに 1 回」から「空き表を使い切るごとに 1 回」に
  なります
- **しおりを置く** (`GC_CURSOR`)。配る順は増える一方なので、しおりより手前に
  空きは残っていません。0 から舐め直すと 32 枠の検査が確保ごとに乗ります
  — **i8080 ではこれが 2 番目の山でした** (902 → 607 ms)

**配った枠に印は立てません。** ここだけ i8080 と違います。印は「到達した
ときの型タグ」なので、**「配り済み」を表す値がありません** — 1 を入れると
走査が中身の読み方を決められなくなります。しおりが戻らないことが「二度
配らない」の中身なので、印は要りません。

**電源投入とリセットのしおりは `max_arrays`** です (「空き表は空」)。走査
する前に配ると、**消えていない印を空き表と読んで生きている枠を配ります。**

#### 古い空き表を配っても壊れない理由

**プールを指す参照は確保でしか生まれません。** 代入 (`a = b`) は値スロットを
写すだけ、ハッシュやオブジェクトが持つスロット番号も確保で入ったものです。
だから走査の時点で印が付かなかった枠は、**その後に誰かから指されることが
ありません** — 配るまでは。配った枠はしおりが外します。

**走査のあとに死んだものは次の走査まで空きません。** 安全側に外すだけで、
生きているものを配ることはありません。

#### 見込み (実機は未確認)

上の実測から組み直した値です。**1 スキャンに確保が 5.5 回 (KV-X500) /
7.2 回 (iQ-R) 入る形で、生きているスロットが 1 個なら空き表は 31 枠**です。

| | 回収なし | 毎回回収 (前) | 空き表 (見込み) |
|---|---|---|---|
| KV-X500 / 生存 1 | 0.21 ms | 1.09 ms | **約 0.24 ms** |
| KV-X500 / 生存 26 | 0.21 ms | 2.01 ms | **約 0.50 ms** |
| iQ-R / 生存 1 | 6.20 ms | 7.56 ms | **約 6.26 ms** |
| iQ-R / 生存 26 | 6.20 ms | 8.61 ms | **約 6.72 ms** |

**生きているスロットが多いほど効きません。** 生存 26 なら空き表は 6 枠しか
無く、6 回の確保ごとに走査が入ります。**効くのは「使っては捨てる」形**
(文字列の作り直し、ループの中の配列) です。

#### 値段

| | 行 | 実行行 |
|---|---|---|
| KV-5000 / KV-X500 / iQ-R | +564 | **+308** |
| Q | +267 | **+146** |

**空き表の探索が確保ごとに 2 回展開されます** (配る / 走査してもう一度)。
確保は 12 箇所あり、生成器は確保のたびに展開します — 使う Z が場所ごとに
違うので共通の手順にできない、という前からの事情です。

**探索は 1 つの `IF` に詰めました。** 「まだ見つかっていない」と「印が無い」を
`AND` でつないで、入れ子の 3 行を省いています (12 箇所 × 2 回で 72 行)。
見出しのアドレスは毎周載せますが、`Z6` は返すので外に影響しません。

**Q が 146 行増えます。** 容量のために配列・ハッシュ・文字を外している機種
なので心配でしたが、**取り込みが通り実機も 122 値一致しました** (2026-11-28)。
`new_object` と `@` の確保が残っているため 0 にはなりません。

### `steps_per_cycle` は 50 のままにする

**回収は見積もりの式を変えません。**

```
スキャン ≒ steps_per_cycle × 1 命令の時間 + そのスキャンの確保回数 × 0.4 ms
```

後ろの項は実測で 2-3 ms、詰めても 5 ms ほどです。ウォッチドッグには遠く、
**既定の 50 を変える理由は見つかりませんでした。**

**1 スキャン 1 回までに切る案も入れません。** 測る前は上限を決める価値が
あると見ていましたが、**止められるのが 3 ms しかない**うえに、切ったスキャンは
数命令しか進まないので命令の流量が落ちます。スキャンを詰めたい設備には
`steps_per_cycle` を下げるという既存の手があり、そちらは回収と関係のない
プログラムにも同じように効きます。

### 機種ごとの事情

| 機種 | GC を積むか | 理由 |
|------|-----------|------|
| KV-5000 / KV-X500 | 積む | 最大のスクリプトが上限の 25% で余裕がある |
| MELSEC iQ-R | 積む | `vm_02_body.st` が 255KB。**容量を確かめてから** |
| MELSEC Q | **積まない** | 配列・文字列・ハッシュを外しているのでプールを使わない |

**Q は機能を外しているので、GC のコードも落とします** (`features.rb`)。
クラスだけは有効なのでオブジェクトは作れますが、`new` の確保が尽きる
使い方は装置プログラムに無く、尽きたときは今までどおりエラー 10 で
止まります。

### 入れる順

どれも単体テストと生成コードの読みで確かめられます。

1. ~~**確保を 1 つの生成ヘルパーに寄せる**~~ — 済み。振る舞いを変えないので、
   生成物がバイト一致のままであることで確かめた (`alloc_check` /
   `alloc_check_pair` / `alloc_header_into` / `alloc_commit`)
2. ~~**GC 作業領域を配置に足す**~~ — 済み。予備から 12 ワード。既存の
   アドレスは動いていない
3. ~~**マークと空き探索**~~ — 済み
4. ~~**到達性の伝播**~~ — 済み。**3 と一緒に入れました** (下記)
5. ~~**`new_hash` を 2 回確保に直す** と `GC_PINNED`~~ — 済み
6. ~~**4 機種ぶん再生成して実機**~~ — 済み。4 機種とも通った
7. **空き表にする** — 済み (2026-11-28)。**実機は未確認**

#### 3 と 4 を分けられなかった

**段階 3 だけを入れると、黙って値が変わる窓が開きます。** ルートだけの
マークは配列の要素を辿らないので、`a << "x"` を繰り返す形で生きている
文字列を回収します。段階 3 を入れた時点でテストがそれを捉えました
(`a[0] == "ab"` が成り立たなくなる)。

止まるより悪いものを一度でもコミットに入れたくないので、伝播まで
まとめて入れました。**分けた単位は「確かめられるか」でしたが、
「途中の状態が安全か」も単位の条件でした。**

### 確かめ方

i8080 のテストと同じ形を PLC でも置きます。

```ruby
a = "abcdefgh"
10.times do
  a << "z"
  a = a[1, 8]
end
```

GC が無ければ 20 スロット以上要るので、32 スロットを超えるまで回数を
増やして確かめます。加えて PLC 版でしか起きない 5 つを見ます。

| 見るもの | 落ちていたら何が起きるか |
|---------|----------------------|
| オブジェクトの `@` が生き残る | `@name` が別の値に変わる |
| ハッシュの要素が生き残る | 鍵や値が変わる |
| 入れ子の配列が生き残る | 内側が変わる |
| `TT_OBJECT` の **-1** | 隣のスロットをマークし、本物を回収する |
| ハッシュの 2 スロットが離れていても動く | 値配列が読めない |

### 踏んだ不具合

**1. 要素数 0 の配列で、書いていない要素を読んでいました。**

伝播の要素ループを「要素数 - 1 まで。ただし 0 なら引かない」と書いたので、
**要素数 0 でも要素 0 番を 1 つ読んでいました。** そのスロットに前に入って
いたものが文字列だと、バイト列が型タグ (7-10) に見えることがあります。値の
ワードも中身のバイトなので、**スロット番号が 32 を大きく超え、プールの外へ
印を書きに行きます。** 三菱なら範囲外の添字、キーエンスなら演算エラーです。

`IF 要素数 > 0 THEN` で囲む形に直しました。**シミュレータでは絶対に出ません** —
Ruby の `0.times` は 1 回も回らないので、PLC 側だけが要素を読んでいました。
生成コードを読んで気づきました。

**2. 伝播の打ち切りに `BREAK` を使っていました。**

内側の `FOR` を抜けるだけなので動きはしますが、**エラーで命令ループを抜ける
`BREAK` と見分けが付きません。** 生成コードを見張るテストが 5 箇所で捉え、
比較 1 回で空回りさせる形に直しました。

**3. レジスタの先頭を焼き込む検査に当たりました。**

ふつうのレジスタ参照は窓 (`REG_BASE`) を通さなければならず、それを見張る
テストがあります。**回収だけは窓の外も見る**必要があるので、「その行は
すべて回収の走査であること」を求める形に変えました。

### 実機で確認したこと (iQ-R)

[test_45_gc_melsec.rb](../test/ruby_programs/test_45_gc_melsec.rb) の 8 項目が
**MELSEC iQ-R で一致しました。** 14 スロットを生かしたまま使い捨てを 50 回
作るので、**36 回以上の回収が走った上で**値が保たれていることになります。

| 見たもの | |
|---------|---|
| 50 回まわりきった | 回収が走っている (案 2 ならエラー 10 で止まる) |
| 配列の要素・ハッシュの値・`@`・入れ子 | どれも生き残る (伝播が効いている) |
| **要素数 0 の配列**を生かしたまま回収 | 符号なしの `0 - 1` を踏んでいない |
| 尽きた後にハッシュを作る | 2 本を別々に取り、1 本目が守られている |

**既存の 28 本も通りました** (全 29 本・274 値・NG なし)。ハッシュの確保を
2 回に変えたので、`test_22` / `test_23` / `test_24` が特に効いています。

**要素数 0 はシミュレータでは出ません。** Ruby の整数は -1 のままなので
空回りするだけですが、実機の符号なしワードでは 65535 になり `FOR` が
65536 回回ります。実機でしか出ない形なので、プールに空の配列を残した
まま回収させています。

回収まで入れた生成物の容量は **162KB / 320KB (51%)** でした。

### 実機で確認したこと (KV-5000)

**30 本・276 値・NG なし。** `test_45_gc.rb` の 8 項目も iQ-R と同じく
通りました。CPU も綴りも違う機種で同じ結果が出たので、回収の手順自体に
機種差は無いと見ています。

**取り込みの照合でコメントが引っかかりました。** 生成物に使った em ダッシュ
(U+2014) が windows-31j に無く、ニーモニックの書き出しで `?` になって
戻ります。41 行すべてコメントで、**プログラムは一致していました**が、
`rake transfer` が毎回「違い」と言う状態になるので使う文字を変えました
([KV Studio の変換上限](architecture.md#kv-studio-の変換上限))。

### 実機で確認したこと (KV-X500)

**29 本・274 値・NG なし** (タイマ・カウンタは KV-5000 専用なので 1 本少ない)。
`test_45_gc.rb` の 8 項目も通りました。

**取り込みの照合は 13 本すべて一致しました。** em ダッシュを外した効果が

**4 機種そろいました。** 回収が実際に走るのを見たのは iQ-R・KV-5000・

## i8080 へ戻すときの助言

**移しました** (2026-11-25)。`rake test:i8080` は 157 本・867 assertions で
通っています。以下は何をどう移したかの記録で、**そのまま移ったところ、
i8080 では形が変わったところ、PLC で踏んだ不具合のうち i8080 でも待って
いたものを分けて書きます。**

**回帰テストは test/test_i8080_gc.rb です。** 配列・ハッシュ・オブジェクトの
中の文字列が残ること、入れ子を辿ること、要素数 0 の配列を生かしたまま
回収しても走り切ることを見ます。**書く前にエミュレータで不具合を再現**して
あるので、直ったことがそのまま分かりました。

### 直したこと — 前の版は生きているスロットを配っていた

`col_gc_alloc` のコメントは「配列要素・Hash 値からの間接参照はスキャンしない
(保守的)」と書いていますが、**これは保守的の逆です。** 保守的とは多めに印を
付けることで、少なめに付けるのは**生きている値を配ること**です。

**入れ子だけの話ではありません。**

```ruby
a = ["ab"]        # 配列には印が付くが、"ab" のスロットには付かない
h = { x: "ab" }   # ハッシュも同じ
o = Foo.new       # @s = "ab" の "ab" は誰も見ていない
```

[(i8080 では未実装) 入れ子の走査](#5-i8080-では未実装-入れ子の走査) は
「入れ子を使うプログラムがプールを使い切ることはほぼ無い」と書いていますが、
**文字列を 1 つ持った配列も同じ形**です。使い切った後は確保ごとに走るので、
`a[0]` が別の文字列に化けます。

**オブジェクトはルート走査から丸ごと漏れています。** 今のルートはレジスタ
64 とグローバル 64 で、見ている型は TT_STRING / TT_ARRAY / TT_HASH の 3 つ
だけです。**オブジェクト自身に印は要りません** — コレクションプールではなく
別のオブジェクトプールに居るためです。**要るのはインスタンス変数の方**で、
7 個それぞれがプールを指します。オブジェクトプールの 32 スロットもルートに
足してください。

### そのまま移るもの

| PLC 版 | i8080 ではどうなるか |
|---|---|
| 到達性を伝播する (印が増えた周だけ回す) | そのまま。**早抜けしてよい** — PLC で `BREAK` を避けたのは PLC 固有の事情で、i8080 には無い |
| 文字列の中身は辿らない | そのまま。中身はバイト列で、値スロットではない |
| ハッシュの中身も辿る | 辿る必要は同じ。ただし i8080 は鍵と値が交互なので読み方が違う |
| `ARRAY_SP` は巻き戻さない | `col_sp` も同じ。巻き戻すと生きているスロットを上書きする |

### 形が変わるもの

**印はビットマップのままでよい。** PLC がスロットの見出しに置いたのは、32
スロットが 16 ビットに入らず、三菱に都合の良いビットシフトが無いからです。
i8080 には `gc_bitmap` が既にあり、見出しは 2 バイト (型と要素数) で予備が
ありません。**走査済みの 2 枚目を 8 バイト足すだけ**で足ります。

**「届いたときの型タグ」を覚える必要はありません。** PLC のスロットの見出しに
型が無く (配列なら要素数、オブジェクトならクラス番号)、中身の読み方が分から
ないので、印に型タグそのものを入れました。**i8080 は +0 が `COL_TYPE_*`
です。** 読めば分かるので、印はビット 1 つで済みます。

**ピン留め (`GC_PINNED`) はまだ要りません。** PLC で要ったのはハッシュが
**2 スロット** (鍵の配列と値の配列) で、1 つめを確保してからレジスタへ書く
までの間に 2 回目の確保が走るからです。**i8080 のハッシュは 1 スロット**で、
`col_alloc` の呼び出しは 7 か所ありますが 1 つの命令で 2 回通る経路はあり
ません。**2 回通る経路を作ったその時に要ります。**

**確保の入口は 1 か所で済んでいます。** PLC では 9 か所に展開されるので、
まずヘルパーに通す下準備が要りました
([確保を 1 本にまとめる](#確保を-1-本にまとめる--ここが前提作業))。i8080 は
`col_alloc` から `col_gc_alloc` を呼ぶ 1 か所なので、**この前提作業は要りません。**

### PLC で踏んだ不具合のうち、i8080 でも待っているもの

**要素数 0 のときは要素を 1 つも見ないこと。** 空配列の経路は既にあります
(`vm_main.a80` の「空配列: スロット確保して count=0」)。前にそのスロットに
入っていた文字列のバイトが残っていると、**値スロットの +0 が TT_STRING や
TT_ARRAY に見え、でたらめなスロット番号でビットを立てます。**

**被害は PLC より大きいです。** PLC はプールの外に印を書くだけで済みましたが、
i8080 の `gc_bitmap` は 8 バイトしかないので、**番号 64 以上では隣の変数を
壊します。** 要素数 0 の検査に加えて、**スロット番号の上限検査を入れてください**
(PLC 版には無い、i8080 で足すべき守りです)。

**これはテストでは出ません。** PLC ではシミュレータが `0.times` で 1 回も
回らないため再現できず、**生成コードを読んで見つけました。** エミュレータの
メモリが 0 から始まるなら i8080 でも出ません。**先にそのスロットへ文字列を
入れ、空配列として使い回させるテスト**を書いてください。

### 速さの見込みは PLC から持ってこないこと

PLC では回収 1 回が 0.16–0.43 ms で、スキャンの伸びが 2–3 ms に収まったので
**上限を縛る機構を入れませんでした** ([実測した停止時間](#実測した停止時間))。
**これは i8080 に持ってこられる結論ではありません。** 64 スロット × 要素 8 個を
2 MHz で辿るので桁が違います。

**スキャン周期という締め切りが無い**代わりに、**使い切った後は確保ごとに走る**
ところは同じです。[`steps_per_cycle` は 50 のままにする](#steps_per_cycle-は-50-のままにする)
で捨てた 2 つの案のうち、**「空きスロットを覚える」方は i8080 では効くかも
しれません。** 測ってから決めてください。

### オブジェクトプールは別の話

**i8080 のオブジェクトプールには回収がありません。** `OBJ_SP >= MAX_OBJECTS`
(32) で `vm_error` です。PLC はオブジェクトも同じプールに居るので一緒に
回収されますが、i8080 は別の領域なので**別の仕組みが要ります。**

**今回は入れないと決めました** (2026-11-25)。`Foo.new` を 33 回呼ぶまで
誰も困らないので、回収の移植とは切り離して後日やります。

入れるときは、**オブジェクトは到達性の起点でもあり対象でもある**ので、印の
仕組みを 2 つ持つことになります。いまのルート走査は「オブジェクトは全部
生きている」前提で 32 スロットを無条件に見ており、そこを変える作業です。

**PLC は同じプールに置いたので無料で得ていました。** 分けた代償がここに
出ています — 分けたのはオブジェクトのインスタンス変数を 7 個に抑えて
スロットを 32 バイトに収めるためで、それ自体は i8080 の容量に合った判断です。

### 実機で確認したこと (ND8080)

**エミュレータでは出ない形をここで見ました。** 電源投入直後のメモリは 0 では
ないので、**書いていない要素を値スロットとして読んだとき**に古いバイト列が
型タグに見えます。入れた 2 つの守り (要素数 0 では 1 つも見ない / 範囲外の
スロット番号を捨てる) が効く場面は、メモリが 0 から始まるエミュレータでは
再現しません。

捨てる文字列を 70 個作って 64 スロットを使い切らせ、走り終わったあとに
メモリを読み戻します。`programs/` は利用者の置き場 (`.gitignore` 済み) なので、
プログラムはここに書いておきます。

```ruby
a = ["keep"]
e = []
n = [["deep"]]

70.times do
  s = "xy"
end

b = 1
```

```
STATUS=2 ERROR=0
R1 → スロット 1  要素数=1   [0] = "keep"      配列が持つ文字列が残った
R2 → スロット 2  要素数=0   (空の配列)         生かしたまま回収させて無傷
R3 → スロット 5  要素数=1   [0][0] = "deep"   入れ子を辿っている
```

**手順** (`rake i8080:upload` が書き込みと照合までやります):

```bash
rake i8080:build
rake i8080:upload SRC=programs/i8080_gc.rb   # 4 領域すべて照合OK
ruby tools/nd8080.rb run 8400
```

読み戻しは `ND8080::Remote#save` でレジスタファイル (0x8100-) と
コレクションプール (0x96C0-) を取り、値スロットを解釈します。

**ROM モードから入りました。** `rake i8080:upload` が自前で見分けて
`bank_init.hex` を流し、拡張 RAM に複製してから書き込みます。

## テスト

i8080 では以下のテストで検証しています:

```ruby
def test_gc_string_loop
  # 10 回ループで毎回 slice + string literal → GC なしなら 20+ スロット必要
  src = <<~RUBY
    a = "abcdefgh"
    10.times do
      a << "z"
      a = a[1, 8]
    end
    b = a
  RUBY
  board = run_ruby(src)
  assert_equal :finished, board[:result]
  assert_equal "zzzzzzzz", board[:board].reg_string(2)
end
```

PLC に適用する際も、同様のパターン (ループ内で文字列操作を繰り返し、
16 スロットを超える確保が必要になるケース) でテストします。
