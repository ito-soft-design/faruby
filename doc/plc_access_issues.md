# plc_access で見つかった問題

faRuby の実機確認中に [plc_access](https://github.com/ito-soft-design/plc_access) で
気づいた点の控えです。後で直すための覚書で、faRuby 側の課題ではありません。

確認環境: plc_access 0.2.1 / Keyence KV-5000 / `KvProtocol`

## 1. ラッチリレー L の名前が生成できない

`KvDevice#name` が **L だけ** nil を返します。番号によらず再現します。

```ruby
K = PlcAccess::Protocol::Keyence::KvDevice
(K.new("L0") + 100).name    # => nil
(K.new("MR0") + 100).name   # => "MR604"
(K.new("B0") + 100).name    # => "B64"
```

名前 → 番号の向きは動きます (`K.new("L100").number` は 100)。番号 → 名前の
向きだけが欠けています。MR / R / B / T / C / DM / EM / ZF / TC / CC は
いずれも正しく返します。

通信を伴わない純粋な計算なので、PLC の挙動ではなく gem 側の問題です。

**影響**: 番号からデバイスを組み立てるコードが L で動きません。faRuby では
プローブ用のスクリプトで踏みました (番号から名前を自作して回避)。

## 2. タイマ・カウンタの接点がビットデバイスと判定されない

`bit_device?` が T と C で false を返し、読み取り値が真偽値ではなく整数になります。

```ruby
K.new("MR100").bit_device?   # => true
K.new("T0").bit_device?      # => false   ← 接点なので true のはず
K.new("C0").bit_device?      # => false   ← 同上

plc["MR100"]   # => false      真偽値
plc["T0"]      # => 224        整数 (ワードとして読んでいる)
plc["C0"]      # => 224
```

KV では `T0` はタイマの**接点**で、現在値は `TC0`、設定値は `TS0` と
別デバイスです。接点はビットとして扱うのが正しいはずです。

**影響**: faRuby は T / C をビットデバイスとして扱い、書き込みに
`SET(T0:Z6)` / `RES(T0:Z6)` を使います。一方コンソールの `dev T0` は
plc_access 経由でワードとして読むため、VM と表示が食い違います。

## 3. ラッチリレー L に書き込めない (要調査)

```ruby
plc["L16"] = 1   # => RuntimeError: E1
plc["L1000"] = 1 # => RuntimeError: E1
```

読み取りは通ります。MR / R / B は同じ書き方で書き込めます。

E1 は PLC が返したエラーコードなので、gem の問題か PLC 側の制限かは
切り分けられていません。この機体で L 領域が割り付けられていない可能性も
あります。

## 4. タイマ・カウンタの現在値に書き込めない (おそらく PLC の仕様)

```ruby
plc["TC0", 2] = [1234, 0]   # => RuntimeError: E0
```

読み取りは通ります (`plc["TC0"]` は現在値を返す)。現在値はプログラムが
更新するものなので、外部から書けないのは PLC として妥当だと思われます。
gem の問題ではなく仕様の確認が必要な項目として残しておきます。

## 5. タイマ・カウンタの 32 ビット読みが 2 デバイスをまたぐ

```ruby
plc["TC0"]          # => 10        TC0 の現在値
plc["TC0", 2]       # => [10, 30]  TC0 と TC1
```

`read_device_long("TC", 0)` は TC0 と TC1 を繋げて 1966090 を返します。
タイマの現在値は 1 個 16 ビットなので、32 ビットとして読むと隣のタイマまで
含んでしまいます。

ワードデバイスとしては素直な挙動なので不具合とは言い切れませんが、
`TC` を 32 ビットで読む場面は無いはずなので注意点として残します。
**実際、これで一度読み違えました。** KV スクリプトの `T0.D` が返す 10 と
食い違って見え、原因の切り分けを誤らせました。
