# 文字列の計画

ロードマップ [項目 6](roadmap.md) のうち String の設計メモです。まだ実装して
いません。Array と Hash が終わり、残るのはこれだけです。

## 逆アセンブルで分かったこと

mrbc 3.3.0 の出力です。

```
s = "hello"            OP_STRING [1, 0]        R[1] = pool[0] の複製
"x#{s}y"               OP_STRING + OP_STRCAT を 2 回
s + t                  OP_ADD    [8]           ← 数値と同じ命令
s * 2                  OP_MUL    [12]          ← 同上
s == "hello"           OP_EQ     [8]           ← 同上
s[0]                   OP_GETIDX [8]           ← 配列・ハッシュと同じ命令
s.length / s.size      OP_SEND
s << "z"               OP_SEND (<<)
s.empty? / s.include?  OP_SEND
["a", "b"]             OP_STRING を並べて OP_ARRAY2
{ "x" => 1 }           OP_STRING + OP_HASH
```

**新しい命令は `OP_STRING` (0x51) と `OP_STRCAT` (0x52) の 2 つだけ**です。
残りはすべて実装済みの経路に枝を足す形になります。Array・Hash と同じ形です。

### 見落とせない点が 3 つあります

**1. `OP_STRING` は毎回複製します。** Ruby の文字列は変更できるので、
同じリテラルを 2 回書けば別のものになります。`s = "a"; t = "a"; s << "b"` で
`t` が変わってはいけません。**リテラルを書くたびにプールを 1 スロット使う**
ということで、ループの中に文字列リテラルを書くと使い切ります。配列リテラルと
同じ制約です。

**2. `==` は中身で比べます。** 今の `OP_EQ` は型と値の一致で、文字列の値は
スロット番号です。別のスロットに入った同じ内容が等しくなりません。
**ハッシュの鍵**も同じ (`find_hash_key`) なので、両方に枝が要ります。

**3. 定数プールに入りません。** 値スロットは 4 ワードで、文字列は入りません。
バイトコードと同じように**FM に文字列定数の領域**を作り、値スロットには
「先頭位置と長さ」を入れます。

## 決めること

### 文字コード — 内部は UTF-8

**内部表現は UTF-8** です。mrbc の定数プールにはソースファイルのバイト列が
そのまま入るので、ソースを UTF-8 で書けば何もしなくても UTF-8 になります。

外部で扱うのは **ASCII と Shift_JIS だけ**です。

**全部を載せた変換表は持てません。** Shift_JIS の漢字は JIS X 0208 で
約 7000 字あり、対応表は 14000 ワードほどになります。FM の空きは
1 インスタンスあたり 872 ワードしかありません。

### 変換表は使う文字だけ

**ホストがプログラム中の文字列リテラルから非 ASCII の文字を集め、その分
だけの表を作って FM に置きます。** 20 文字使っていれば 20 件です。
デバイスへは Shift_JIS で出るので、表示器がそのまま読めます。

1 件 2 ワードです。

| ワード | 内容 |
|-------|------|
| +0 | Unicode のコードポイント (Shift_JIS にあるものは全て 0xFFFF 以下) |
| +1 | Shift_JIS のバイト。1 バイトの文字 (半角カナ) は 0x100 未満 |

実行時は UTF-8 を復号してコードポイントにし、表を引きます。3 バイトの
UTF-8 は `(b0 & 0x0F) * 4096 + (b1 & 0x3F) * 64 + (b2 & 0x3F)` で出ます。
ASCII (0x7F 以下) は表を引かずそのまま通します。

**表に無い文字は変換できません。** リテラルに書いていない文字は、
デバイスから読んだものを書き戻すときなどに現れます。そのときは止めます。
黙って化けさせるより、書いていない文字が出たと分かるほうがましです。

### 置き場所 — 配列プールのスロット 1 つ

Hash と同じく**新しいプールを作りません**。1 スロット 50 ワードのうち、
先頭 2 ワードが見出しで残り 48 ワードを使います。

```
  R[x]  タグ=TT_STRING  下位=スロット番号

  スロット5  バイト数=5  [ "he" "ll" "o\0" ... ]
```

**1 ワードに 2 バイト詰めます。** 96 バイトです。1 バイト 1 ワード (48 バイト)
のほうが取り出しは速いのですが、**PLC のデバイス文字列が 2 バイト 1 ワード**
なので、そちらに合わせるとデバイスとの行き来がワード単位の写しで済みます。
文字列を使う目的の多くがデバイスとのやり取りなので、こちらを採ります。

96 バイトは ASCII なら 96 文字、日本語 (UTF-8) なら 32 文字です。

### 長さは文字数

`"あ".length` は Ruby では 1 です。バイト数の 3 ではありません。**Ruby に
合わせます。** UTF-8 は継続バイトが `10xxxxxx` なので、それ以外を数えれば
文字数になります。バイトを 1 つずつ見る必要がありますが、96 バイトなら
高々 96 回です。

`s[0]` も文字単位です。同じ理由で先頭から数えます。

### `==` と鍵の一致

`OP_EQ` に文字列の枝を足し、バイト数が同じならワード単位で比べます。
2 バイト詰めなので、比較の回数はバイト数の半分で済みます。

ハッシュの鍵も同じ判定にします。`find_hash_key` は今「タグと値の両方」で
比べていますが、文字列だけは中身を見る枝が要ります。

## 進め方

1. **リテラルと代入** — FM の文字列定数領域、`OP_STRING`、`OP_MOVE`。
   デバイスへの書き込み (`$DM100 = "abc"`)
2. **比較と連結** — `OP_EQ` / `!=`、`OP_STRCAT`、`+`、ハッシュの鍵
3. **メソッド** — `length` / `size` / `<<` / `empty?`、`[]` (文字単位)
4. **デバイスから読む** — デバイス文字列を faRuby の文字列にする

段階 1 が終われば実機で「文字列を作ってデバイスへ書く」が通ります。
そこが一番使う形です。

## 先送りする論点

**`*` (繰り返し)。** `s * 2` は `OP_MUL` です。数値の掛け算の枝に文字列の
判定が入るので、**最も多く通る経路が長くなります**。後回しにします。

**`sub` / `gsub` / `upcase` などの加工。** どれも新しいスロットを取ります。
使う場面を見てから決めます。

**書式化 (`format` / `%`)。** 数値を文字列にする `to_s` が要ります。
桁を出す処理を KV スクリプトで書くことになるので、独立した段階にします。

## 確認が要ること

- **PLC のデバイス文字列のバイト順。** 1 ワードの下位バイトが先か後か。
  ここを間違えると読み書きが全部ひっくり返ります。実機で確かめます
- 変換表の枠をいくつにするか。FM の空きは 872 ワードなので、2 ワード/件
  なら 400 件ほどまで置けます。溢れたら転送前に止める検査を足します
- 96 バイトで足りるか。足りなければスロットを大きくするか、複数スロットに
  またがる形を考えることになります
- `OP_STRING` がリテラルごとにスロットを使うため、16 スロットがどれくらい
  持つか。ループの中のリテラルは特に危ない
