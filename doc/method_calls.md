# メソッド定義・呼び出しの計画と記録

ロードマップ [項目 3](roadmap.md) の設計メモと、実装したときの記録です。
**実装済みです。** 設計を決めた時点の文章をそのまま残してあるので、
「これから作る」書き方の箇所があります。

## 何が必要か

`def` と、そのメソッドの呼び出しです。

```ruby
def clamp(v)
  return 0 if v < 0
  v * 2
end
$DM100 = clamp(3)
```

## 逆アセンブルで分かったこと

mrbc 3.3.0 の出力です。

```
[top] nlocals=1 nregs=4 syms=["clamp", "$DM100"] children=1
  OP_TCLASS [1]          R[1] = 定義先のクラス (トップレベルでは Object)
  OP_METHOD [2, 0]       R[2] = 子 irep 0 から作ったメソッド
  OP_DEF    [1, 0]       R[1] に symbols[0] という名前で R[2] を登録
  OP_LOADI_3 [2]
  OP_SSEND  [1, 0, 1]    self.symbols[0](R[2])
  OP_SETGV  [1, 1]
  OP_RETURN [1]
  OP_STOP

  [top.0] nlocals=4 nregs=7 syms=[] children=0
    OP_ENTER  [262144]   引数の形 (aspec)
    OP_MOVE   [4, 1]
    ...
    OP_RETURN [4]
```

設計に効く発見が 3 つあります。

**1. 呼び出しは `OP_SEND` ではなく `OP_SSEND` です。** レシーバを書かない
呼び出し (`clamp(3)`、再帰の `fact(n-1)`) はすべて `OP_SSEND` になります。
実装済みの `OP_SEND` とは別命令なので、両方が要ります。

**2. シンボル表は irep ごとに別です。** 再帰する `fact` では、トップレベルの
`syms` が `["fact", "$DM100"]`、子 irep の `syms` が `["fact"]` で、同じ名前が
別の番号になります。現在は**トップレベルのシンボル表だけ**をデバイス
マッピングテーブルとして転送しているため、この前提が崩れます。

**3. レジスタは窓をずらして共有します。** `OP_SSEND [a, sym, argc]` では
呼ばれた側の `R[0]` が呼んだ側の `R[a]` です。引数は `R[a+1]` から連続します。
つまり**戻り値のコピーが要りません**。`OP_RETURN [b]` で `R[b]` を `R[0]` へ
写してフレームを捨てれば、呼んだ側から見て `R[a]` に結果が入っています。

`OP_ENTER` のオペランドは 24 ビットの aspec で、必須引数の数は `aspec >> 18`
です (引数 1 個で 262144 = 0x40000、2 個で 524288 = 0x80000)。

`vm.c` で裏を取った点:

```c
CASE(OP_SSEND, BBB) {
  regs[a] = regs[0];      /* self をレシーバ位置に置く */
  insn = OP_SEND;         /* あとは OP_SEND と同じ経路 */
}
...
int n = c&0xf;            /* 位置引数の数 */
int nk = (c>>4)&0xf;      /* キーワード引数の数 */
ci = cipush(mrb, a, ...); /* レジスタ窓が a だけずれる */
```

**オペランド C は「引数の数」そのものではありません。** 下位 4 ビットが位置
引数、上位 4 ビットがキーワード引数の数で、15 (`CALL_MAXARGS`) は「配列や
ハッシュにまとめて渡す」印です。faRuby が扱う普通の呼び出しでは C が引数の数と
一致するため、C と定義を比べる現在の検査でよく、スプラットやキーワード付きの
呼び出しは値が一致せずエラーになります。

## 決めること

### IREP テーブル

図で見るなら [irep の構造](architecture.md#irep-の構造) を参照してください。
木から通し番号への並べ方、領域の分け合い方、実行時の切り替えが図にしてあります。

irep が複数になるため、「今どの irep を実行しているか」を VM が持つ必要が
あります。irep ごとに次を並べたテーブルを置きます。

| ワード | 内容 |
|-------|------|
| +0 | バイトコード先頭 |
| +1 | バイトコード長 |
| +2 | 定数プール先頭 |
| +3 | シンボル表先頭 |
| +4 | nregs |

命令フェッチ・`OP_LOADL`・`OP_GETGV` / `OP_SSEND` のシンボル参照は、定数では
なくこのテーブルから引くようになります。**現在の生成コードで固定値になって
いる箇所がすべて 1 段の間接参照になります。**

### 呼び出しフレーム

窓のずれ方と積み方は
[呼び出しフレームとレジスタ窓](architecture.md#呼び出しフレームとレジスタ窓)
に図があります。

積むのは 3 ワードで足ります。

| ワード | 内容 |
|-------|------|
| +0 | 戻り先 PC |
| +1 | 戻り先 irep 番号 |
| +2 | 戻り先レジスタ基点 |

レジスタ基点は現在 `reg_file_base` 固定です。これを VM 状態の 1 ワードにし、
`OP_SSEND` で `基点 + a * 4` に進め、`OP_RETURN` で戻します。

深さの上限はフレーム領域のサイズで決まります。溢れたらエラーで停止します
(PLC はメモリ固定なので、深さを制限してエラーにするしかありません)。
レジスタ基点 + nregs × 4 がレジスタ領域を超える場合も同じです。

### メソッド表

`OP_DEF` は実行時にメソッドを登録します。名前の同一性は irep をまたぐため、
**ホスト側でメソッド名ごとに通し番号を振ります。** 組み込みメソッドで使って
いるシンボル表の仕組みをそのまま広げます。

現在のメソッド名エントリ:

| ワード | 現在 | 変更後 |
|-------|------|-------|
| +0 | 組み込みメソッド番号 | 同じ |
| +1 | 未使用 | **ユーザー定義メソッド ID** |
| +2 | 引数の数 (組み込み) | 同じ |
| +3 | 種別 = 2 | 同じ |

`OP_DEF` は `メソッド表[ID] = irep 番号` を書き、`OP_SSEND` はまず組み込み
番号を見て、0 なら ID でメソッド表を引きます。

### メモリ配置

いちばん影響が大きい変更です。現在の 1 ブロックは

```
VM状態 / レジスタファイル / バイトコード / 定数プール / デバイステーブル / 汎用グローバル
```

で、バイトコード・プール・シンボル表が 1 組しかありません。これを irep ごとに
持つ必要があります。長さが irep によって違うため、ホスト側で詰めて配置し、
IREP テーブルにアドレスを書き込む形になります。

```
VM状態 / レジスタスタック / 呼び出しスタック / IREPテーブル /
  irep0 のバイトコード・プール・シンボル表 / irep1 の… / 汎用グローバル
```

`memory.max_bytecode` などの設定の意味も「全 irep の合計」に変わります。

## 追加する命令

| 命令 | 動作 | 備考 |
|------|------|------|
| OP_TCLASS (0x63) | R[a] = 定義先クラス | オブジェクトが無いので TT_OBJECT のダミーで足りる |
| OP_METHOD (0x58) | R[a] = 子 irep b への参照 | 新しい型タグ (値 = irep 番号) |
| OP_DEF (0x5F) | メソッド表に登録 | 戻り値はメソッド名の Symbol |
| OP_SSEND (0x2D) | self へのメソッド呼び出し | フレームを積む |
| OP_ENTER (0x34) | 引数の数を検査 | `aspec >> 18` と実引数を比べる |
| OP_RETURN (0x38) | フレームを戻す | 現在は VM 停止のみ。フレームがあれば復帰する |

`OP_SEND` (実装済み) も、組み込みに無ければユーザー定義を探すよう広げます。

## 進め方

1. **IREP テーブルとメモリ配置** — 子 irep の転送。実行は 1 つ目の irep だけ
   のまま。ここで既存のテストがすべて通れば土台は正しい — **実装済み**
2. **フレームとレジスタ基点** — `OP_SSEND` / `OP_RETURN` / `OP_ENTER`
3. **`def` の登録** — `OP_TCLASS` / `OP_METHOD` / `OP_DEF`
4. **再帰と深さの制限** — 溢れたときにエラーで止まることを実機で確認

段階 2 と 3 は**分けて検証できない**ため 1 つの変更にまとめました。呼び出しを
試すには `def` の登録が要り、登録しても呼べなければ確認できないためです。
段階 4 は 2・3 と同時に入りました (深さの上限はフレームを積む所で見るため)。

1 が終われば残りは積み上げです。**1 が最も大きく、生成コードの広い範囲に
触ります。** 現在アドレスが定数として焼き込まれている箇所が、すべて IREP
テーブル経由の間接参照になるためです。

### 段階 1 でしたこと

- IREP テーブルと呼び出しスタックの領域を追加。合計が 1 インスタンス
  5000 ワードに収まるよう `max_pool` を 200 から 150 に減らした
- バイトコード・定数プール・シンボル表を irep ごとに詰めて配置し、位置を
  IREP テーブルに記録
- 生成コードの領域先頭を VM 状態経由の間接参照に変更。命令フェッチ・
  `OP_LOADL`・シンボル参照・レジスタがすべて 1 段の間接参照になった
- リセット時にトップレベルの irep に戻す処理を `vm_init` に追加

実機で確認済みです。既存のプログラム (`test_17` / `test_18`) が変わらず動き、
`def` を含むプログラムは転送できて `OP_TCLASS` (未対応、code 99) で止まります。
段階 1 の境界としてこれが正しい動きです。

#### 実行速度の基準値

命令ごとに VM 状態を 1 ワード余分に読むようになりました。実機での測定値です
(KV-5000、`steps_per_cycle: 50`、`instances: 2`、1 つだけ実行)。

| 項目 | 値 |
|------|----|
| 命令/秒 | 約 34,700 |
| スキャン/秒 | 約 694 |
| スキャン周期 | 約 1.44 ms |

**変更前を測っていないため、間接参照による増分は分かりません。** 上の値は
段階 2 以降と比べるための基準値です。

算出したスキャン周期 1.44 ms は、KV Studio のモニターが示すスキャンタイム
最大値 1.59 ms と整合します (こちらは 5 秒間の平均、モニターは最大値)。
下記の間接的な測り方でも値は信用できると判断しました。

測定は `$DM660L` をループごとに 1 増やし、逆アセンブルから求めた 1 周の命令数
(9 命令) を掛けて出しました。当時 VM 状態の `STEP_COUNT` は領域も表示も
ありましたが、**生成コードが更新しておらず**使えませんでした (コンソールの
`status` は常に 0 を表示していました)。後に `INC` で数えるようにしています。

### 段階 2-4 でしたこと

- メソッド表 (ユーザー定義メソッド ID → 本体の irep 番号) の領域を追加。
  32 ワードで、段階 1 で残っていた端数に収まった
- `OP_TCLASS` / `OP_METHOD` / `OP_DEF` / `OP_SSEND` / `OP_ENTER` を実装し、
  `OP_RETURN` をフレーム復帰に対応させた
- メソッド名はホスト側で 1 から通し番号を振る。シンボル表は irep ごとに
  別なので、番号を挟まないと同じメソッドに行き着かない
- 同じ名前のグローバル変数は irep をまたいでも同じスロットを指すようにした
- `OP_ENTER` の aspec は 24 ビットで 16 ビットの EM に収まらないため、生成
  コードでは上位バイトと下位 2 バイトに分けて持つ。必須引数の数は上位バイトを
  4 で割った値 (`aspec >> 18` と同じ)

シミュレータで確認した範囲: 引数なし・引数あり・1 つの式で二度呼ぶ・入れ子・
再帰 (階乗)・途中の `return`・ローカル変数・メソッド内のデバイスアクセス・
グローバル変数の共有・組み込みメソッドとの併用。エラーは未定義の呼び出し
(code 3)、引数の数違いと省略可能引数 (code 6)、深すぎる再帰 (code 5)。

実機でも同じ範囲に加えて、`sum(10)` の 32 ビット結果と実数を返すメソッドを
確認しました ([test_19_method_calls.rb](../test/ruby_programs/test_19_method_calls.rb))。

実行速度は 34,191 命令/秒、スキャン周期 1.46 ms でした。段階 1 の基準値
(34,722 命令/秒、1.44 ms) から 1.5% 遅くなっています。命令の振り分けが
`ELSE IF` の連鎖なので、命令を足すと後ろにある命令の判定が伸びます。
呼び出しを含まないループでの測定なので、これは**呼び出し自体の費用ではなく
連鎖が伸びた分**です。

## 先送りする論点

**ブロック** (ロードマップ項目 4) は `OP_SENDB` で、同じフレーム機構に乗ります。
ただしブロックは外側のローカル変数を読み書きします (`OP_GETUPVAR` /
`OP_SETUPVAR`)。フレームに上位フレームへの参照を持たせるかどうかは、項目 4 に
着手するときに決めます。**今のうちにフレームへ 1 ワード空けておくと後が楽です。**

**self**。トップレベルでもメソッド内でも self は main です。オブジェクトが
無いうちは区別する必要がありません。
